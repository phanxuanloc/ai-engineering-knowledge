# Documentation Excalidraw

Create whiteboard explanations that make an argument visually. A diagram is not formatted prose and Excalidraw is not React Flow with rough borders.

Use this skill only after `docs-diagram` classifies the communication intent and selects Excalidraw. Preserve the orchestration skill's grounded entities, relationships, teaching message, and complexity boundary while translating them into a hand-drawn visual argument.

Canonical educational diagrams optimize for these priorities, in order:

1. Semantic correctness
2. Teaching clarity
3. Visual hierarchy
4. Simplicity
5. Visual consistency and polish

Polish must never override semantic correctness. Spatial placement, containment, grouping, and arrow direction must represent the real concept: containers are real conceptual boundaries, arrows follow actual information flow, and placement must not imply ownership, creation, or relationships that do not exist.

## Choose the medium before drawing

State the teaching job: the 3–5 second takeaway, main and supporting ideas, relationships, visual metaphor, and one focus area. A canonical diagram should communicate its primary lesson within roughly 3–5 seconds without requiring every label to be read. Prefer one primary message, one obvious flow, short labels, limited emphasis, and minimal secondary detail.

- Use normal MDX when two to four short lines are clearer.
- Use Excalidraw for mental models, analogies, conceptual boundaries, cause/effect, before/after comparisons, and “how to think about this” explanations.
- Use `docs-react-flow` for directed pipelines, architecture, lifecycle, orchestration, multi-component systems, or graphs needing automatic layout or exploration.
- Mermaid is an exception for a tiny relationship whose only useful content is its topology. Do not default to it or use it where custom visual teaching adds value.

Stop and hand off to React Flow when the scene accumulates many nodes or edges, subflows, crossings, interactive navigation, or layout logic. Do not manually maintain a graph engine in Excalidraw.

## Inspect the repository first

Read `AGENTS.md`, `DESIGN.md`, this file, `color-palette.md`, `element-patterns.md`, and `review-checklist.md`. Inspect `src/components/Diagrams/ExcalidrawDiagram.tsx`, `scripts/excalidraw-presets.mjs`, and `scripts/build-excalidraw-diagrams.mjs`. Search existing notes and assets before creating anything. Preserve a clear visual; classify existing visuals before proposing migration.

Official Excalidraw behavior and the installed `@excalidraw/excalidraw` renderer are the source of truth. Third-party skills are design references, not file-format authorities.

## Design before JSON

1. Write a one-sentence teaching objective.
2. Identify the main idea, supporting ideas, relationships, visual metaphor, and focus.
3. Choose a pattern from `element-patterns.md`; sketch the reader's eye path.
4. Decide what behavior must be shown rather than labeled: selection, rejection, containment, scarcity, convergence, contrast, or transformation.
5. Choose two to four semantic colors from `color-palette.md`.
6. Only then create scene elements.

Prefer spatial relationships, scale, grouping, whitespace, contrast, annotations, and visual metaphors. Vary shape and size by meaning. Default labels and annotations to free-floating text; add a container only when containment is semantic. One visual should carry one clear message.

Before accepting the composition, read it literally. Ask what each boundary claims to contain, what each position implies, where every arrow says information came from and went, and whether grouping changes the intended meaning. Correct false implications before improving aesthetics.

For Context Engineering mental models, prefer the explicit conceptual sequence when it applies: `Available / Candidate Information → Select / Filter / Assemble → Selected Context → Context Window → LLM`. Sources are candidates, not automatic inputs to the window. Show one or two rejected/noisy examples outside the selected group with a cross-out, faded branch, or visibly blocked path. Inside the Context Window, concise assembled components such as `Task / Instructions`, `Constraints`, and `Relevant Information` are enough; their placement and incoming flow must show that they were assembled before entering rather than generated by the window.

## Composition and typography

- Establish a dominant concept, then secondary concepts, then annotations. Equal visual weight is a failure unless equality is the lesson.
- Keep labels short; paragraphs belong in the article. Use Virgil (`fontFamily: 1`) and approximately 28–32 px for a title, 20–24 px for primary labels, 16–18 px for details, and 14–16 px for notes.
- Size text before finalizing shapes. Allow at least 24–32 px internal padding around primary labels and 16–24 px around secondary labels.
- Use roughly 80–120 px between related major elements; allow 140–200 px when an arrow label or distinct group needs room. Keep 40–60 px inside group boundaries.
- Related items sit closer; unrelated groups sit farther apart. Avoid touching elements and unexplained empty regions.
- Alignment may be clean while positions, angles, strokes, and arrows retain small organic variation. Prefer `roughness: 1–2`, hachure/cross-hatch pastel fills, and restrained asymmetry.
- Avoid uniform card grids, strict symmetry, decorative icons, clouds, stars, callouts, or colors that do not improve comprehension.

## Arrow routing

Arrows encode direction, transformation, causality, or flow. Use the shortest clear route: straight for direct relations, elbow-style for structured routing, and a gentle bend for a softer conceptual relation. Do not mix styles without semantic reason. For canonical technical-learning diagrams, use solid arrows for primary information flow, dashed arrows only for consistently defined candidate/optional flow, and a crossed-out path for rejection. If no distinction exists, use one arrow style.

If arrows cross or travel around half the scene, fix the composition first: regroup, move endpoints or annotations, simplify relationships, or switch to React Flow. Leave enough gap for labels; never place a label on a short arrow where it collides with endpoints. Primary arrows are solid; dashed arrows mean secondary, rejected, optional, or weak movement only when the distinction is explained.

## Source, export, and embedding

- Keep canonical `.excalidraw` source and generated `.svg` together in `static/img/diagrams/excalidraw/`. Do not hand-edit exported SVG.
- Reuse `scripts/excalidraw-presets.mjs`; extend semantic presets there when a repeated need appears.
- Add scenes to `scripts/build-excalidraw-diagrams.mjs`, run `npm run diagrams:build`, and export through the installed Excalidraw renderer.
- Embed with `ExcalidrawDiagram`; provide meaningful `alt`, an insight-focused caption, and a mobile scene when desktop labels would become too small. Surrounding prose must preserve the lesson without the image.

The canonical reference is `context-window-mental-model(.excalidraw|.svg)` with its mobile variant. It demonstrates candidate sources converging on an explicit selection stage, visible rejection of noise, selected context entering a finite window, assembled context components, a clear LLM endpoint, responsive embedding, and accessible prose. Imitate its teaching discipline, not its exact layout.

## Mandatory render-review loop

Run `npm run diagrams:build`, inspect the rendered output, fix it, and render again. JSON validity is not visual correctness. Inspect desktop and mobile variants, then verify the page at desktop/mobile widths and in light/dark site themes. Use `review-checklist.md` for every changed scene.

Finish with `npm run typecheck` and `npm run build`. Do not accept clipping, overlap, unreadable labels, ambiguous arrows, unbalanced whitespace, or a diagram that adds no value beyond prose.
