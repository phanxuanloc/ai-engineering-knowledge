# Distributed Cache Design

## TL;DR

<TLDR>
Cache là **fast copy**, không phải source of truth. Nó giảm latency và repeated read load nhưng đổi lại thêm freshness, invalidation và failure complexity. Production cache design phải phân biệt **Hot Key** với **Cache Stampede**, chọn read/write strategy theo correctness requirement và không dùng TTL như giải pháp duy nhất cho security-critical freshness.
</TLDR>

## Why It Matters

Cache thường được thêm vì một lý do rất hợp lý: Database đang chịu quá nhiều repeated reads. Nhưng ngay khi cache xuất hiện, hệ thống có thêm một bản copy có thể stale, expire, mất toàn bộ sau restart hoặc trở thành hotspot mới.

Một design chỉ hỏi “dùng Redis không?” là chưa đủ. Cần trả lời dữ liệu nào được phép stale, khi nào invalidate, cache miss sẽ dồn tải xuống đâu, một popular key expire thì chuyện gì xảy ra, và write path có được phép trả success trước khi durable source được cập nhật hay không.

Cache vì thế là trade-off: **đổi performance lấy consistency + failure complexity**.

## Mental Model

<Principle label="Cache rule">Source of truth quyết định business fact; cache chỉ giữ một fast copy đủ fresh cho use case.</Principle>

## Core Concepts

### Cache-Aside, TTL và invalidation

Cache-Aside để application kiểm tra cache trước, miss mới đọc Database và populate. **TTL** giới hạn lifetime nhưng không đảm bảo Database update sẽ xuất hiện ngay trong cache. Khi freshness quan trọng, write path thường cần explicit invalidate/update; TTL đóng vai safety net.

Với permission revoke, stale 30 phút có thể là security violation. Đây là ví dụ điển hình cho việc TTL không thay thế correctness policy.

### Hot Key là traffic concentration

Hot Key xảy ra khi một key nhận traffic không cân xứng và làm node/partition chứa nó quá tải dù cluster-wide hit rate vẫn rất tốt. Đây là distribution problem, không phải cache-miss problem.

### Cache Stampede là concurrent rebuild

Khi popular entry expire/mất, nhiều requests cùng miss và cùng query/rebuild origin. Root cause là herd behavior. Single-flight/locking, stale-while-revalidate, proactive refresh và TTL jitter là các cách giảm concurrent rebuild tùy semantics.

### Write-through và Write-behind

**Write-through** giữ write success gắn chặt với backing store update, phù hợp hơn khi durable canonical state phải đúng trước response. **Write-behind** defer backing-store update để tối ưu latency/throughput, chỉ phù hợp khi eventual consistency được chấp nhận và pending writes có durability/replay.

### Durability không đồng nghĩa sync Database write

Một durable log/queue có thể persist event trước rồi consumer batch/aggregate vào Database sau. Điều quan trọng là event có thể replay và không mất; freshness là một dimension khác durability.

## Example

### Starting Point

Product API query Database cho mọi request. Database CPU tăng vì nhiều reads cùng một product.

### Requirement Changes

Team thêm Cache-Aside và latency giảm mạnh. Sau đó `product:123` viral, rồi entry expire trong peak traffic.

### Naive Fix

Tăng Database connection pool để chịu cache misses. Khi popular key expire, hàng nghìn requests cùng query origin và Database overload nhanh hơn.

### Root Cause

Hot Key là concentrated traffic; Stampede là simultaneous rebuild sau miss. Tăng origin concurrency không loại bỏ herd behavior.

### Better Design

Giữ Database là source of truth, cache repeated reads, monitor per-key load, coalesce rebuild bằng single-flight hoặc stale-while-revalidate, dùng explicit invalidation cho correctness-critical changes và chọn write strategy theo durability/freshness needs.

### Why It Works

Design tách rõ fast copy khỏi canonical state và xử lý failure theo root cause: hot-key mitigation cho skew, rebuild coordination cho stampede, invalidation cho stale correctness và durable buffering khi write-behind cần không mất data.

## When to Use

Cache phù hợp khi repeated reads hoặc expensive computation tạo bottleneck và một bounded stale policy chấp nhận được. Cache không phải default cho mọi table/query; nếu data access đã nhanh, traffic thấp hoặc freshness tuyệt đối quan trọng, extra cache layer có thể tăng complexity nhiều hơn value.

## Common Mistakes

- Cache = source of truth.
- TTL = consistency guarantee.
- Hot Key = Cache Stampede.
- Tăng DB connection pool để chữa stampede.
- Write-behind = ghi volatile RAM rồi hy vọng flush sau.
- Không capacity-plan cold start/cache loss.

## Decision Guide

1. Dữ liệu nào là canonical source of truth?
2. Stale bao lâu là chấp nhận được theo từng use case?
3. Update cần explicit invalidation hay TTL đủ?
4. Cache loss/cold start tạo origin load bao nhiêu?
5. Key distribution có skew/hot key không?
6. Popular-entry miss có cần single-flight/stale-while-revalidate không?
7. Write path cần durable-before-success hay eventual backing-store update?
8. Metrics nào theo dõi hit rate, eviction, hot key, origin QPS và rebuild latency?

## Practical Takeaway

Hãy thiết kế cache bằng bốn câu hỏi: **copy của cái gì, fresh đến mức nào, miss/rebuild xảy ra thế nào, failure đẩy tải về đâu**. Khi source of truth và freshness contract rõ, Cache-Aside, invalidation, stampede protection và write strategy trở thành các quyết định có lý do thay vì một bộ “best practices” rời rạc.

## Self-test

1. Hot Key và Cache Stampede khác nhau thế nào?
2. Vì sao TTL không đủ cho permission revoke?
3. Single-flight giải quyết root cause của stampede thế nào?
4. Khi nào write-behind hợp hơn write-through?
5. Durable queue giúp write-behind giữ data bằng cách nào?
