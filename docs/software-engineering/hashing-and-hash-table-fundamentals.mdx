# Hashing & Hash Table Fundamentals

## TL;DR

<TLDR>

Hash Table dùng **key để xác định nơi cần tìm** thay vì scan toàn bộ collection. `HashMap` trả lời `key → value`; `HashSet` trả lời membership/uniqueness. Lookup thường gần `O(1)` average khi hash distribution tốt, nhưng collision, resize, memory overhead và ordering requirement vẫn là trade-off thật.

</TLDR>

## Why It Matters

Nhiều bài toán production không cần “search” theo nghĩa ranking; chúng chỉ cần trả lời rất nhanh một câu hỏi exact: user này là ai, request ID này đã xử lý chưa, file path này có cache chưa, node này đã visited chưa.

Nếu mỗi lần đều scan một List, cost tăng theo collection size. Hash Table đổi bài toán từ **“duyệt qua mọi item để tìm key”** thành **“tính vị trí có khả năng chứa key rồi kiểm tra ở đó”**.

Nhưng `O(1)` không phải phép màu. Hiểu hash function, collision và semantics của Map/Set giúp tránh chọn cấu trúc chỉ vì một Big-O đẹp trên giấy.

## Core Concepts

### Hash function

Hash function biến key thành một hash value có kích thước hữu hạn. Hash Table dùng giá trị đó, thường kết hợp với table capacity, để xác định bucket/index.

Một hash function hữu ích cho Hash Table cần hai property thực dụng:

- cùng một key phải cho kết quả ổn định trong phạm vi operation cần dùng;
- key nên được phân bố đủ đều để tránh quá nhiều item dồn vào một số ít bucket.

Hash function dùng cho data structure **không đồng nghĩa cryptographic hash**. HashMap ưu tiên distribution và performance; password hashing/signature integrity có threat model hoàn toàn khác.

Nhiều implementation của Set có thể được xây trên cơ chế tương tự Map, nhưng API khác nhau vì **intent khác nhau**. Nếu code chỉ hỏi `has(key)`, Set diễn đạt domain tốt hơn một Map chứa value giả.

### Collision

Hash space/bucket space hữu hạn, còn tập key có thể rất lớn. Vì vậy hai key khác nhau có thể rơi vào cùng bucket: đó là **collision**.

Collision không có nghĩa value mới tự động overwrite value cũ. Hash Table phải resolve collision bằng strategy của implementation, chẳng hạn chaining hoặc probing, và cuối cùng vẫn so sánh key thật.

Điều cần nhớ: **hash không phải unique identity**.

### Vì sao `O(1)` chỉ là average-case intuition?

Nếu hash distribution tốt và load factor được kiểm soát, bucket cần kiểm tra thường nhỏ, nên lookup/insert/delete có expected cost gần constant time.

Nếu nhiều keys collision hoặc table quá đầy, một bucket/probe sequence có thể dài hơn đáng kể. Worst case lý thuyết có thể degrade tới `O(n)` tùy implementation.

### Capacity, load factor và resize

Hash Table thường giữ extra capacity để collision không tăng quá nhanh. Khi load factor vượt threshold, implementation có thể allocate table lớn hơn và rehash/move entries.

Vì vậy một insert riêng lẻ đôi khi đắt, dù **amortized** cost của nhiều inserts vẫn tốt. Đổi lại, Hash Table thường dùng nhiều memory hơn một compact array/list.

## Example

### Starting Point: Coding Agent scan repository

Một Coding Agent đi qua dependency graph. Ban đầu code giữ `visitedFiles` trong array:

```ts
const visitedFiles: string[] = [];

if (!visitedFiles.includes(path)) {
  visitedFiles.push(path);
  inspect(path);
}
```

Với ít files, cách này đơn giản và hoàn toàn chấp nhận được.

### Requirement Changes: repository lớn và lookup lặp lại

Khi traversal lên hàng chục nghìn nodes, `includes()` scan lại array cho mỗi membership check. Cùng lúc agent cần cache file content theo path.

Hai requirement khác nhau xuất hiện:

- “path này đã visited chưa?” → membership;
- “content của path này là gì?” → key-to-value lookup.

### Better Design

```ts
const visitedFiles = new Set<string>();
const fileCache = new Map<string, string>();

if (!visitedFiles.has(path)) {
  visitedFiles.add(path);

  const content = fileCache.get(path) ?? readFile(path);
  fileCache.set(path, content);

  inspect(content);
}
```

### Why It Works

`Set` và `Map` encode đúng operation mà algorithm lặp lại. Agent không cần scan toàn bộ visited history để hỏi membership, và không cần một parallel array để tìm content tương ứng với path.

Lợi ích không chỉ là Big-O; intent của code cũng rõ hơn: một structure dành cho **membership state**, một structure dành cho **mapping state**.

## When to Use

- Dùng `HashMap` khi operation chính là exact lookup/update theo key.
- Dùng `HashSet` khi operation chính là membership, deduplication hoặc uniqueness.
- Dùng HashSet cho `visited` trong graph traversal khi node có thể được reach nhiều lần.
- Dùng List/Array khi ordering, compact storage hoặc sequential traversal mới là requirement chính.
- Cân nhắc ordered map/tree/sorted structure nếu cần range query hoặc ordered iteration có guarantee rõ ràng.

## Common Mistakes

- **Nghĩ hash là unique ID:** collision là property bình thường cần được implementation xử lý.
- **Nghĩ Hash Table luôn `O(1)`:** đó là average/expected behavior dưới assumptions phù hợp.
- **Dùng HashMap khi chỉ cần membership:** Set diễn đạt intent trực tiếp hơn.
- **Dùng Hash Table khi cần range query:** hashing phá locality/order nên không tự nhiên cho “mọi key từ A đến B”.
- **Dựa vào iteration order ngoài contract của language/runtime:** một số implementation giữ insertion order, một số không; phải theo guarantee cụ thể.
- **Nhầm non-cryptographic hashing với security hashing:** cùng chữ “hash” nhưng mục tiêu và threat model khác nhau.

## Decision Guide

Hỏi các câu sau trước khi chọn Hash Table:

1. **Operation chính có phải exact lookup/membership không?** Nếu có, Map/Set là candidate mạnh.
2. **Có cần value đi cùng key không?** Có → Map; không → Set.
3. **Có cần sorted/range traversal không?** Nếu có, tree/sorted structure có thể phù hợp hơn.
4. **Memory overhead có đáng kể không?** Với dataset cực lớn, extra capacity/object overhead có thể quan trọng.
5. **Key có hash/equality semantics ổn định không?** Mutable key hoặc equality sai có thể làm lookup khó hiểu.
6. **Workload có adversarial/untrusted keys không?** Implementation/runtime strategy có thể ảnh hưởng resilience trước collision patterns xấu.

## Practical Takeaway

<Principle label="Review heuristic">Chọn data structure từ operation lặp lại nhiều nhất: `get by key`, `contains`, `iterate in order`, hay `range query`.</Principle>

Hash Table là default mạnh cho exact lookup, nhưng không phải “data structure nhanh nhất”. Nó mua lookup average-case tốt bằng hashing, extra capacity và việc từ bỏ một số ordering/range properties.

## Self-test

1. Khi nào nên dùng HashSet thay vì HashMap?
2. Collision là gì và vì sao hash không phải unique ID?
3. Vì sao Hash Table được mô tả là `O(1) average` chứ không phải guarantee tuyệt đối?
4. Vì sao Hash Table không tự nhiên cho range query?
5. Coding Agent cần `filePath → fileContent`; cấu trúc nào phù hợp?

<details>
<summary>Answers</summary>

1. Khi chỉ cần membership/uniqueness, không cần value đi kèm.
2. Collision xảy ra khi hai key khác nhau rơi vào cùng bucket; implementation vẫn phải phân biệt key thật.
3. Distribution tốt giữ bucket/probe ngắn, nhưng collision/load xấu có thể làm lookup phải kiểm tra nhiều entries hơn.
4. Hashing phân tán keys theo hash thay vì giữ thứ tự key, nên các key liên tiếp về giá trị không nhất thiết nằm gần nhau.
5. HashMap/Map vì requirement là mapping từ key sang value.

</details>
