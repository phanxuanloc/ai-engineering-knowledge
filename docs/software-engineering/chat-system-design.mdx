# Chat System Design

## TL;DR

<TLDR>
Chat System có ít nhất ba loại state khác nhau: live WebSocket connection, distributed connection-routing state và durable message history. WebSocket chỉ giải quyết realtime transport; message phải sống qua disconnect cần Message Store, còn nhiều connection servers cần registry/router để tìm đúng recipient connection.
</TLDR>

## Why It Matters

Một chat prototype có thể giữ WebSocket và messages trong cùng process. Khi scale lên nhiều instances, assumptions đó vỡ rất nhanh: sender nối vào Server 3 nhưng recipient đang ở Server 17; process restart làm mất connection map; mobile client disconnect vài phút nhưng vẫn phải nhận messages bị lỡ.

Nếu design đồng nhất “message được gửi qua socket” với “message đã được lưu”, “recipient đã nhận” hoặc “recipient đã đọc”, trạng thái sản phẩm sẽ sớm mơ hồ. Chat cần tách **durability**, **routing** và **live transport** thành các trách nhiệm riêng.

## Mental Model

Một message có hai paths liên quan nhưng khác mục tiêu:

- **Durable path:** accept → persist → history/unread state.
- **Live path:** locate recipient connection → route → push qua WebSocket.

<Principle label="State separation">Connection location là ephemeral distributed state; message history là durable business state.</Principle>

## Core Concepts

### WebSocket là transport, không phải storage

WebSocket phù hợp cho bidirectional low-latency communication nhưng connection có thể mất khi mobile network đổi, process restart hoặc user offline. Message cần đọc lại không thể chỉ sống trong connection process.

### Connection routing là distributed ephemeral state

Nếu User A và User B nằm trên hai connection servers khác nhau, sender server cần shared registry/router để biết recipient đang ở đâu. Mapping phải expire/reconcile khi connection churn; stale mapping là normal failure mode cần xử lý.

### Message Store giữ durable history

Persist message tách “hệ thống đã chấp nhận message” khỏi “recipient đang online”. Offline user vẫn có unread/history path, còn live delivery failure không đồng nghĩa business message bị mất.

### Delivery state không nên bị đồng nhất

`persisted`, `delivered to connection` và `read` là ba transitions khác nhau với evidence khác nhau. Server write thành công vào socket không chứng minh user đã đọc.

### Ordering nên có scope nhỏ nhất cần thiết

Global total order thường đắt và không cần thiết. Per-conversation ordering thường đủ cho chat semantics và cho phép các conversations khác xử lý song song. `conversation_id` thường là natural partition/ordering scope.

### Reconnect là synchronization path

Reconnect không chỉ mở socket mới. Client cần cursor/last-seen token để fetch missed history, dedupe nếu live stream overlap và sau đó resume realtime updates.

## Example

### Starting Point

Một single-node chat app giữ connection map và messages trong memory.

### Requirement Changes

Service scale horizontal, mobile clients disconnect thường xuyên và users cần history/unread state.

### Naive Fix

Thêm nhiều WebSocket servers sau Load Balancer nhưng mỗi server chỉ biết local connections. Message từ Server 3 không biết User B đang ở Server 17; restart làm mất local history.

### Root Cause

Live connection state, routing state và durable message state có lifecycle và guarantee khác nhau nhưng đang bị trộn trong một process.

### Better Design

Persist message vào Message Store, externalize connection registry, route live message tới instance giữ recipient và dùng reconnect cursor để sync missed history. Scope ordering theo conversation thay vì toàn hệ thống.

### Why It Works

Durability không phụ thuộc socket lifecycle, routing hoạt động qua nhiều instances và reconnect trở thành deterministic data-sync path thay vì “hy vọng client không bỏ lỡ event”.

## When to Use

Dùng WebSocket khi cần bidirectional realtime communication; externalize routing khi có nhiều connection servers; persist trước/độc lập với live delivery khi offline messages không được mất; dùng per-conversation ordering khi business semantics cho phép.

Một system nhỏ có thể bắt đầu single-node. Đừng thêm distributed registry trước khi có nhu cầu scale/failover thật, nhưng cũng đừng coi in-memory connection map là durable architecture.

## Common Mistakes

- Coi WebSocket là Message Store.
- Giữ connection location chỉ trong local RAM khi đã có nhiều servers.
- Đồng nhất delivered với read.
- Yêu cầu global ordering không cần thiết.
- Bỏ qua stale registry/connection churn.
- Reconnect mà không sync missed history.

## Decision Guide

1. Message phải survive disconnect/process restart không?
2. Ordering cần global, per conversation hay weaker?
3. Recipient connection được locate qua bao nhiêu instances/regions?
4. Registry freshness/TTL và stale-route recovery thế nào?
5. `persisted`, `delivered`, `read` được chứng minh bằng event nào?
6. Reconnect cursor/deduplication hoạt động ra sao?
7. Presence có cần strong correctness hay chỉ best-effort?

## Practical Takeaway

Chat scale tốt khi bạn tách đúng state ownership: **WebSocket vận chuyển**, **registry định tuyến**, **Message Store giữ history**, còn conversation scope định nghĩa ordering cần thiết. Khi các boundary đó rõ, offline delivery, reconnect và horizontal scaling trở thành những paths có thể reasoning riêng thay vì một khối “realtime” mơ hồ.

## Self-test

1. WebSocket, connection registry và Message Store có trách nhiệm khác nhau thế nào?
2. Vì sao local connection map không đủ khi có nhiều servers?
3. Persisted, delivered và read khác nhau ở evidence nào?
4. Vì sao per-conversation ordering thường phù hợp hơn global ordering?
5. Reconnect cần làm gì ngoài mở lại WebSocket?

<details><summary>Answers</summary>
1. WebSocket vận chuyển realtime; registry tìm live route; Message Store giữ durable history. 2. Sender server không biết recipient nằm trên instance khác và local state không hỗ trợ failover. 3. Persisted là durable accept; delivered là tới live connection; read cần acknowledgment/user action riêng. 4. Nó bảo vệ invariant có ý nghĩa với coordination scope nhỏ hơn. 5. Fetch missed history từ cursor rồi hợp nhất với live stream.
</details>
