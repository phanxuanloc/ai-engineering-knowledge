# Chat System Design

## TL;DR

<TLDR>

Chat System có ít nhất ba loại state khác nhau: live WebSocket connection, distributed routing/presence state và durable message history. WebSocket chỉ giải quyết realtime transport; message phải sống qua disconnect cần Message Store, còn nhiều connection servers cần registry/router để tìm đúng recipient connection.

</TLDR>

## Mental Model

Một message không chỉ “đi qua WebSocket”. Nó đi qua hai trách nhiệm song song:

- **Durable path:** accept → persist message → expose history/unread state.
- **Live delivery path:** locate recipient connection → route tới đúng server → push qua WebSocket.

<Principle label="State separation">Connection location là ephemeral distributed state; message history là durable business state.</Principle>

## Core Concepts

### WebSocket là delivery channel

WebSocket giữ long-lived bidirectional connection, phù hợp với realtime message exchange và tránh polling liên tục. Nhưng connection có thể mất khi mobile network đổi, process restart hoặc user offline. Vì vậy WebSocket không thể là nơi duy nhất giữ message cần đọc lại.

### Connection routing là distributed state

Nếu User A nối vào Server 3 còn User B nối vào Server 17, Server 3 không thể tìm B chỉ bằng local memory. Một shared connection registry/router cần biểu diễn user/session đang thuộc connection server nào để message được forward tới đúng nơi.

Registry state có lifecycle ngắn hơn message: connect đăng ký, disconnect/timeout loại bỏ hoặc expire mapping. Stale mapping có thể route nhầm tới connection đã chết, nên routing path phải chấp nhận connection churn thay vì coi registry như durable truth vĩnh viễn.

### Message Store giữ history qua disconnect

Message cần được persist để recipient offline có thể nhận unread messages và reconnect có thể đồng bộ history. Durable storage cũng tách “message đã được hệ thống chấp nhận” khỏi “recipient đang online và đã nhận live push”. Live delivery thất bại không nhất thiết làm mất message nếu durable path đã thành công.

### Delivery state không nên bị đồng nhất

Các trạng thái `accepted/persisted`, `delivered to a live connection` và `read by user` diễn tả ba sự kiện khác nhau. Không nên suy ra “read” chỉ vì server đã ghi socket, hoặc suy ra “not stored” chỉ vì recipient offline. Design message status cần gắn mỗi transition với evidence thực sự mà hệ thống có.

### Ordering nên có scope nhỏ nhất cần thiết

Global message ordering đòi coordination rộng và thường không cần thiết. Chat thường cần order trong từng conversation. Dùng `conversation_id` như ordering/partition key giúp message cùng conversation đi qua một ordered path, trong khi các conversation khác có thể xử lý độc lập.

Điều này không tự giải quyết mọi reconnect/duplicate case, nhưng nó xác định rõ invariant thay vì yêu cầu toàn hệ thống có một total order đắt đỏ.

### Reconnect là một data synchronization path

Sau disconnect, client không nên giả định live stream liên tục. Nó cần một cursor/last-seen boundary để hỏi durable store những message bị lỡ, rồi hợp nhất với live delivery. Do đó reconnect không chỉ là mở lại socket; nó còn là khôi phục state từ durable history.

## Example

User A gửi message cho User B:

1. A đang nối vào Connection Server 3.
2. Message được accept và persist với `conversation_id`.
3. Registry cho biết B đang nối vào Server 17.
4. Server 3/router forward message tới Server 17, rồi Server 17 push qua WebSocket.
5. Nếu B offline hoặc connection mapping stale, live push thất bại nhưng durable message vẫn tồn tại.
6. Khi B reconnect, client đồng bộ phần history sau last-seen boundary.

Design này tách rõ durability khỏi low-latency delivery và không buộc một failed socket write phải làm mất business message.

## When to Use

- Dùng WebSocket khi cần bidirectional realtime communication.
- Externalize connection routing khi có nhiều connection servers hoặc cần failover.
- Persist message trước/độc lập với live delivery khi offline recipient không được mất message.
- Scope ordering theo conversation/entity thay vì global khi business requirement cho phép.
- Thiết kế reconnect như history synchronization, không chỉ socket re-establishment.

## Common Mistakes

- **Coi WebSocket là Message Store:** disconnect hoặc restart làm mất state chỉ nằm trong connection process.
- **Giữ connection location chỉ trong local RAM:** server gửi không biết recipient đang ở instance nào.
- **Đồng nhất delivered với read:** socket delivery không chứng minh user đã xem message.
- **Yêu cầu global order:** tăng coordination cost dù chỉ per-conversation order mới có ý nghĩa.
- **Bỏ qua stale registry:** connection churn làm routing state lỗi thời.
- **Reconnect mà không sync history:** message trong khoảng offline có thể bị bỏ lỡ.

## Self-test

1. WebSocket, connection registry và Message Store có trách nhiệm khác nhau thế nào?
2. Vì sao local connection map không đủ khi có nhiều servers?
3. Persisted, delivered và read khác nhau ở evidence nào?
4. Vì sao per-conversation ordering thường phù hợp hơn global ordering?
5. Reconnect cần làm gì ngoài mở lại WebSocket?

<details>
<summary>Answers</summary>

1. WebSocket vận chuyển realtime; registry tìm server giữ live connection; Message Store giữ history qua disconnect.
2. Sender server không biết recipient connection nằm trên instance khác và local state không hỗ trợ failover/global routing.
3. Persisted là durable accept; delivered là tới live connection; read cần acknowledgement/user action riêng.
4. Nó bảo vệ invariant có ý nghĩa trong chat với coordination scope nhỏ hơn và cho phép conversation khác xử lý độc lập.
5. Dùng last-seen/cursor boundary để lấy message bị lỡ từ durable history rồi hợp nhất với live stream mới.
