# Process, Thread & Concurrency

## TL;DR

<TLDR>

**Process** là resource/isolation boundary; **thread** là execution path bên trong process. **Concurrency** nghĩa là nhiều task cùng có progress trong một khoảng thời gian; **parallelism** nghĩa là nhiều task thực sự execute cùng lúc. Bug xuất hiện khi nhiều execution cùng chạm vào **shared mutable state** mà business invariant không được bảo vệ bằng một atomicity boundary phù hợp.

</TLDR>

## Why It Matters

Production systems gần như luôn có concurrency: nhiều HTTP requests, worker jobs, scheduled tasks hoặc agent tool calls cùng chạy. Nếu chỉ nghĩ “mỗi request có code đúng” mà không nghĩ “hai request có thể interleave ra sao”, hệ thống vẫn có thể oversell inventory, withdraw quá balance, claim cùng job hai lần hoặc ghi đè update của nhau.

Điểm quan trọng không phải học thuộc process/thread. Điểm quan trọng là xác định đúng **execution boundary**, **shared state boundary** và **logical operation nào phải giữ nguyên tính atomic**.

## Mental Model

<Principle label="Mental rule">
Shared state quyết định nơi concurrency trở nên nguy hiểm; correctness phụ thuộc vào atomicity boundary chứ không phụ thuộc số dòng source code.
</Principle>

Một **process** giống một workspace được OS cấp riêng về address space và resources. Bên trong workspace đó có thể có nhiều **threads** cùng làm việc. Threads có execution state riêng nhưng cùng nhìn thấy nhiều process resources, đặc biệt là heap.

## Core Concepts

### Process là isolation boundary

Một process là chương trình đang chạy cùng execution environment của nó: virtual address space, heap, open files/sockets và một hoặc nhiều threads. Hai process thường không đọc/ghi trực tiếp memory của nhau; muốn trao đổi phải qua IPC, socket, shared memory hoặc external state như database.

Isolation giúp giới hạn blast radius: crash hoặc memory corruption trong process A không mặc định cho phép A sửa arbitrary memory của process B. Tuy nhiên process isolation không có nghĩa mỗi process sở hữu physical RAM riêng; virtual memory mới là abstraction tạo cảm giác address space riêng.

### Thread là execution path

Thread là một dòng execution bên trong process. Mỗi thread thường có stack/register state riêng nhưng có thể truy cập cùng heap và process resources. Shared access làm communication rẻ hơn process-to-process communication, nhưng đồng thời mở ra race condition nếu nhiều threads cùng sửa mutable state.

### Concurrency khác parallelism

Một CPU core vẫn tạo concurrency bằng cách scheduler chuyển qua lại giữa nhiều runnable tasks. Parallelism chỉ xuất hiện khi nhiều work thực sự execute cùng lúc trên nhiều cores hoặc compute units.

Vì vậy `100 threads` không có nghĩa `100 tasks chạy parallel`. Trên machine 8 cores, CPU-heavy work vẫn bị compute capacity giới hạn.

### Race condition là bug của interleaving

Race condition xảy ra khi kết quả phụ thuộc timing/interleaving giữa concurrent executions. Source code `counter++` nhìn như một operation nhưng conceptually có thể là `read → modify → write`.

Điều cần bảo vệ thường là **business invariant**, ví dụ `check balance → decide → update balance`. Nếu hai requests cùng đi qua logical unit này trên shared state, correctness có thể bị phá dù từng request riêng lẻ đều đúng.

### Shared-state boundary quyết định coordination boundary

Concurrency control chỉ hiệu lực nếu mọi competing execution cùng tham gia nó. Nếu hai service instances cùng sửa một database row, mutex local trong instance A không khóa instance B. Khi state nằm ở database, atomic update, transaction, compare-and-set hoặc distributed coordination mới có thể là boundary đúng.

## Example

### Starting Point

Một payment service có `balance = 100`. Với một request duy nhất, code này có vẻ hợp lý:

```ts
if (balance >= amount) {
  balance = balance - amount;
}
```

### Requirement Changes

Bây giờ hai requests cùng withdraw `80`.

### Root Cause

Sai không nằm ở phép trừ. Sai nằm ở việc **check + update không atomic trên shared state**. Hai requests có thể interleave giữa check và write.

### Better Design

Nếu balance nằm trong PostgreSQL và service có nhiều instances, process-local mutex không đủ. Có thể dùng transaction với row locking, atomic conditional update hoặc optimistic concurrency control tùy contention và semantics.

Ví dụ ý tưởng atomic conditional update:

```sql
UPDATE accounts
SET balance = balance - 80
WHERE id = $1
  AND balance >= 80;
```

Success/failure của một shared-state operation được quyết định tại database boundary thay vì ở một snapshot cũ trong application memory.

### Why It Works

Competing requests không còn tự check rồi tự write độc lập. Invariant `balance >= 0` được kiểm tra cùng nơi state được thay đổi, nên atomicity boundary khớp shared-state boundary.

## When to Use

- Debug lost update, duplicate claim, oversell inventory hoặc check-then-act bug.
- Quyết định state có thể an toàn read/write từ nhiều threads/processes không.
- Phân biệt lợi ích của concurrency với parallel CPU execution.
- Thiết kế worker/service có nhiều execution paths cùng truy cập shared mutable state.

## Common Mistakes

- **`Thread = process nhẹ hơn` rồi bỏ qua shared state:** distinction quan trọng hơn là isolation boundary vs execution path.
- **`Concurrency = parallelism`:** concurrent tasks có thể chỉ đang interleave trên ít cores.
- **`Một dòng code = atomic`:** source syntax không nói operation có thể bị chia nhỏ thế nào.
- **`Thêm mutex local là đủ`:** lock chỉ bảo vệ executions cùng tham gia coordination mechanism đó.
- **`Hai requests concurrent là lỗi`:** concurrency tự nó không sai; invariant không được bảo vệ mới là vấn đề.

## Decision Guide

Khi thấy concurrency concern, hỏi theo thứ tự:

1. **State nào đang shared?** Heap object, file, database row, queue message hay external resource?
2. **Invariant nào phải giữ?** Không oversell, balance không âm, job chỉ claim một lần?
3. **Ai cạnh tranh với ai?** Threads cùng process, processes khác nhau hay service instances khác nhau?
4. **Atomicity boundary nằm ở đâu?** Local lock, database transaction, atomic operation hay distributed coordination?
5. **Có thật sự cần mutable shared state không?** Nếu có thể partition/serialize ownership thì đôi khi bỏ shared mutation đơn giản hơn locking.

## Practical Takeaway

Khi review concurrent code, đừng bắt đầu từ số threads. Hãy vẽ ra `execution A`, `execution B`, `shared state` và logical operation cần giữ invariant. Nếu hai executions có thể đi qua cùng invariant mà không gặp chung một atomicity boundary, hệ thống đang có race risk.

## Self-test

1. Process và thread khác nhau ở boundary nào?
2. Vì sao concurrency không yêu cầu nhiều CPU cores?
3. `counter++` có thể race theo sequence nào?
4. Vì sao mutex trong một service instance không bảo vệ database row trước instance khác?

<details>
<summary>Answers</summary>

1. Process là resource/isolation boundary; thread là execution path bên trong process.
2. Scheduler có thể interleave nhiều tasks trên một core để chúng cùng progress.
3. `read → modify → write` của hai executions có thể interleave và tạo lost update.
4. Vì mỗi process có lock riêng; database row là shared state nằm ngoài process-local synchronization boundary.

</details>
