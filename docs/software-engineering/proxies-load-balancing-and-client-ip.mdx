# Proxies, Load Balancing & Client IP

## TL;DR

<TLDR>

Production traffic thường đi qua intermediaries thay vì tới backend trực tiếp. **Forward proxy** đại diện phía client; **reverse proxy** đại diện phía server; **load balancing** phân phối traffic giữa backends. Khi có proxy/LB, backend thường nhìn thấy **direct network peer** là intermediary, nên original client identity phải được truyền qua một trusted boundary thay vì suy ra mù quáng từ socket source IP hoặc header do Internet gửi lên.

</TLDR>

## Why It Matters

Proxy và load balancer giải quyết scale, availability, TLS termination, routing và topology hiding, nhưng đồng thời tạo ra một consequence quan trọng: **network path mà backend nhìn thấy không còn giống logical request path mà user nghĩ tới**.

Nếu không hiểu boundary này, team dễ:

- log sai client IP;
- rate-limit nhầm tất cả user theo IP của load balancer;
- trust `X-Forwarded-For` do attacker tự gửi;
- debug instance unhealthy từ phía client dù client không hề biết instance nào xử lý request;
- nhầm reverse proxy với load balancing như hai loại product loại trừ nhau.

## Mental Model

Đừng học theo tên vendor. Hãy tách responsibility:

- **Forward proxy:** đứng phía client, thay client đi ra ngoài.
- **Reverse proxy:** đứng phía server, nhận request trước backend.
- **Load balancer:** chọn một backend hoặc một nhóm backends để xử lý traffic.
- **Health checking:** quyết định backend nào còn đủ điều kiện nhận traffic.
- **Client identity propagation:** truyền original-client metadata qua trusted intermediary chain.

<Principle label="Boundary rule">Một component có thể giữ nhiều responsibility. Hãy hỏi “nó đang đại diện cho phía nào và quyết định điều gì?” thay vì chỉ hỏi “đây là Nginx, ALB hay API Gateway?”.</Principle>

## Core Concepts

### Forward proxy và reverse proxy khác nhau ở phía được đại diện

<Comparison items={[
  {title: 'Forward proxy', description: 'Đứng phía client; destination server thấy proxy là network peer.'},
  {title: 'Reverse proxy', description: 'Đứng phía server; client chỉ thấy public/server-facing endpoint.'},
]} />

Một corporate outbound proxy là forward proxy điển hình. Một ingress/reverse proxy đứng trước app instances là reverse proxy.

### Load balancing là routing responsibility

Load balancer nhận traffic ở một entry point rồi chọn backend dựa trên strategy và health state. Nó có thể dùng round-robin, least-connections, hashing hoặc policy khác; fundamental quan trọng hơn algorithm là **client không cần biết backend topology**.

### Health check biến topology thành runtime state

Backend không chỉ “có trong config” hoặc “không có”. Nó còn có trạng thái runtime: healthy, unhealthy, draining, warming up… Load balancer phải route dựa trên state hợp lệ thay vì chỉ danh sách static.

### Direct peer khác original client

Flow:

```text
Client 14.1.2.9 → Load Balancer 10.0.1.5 → Backend 10.0.2.10
```

Backend socket có thể thấy peer là `10.0.1.5`. Original client `14.1.2.9` chỉ còn là metadata nếu intermediary truyền tiếp.

### Forwarded headers nằm trong trust boundary

Headers như `Forwarded` hoặc `X-Forwarded-For` có thể mang client IP, nhưng Internet client cũng có thể tự gửi header cùng tên. Vì vậy backend chỉ nên trust giá trị được **trusted proxy append/normalize** theo cấu hình rõ ràng.

Nếu trust chain sai, attacker có thể spoof IP dùng cho audit, access control hoặc rate limiting.

### Pain Appears: backend log chỉ thấy load balancer IP

Team dùng source IP ở socket để rate-limit user. Sau khi thêm LB, mọi request trông như tới từ `10.0.1.5`, khiến hàng nghìn user bị gom thành một identity.

Naive fix là trust bất kỳ `X-Forwarded-For` nào backend nhận được. Cách này mở spoofing risk.

### Root Cause

Transport peer và original client là hai identity khác nhau. Load balancer trở thành peer trực tiếp; original client chỉ có thể được bảo tồn dưới dạng metadata qua trusted intermediary chain.

### Better Design

1. Edge/load balancer xóa hoặc normalize header không đáng tin từ Internet.
2. Edge ghi/append original client information theo policy chuẩn.
3. Backend chỉ trust forwarded headers khi request tới từ known trusted proxy range.
4. Rate limiting/audit sử dụng normalized client identity, không dùng raw user-controlled header.
5. Health-aware routing loại backend unhealthy khỏi active pool.

### Why It Works

Thiết kế tách rõ **network peer**, **logical client identity** và **backend availability**. Mỗi concern có owner: transport xác định peer, trusted proxy xác nhận/propagate identity, load balancer quản lý routing candidates.

## When to Use

- Scale backend horizontally.
- Cần một public entry point cho nhiều instances/services.
- Terminate TLS hoặc centralize routing ở edge.
- Debug backend log thấy IP proxy/LB thay vì client.
- Thiết kế health checks, draining và failover.
- Xây rate limit/audit dựa trên client identity phía sau trusted proxies.

## Common Mistakes

- **Reverse proxy = load balancer:** một component có thể làm cả hai, nhưng hai responsibility khác nhau.
- **Backend luôn thấy original client IP:** proxy/LB thường là network peer trực tiếp.
- **Tin mọi `X-Forwarded-For`:** user có thể tự gửi header nếu edge không normalize.
- **Health check pass = business endpoint chắc chắn tốt:** check quá nông có thể bỏ sót dependency failure; check quá sâu có thể làm hệ thống flap.
- **Client phải retry sang instance khác:** trong kiến trúc có LB, backend selection thường là trách nhiệm của intermediary.
- **Dùng client IP làm identity tuyệt đối:** NAT, mobile networks và shared proxies có thể khiến nhiều user dùng chung IP.

## Decision Guide

Khi thiết kế intermediary layer, hỏi:

1. **Component đang đại diện cho client hay server?** → forward vs reverse proxy responsibility.
2. **Có nhiều backend candidates không?** → cần load-balancing decision.
3. **Backend health thay đổi runtime không?** → health checks/draining phải ảnh hưởng routing.
4. **Backend cần original client IP để làm gì?** → observability, rate limit hay security policy có mức trust khác nhau.
5. **Ai được phép ghi forwarded headers?** → chỉ trusted edge/proxy chain.
6. **Có đang dùng IP như user identity không?** → xem lại vì NAT/shared networks có thể phá assumption.

## Practical Takeaway

<Principle label="Trust rule">Chỉ trust original-client metadata sau khi xác định trusted proxy chain và cách edge normalize header. Raw header từ Internet không phải identity.</Principle>

Trong architecture review, vẽ riêng ba thứ: **public entry point**, **routing candidates + health state**, và **client identity propagation**. Nếu chúng bị gộp thành một mũi tên “client → backend”, nhiều production assumption quan trọng đang bị che mất.

## Self-test

1. Forward proxy và reverse proxy khác nhau ở phía nào được đại diện?
2. Vì sao backend sau LB có thể thấy IP của LB thay vì client?
3. Tại sao không nên trust `X-Forwarded-For` từ mọi request?
4. Một backend fail health check nên ảnh hưởng routing thế nào?

<details>
<summary>Answers</summary>

1. Forward proxy đại diện client; reverse proxy đại diện server/backend side.
2. Vì connection trực tiếp tới backend được tạo từ LB/proxy, nên đó là network peer.
3. Vì Internet client có thể tự spoof header; chỉ trusted proxy chain mới nên xác nhận/normalize nó.
4. Backend unhealthy phải bị loại khỏi active routing candidates cho tới khi đủ điều kiện trở lại.

</details>
