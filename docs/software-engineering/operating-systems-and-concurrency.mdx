# Operating Systems & Concurrency

## TL;DR

<TLDR>

Operating Systems & Concurrency giải thích **execution chạy ở đâu, chia sẻ resource thế nào, chờ cái gì và vì sao correctness/performance có thể hỏng khi nhiều work cùng tồn tại**. Mental map hiện tại gồm năm phần đã học: process/thread & race condition, synchronization & deadlock, async I/O, memory management và CPU scheduling.

</TLDR>

<Principle label="Mental map">
Shared state → correctness. Waiting → async/concurrency. Compute → CPU parallelism. Memory → capacity. Scheduler → ai thực sự nhận CPU time.
</Principle>

## Core Concepts

### 1. Process, Thread & Concurrency

[Process, Thread & Concurrency](./process-thread-and-concurrency.mdx) xây foundation: process vs thread, concurrency vs parallelism, shared mutable state, interleaving và race condition. Đây là bài cần đọc trước các concurrency mechanics khác.

### 2. Synchronization & Deadlocks

[Synchronization & Deadlocks](./synchronization-and-deadlocks.mdx) giải thích critical section, mutex, lock contention, deadlock và consistent lock ordering. Trọng tâm là bảo vệ đúng invariant mà không serialize quá nhiều unrelated work.

### 3. Async I/O & Event Loop

[Async I/O & Event Loop](./async-io-and-event-loop.mdx) phân biệt blocking với non-blocking waiting, event loop, `async/await`, thread pool và bounded concurrency. Mental rule chính: I/O-bound tối ưu waiting; CPU-bound tối ưu compute.

### 4. Memory Management

[Memory Management](./memory-management.mdx) phân biệt stack, heap, virtual memory, memory leak, stack overflow và OOM. Phần này đặc biệt hữu ích khi debug container memory limit, GC baseline growth và peak memory pressure.

### 5. CPU Scheduling & Context Switching

[CPU Scheduling & Context Switching](./cpu-scheduling-and-context-switching.mdx) giải thích runnable vs running, scheduler, context-switch cost và vì sao tăng CPU-bound workers quá mức có thể làm latency tệ hơn.

## Example

Một AI service có thể chứa cả năm vấn đề cùng lúc:

```text
Agent process
│
├── many concurrent requests
│   ├── shared state → race/synchronization concern
│   └── LLM/DB waits → async I/O concern
│
├── per-request working set → memory pressure
│
└── CPU-heavy preprocessing
    └── worker sizing / scheduling concern
```

Một production diagnosis tốt không bắt đầu từ “thêm thread hay thêm CPU?”, mà bắt đầu từ câu hỏi **work đang chờ gì, state nằm ở đâu và resource nào đang saturated**.

## When to Use

- Debug API/worker latency khi chưa rõ đang CPU-bound, I/O-bound hay lock-bound.
- Debug race condition, lost update hoặc deadlock trong concurrent code.
- Thiết kế AI Agent fan-out tool calls và bounded concurrency.
- Điều tra OOM, memory leak, stack overflow hoặc high peak working set.
- Sizing worker pools cho CPU-heavy preprocessing hoặc background jobs.

## Common Mistakes

- **Dùng một concurrency model cho mọi workload:** CPU-bound và I/O-bound cần strategy khác nhau.
- **Thấy race là thêm lock ngay:** cần tìm shared invariant và synchronization boundary trước.
- **Thấy OOM là kết luận leak:** peak concurrency cũng có thể vượt memory limit.
- **Thấy CPU thấp là kết luận khỏe:** system có thể đang chờ lock/I/O/downstream.
- **Đánh đồng checkpoint với broad-topic completion:** phần IPC và synchronization primitives chuyên sâu chưa được capture trong learning path này.
