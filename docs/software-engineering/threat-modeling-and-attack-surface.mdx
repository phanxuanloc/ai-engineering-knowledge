# Threat Modeling & Attack Surface

## TL;DR

<TLDR>

Threat Modeling là cách nhìn architecture như một tập **assets, trust boundaries và attack paths** trước khi incident xảy ra. Mục tiêu không phải đoán hết mọi kiểu tấn công, mà là tìm những đường có thể nối **Untrusted Input → Privileged Capability → Valuable Asset**, đánh giá risk và đặt controls để phá đường đó hoặc giảm blast radius.

Attack Surface là phần system mà attacker hoặc untrusted input có thể chạm tới. Threat model tốt biến một danh sách “có thể bị hack” thành câu hỏi engineering cụ thể: **đường nào đáng lo nhất, boundary nào đang trao thêm privilege, và control nào phải enforce invariant?**

</TLDR>

## Why It Matters

Một hệ thống có thể có authentication, firewall, encryption và nhiều security tools nhưng vẫn nguy hiểm nếu architecture tạo ra một đường đi từ input không đáng tin cậy tới capability có quyền cao.

Ví dụ một Coding Agent đọc issue từ public repository rồi có quyền chạy shell, đọc secrets và push vào `main`. Không thành phần nào riêng lẻ nhất thiết “sai”, nhưng khi ghép lại chúng tạo thành một **privilege bridge**: dữ liệu do attacker kiểm soát có thể ảnh hưởng đến hành động mà attacker bình thường không có quyền thực hiện.

Threat Modeling giúp chuyển security từ checklist sang reasoning về architecture:

- thứ gì có giá trị cần bảo vệ;
- interaction bắt đầu ở đâu;
- trust hoặc privilege thay đổi ở đâu;
- attacker cần đi qua những bước nào để tạo impact;
- control nào thực sự cắt được attack path.

## Mental Model

Hãy nghĩ threat model như việc vẽ **đường đi tới impact**. Một attack chỉ đáng ưu tiên khi attacker có thể đi từ entry point, qua các boundary/capability cần thiết, tới asset hoặc consequence quan trọng.

## Core Concepts

### Asset: thứ có giá trị cần bảo vệ

Asset không chỉ là data. Một asset có thể là:

- customer data hoặc confidential source code;
- tiền hoặc quyền thực hiện refund/payment;
- production deployment capability;
- availability của service;
- model/system integrity;
- reputation hoặc regulatory obligations.

Threat model bắt đầu từ asset vì cùng một weakness có risk rất khác tùy thứ nó có thể ảnh hưởng.

### Attack Surface: nơi untrusted interaction có thể bắt đầu

Attack Surface là tổng các điểm mà attacker hoặc untrusted input có thể tương tác với system: public APIs, uploaded files, webhooks, browser inputs, external documents, repository issues, network services hoặc third-party integrations.

Thêm feature thường cũng thêm attack surface. Một integration mới không chỉ là “thêm capability”; nó còn thêm một đường để external input đi vào system.

Entry point trả lời **“attacker đi vào từ đâu?”**; asset trả lời **“nếu attack thành công thì điều gì đáng kể bị ảnh hưởng?”**.

### Trust Boundary và Privilege Boundary

**Trust Boundary** xuất hiện khi data hoặc control đi từ vùng có assumptions khác sang vùng khác, ví dụ Internet → backend hoặc external document → agent context.

**Privilege Boundary** xuất hiện khi một component có capability mà nguồn input không có. Đây thường là nơi attack path trở nên nguy hiểm.

Ví dụ public user chỉ có thể tạo issue, nhưng Coding Agent có thể đọc repository secret và push code. Agent đang đứng giữa hai mức privilege rất khác nhau.

### Threat, Vulnerability và Risk

Ba khái niệm này liên quan nhưng không đồng nghĩa:

- **Threat:** điều xấu có thể xảy ra — attacker khiến agent deploy malicious code.
- **Vulnerability:** weakness khiến threat khả thi — agent được phép deploy mà không có approval gate.
- **Risk:** mức độ đáng ưu tiên trong context thực tế — kết hợp impact, likelihood/exploitability và exposure.

Danh sách vulnerability dài không tự động là threat model tốt. Engineering decision cần biết weakness nào thật sự nối được tới impact lớn.

### Control phải phá attack path hoặc giảm impact

Control có giá trị khi nó thay đổi attack path thực tế. Một control có thể:

- chặn input trước boundary;
- validate/sanitize data;
- giảm privilege;
- require approval;
- enforce policy ở privileged API;
- isolate component;
- giới hạn lifetime/capability;
- detect và stop misuse sớm.

Security không nhất thiết yêu cầu threat biến mất hoàn toàn. Nếu một bước quan trọng trong path bị chặn hoặc blast radius bị giảm mạnh, risk có thể giảm đáng kể.

## Example

Giả sử một Support Agent có ba capability:

1. nhận `Customer Message` từ Internet;
2. đọc order data;
3. gọi `Refund API`.

### Starting Point — feature trông hợp lý

Agent cần đọc nội dung customer gửi để hiểu vấn đề và tạo refund khi phù hợp. Nếu chỉ nhìn từng component riêng lẻ, architecture có vẻ bình thường:

`Customer Message → Support Agent → Refund API`

### Requirement Changes — agent được trao nhiều authority hơn

Ban đầu agent chỉ draft đề xuất. Sau đó team cho phép agent tự gọi `Refund API` để giảm thời gian xử lý support ticket.

Thay đổi này không chỉ cải thiện automation. Nó tạo một đường mới:

`Attacker-controlled message → Agent reasoning → Privileged refund capability → Money`

### Root Cause — untrusted input đang influence privileged action

Vấn đề cốt lõi không phải “LLM có thể bị prompt injection” theo nghĩa chung chung. Root cause ở architecture là **untrusted input có thể ảnh hưởng trực tiếp tới một component được trao financial authority**.

Nếu toàn bộ quyết định “được refund bao nhiêu” chỉ nằm trong model reasoning, security invariant đang phụ thuộc vào một boundary không đáng tin cậy để enforce policy.

### Better Design — đặt invariant ở privileged boundary

Giả sử business rule cho phép agent tự refund tối đa `$100`. `Refund API` phải enforce rule đó độc lập với model:

```ts
async function refund(input: RefundRequest, actor: Actor) {
  if (actor.type === 'support-agent' && input.amount > 100) {
    throw new ForbiddenError('Agent refund limit exceeded');
  }

  return paymentProvider.refund(input);
}
```

Với refund lớn hơn, system có thể yêu cầu human approval hoặc workflow khác.

### Why It Works — attack path bị giới hạn tại đúng capability boundary

Prompt injection vẫn có thể khiến agent muốn refund `$10,000`, nhưng model không còn là nơi cuối cùng quyết định financial authority.

Attack path thay đổi từ:

`Untrusted Message → Agent → Unlimited Refund`

thành:

`Untrusted Message → Agent → Refund API policy → max $100 / approval required`

Threat chưa biến mất, nhưng control đã giới hạn **capability** và vì thế giảm **blast radius**.

<Principle label="Security invariant ownership">Rule bảo vệ asset nên được enforce ở boundary sở hữu privileged capability, không chỉ ở component đang reasoning trước boundary đó.</Principle>

## When to Use

Threat Modeling đặc biệt hữu ích khi:

- expose endpoint, webhook, file upload hoặc integration mới;
- một service/agent nối untrusted input với database, shell, CI/CD, cloud API hoặc financial action;
- thêm privilege mới cho automation;
- review architecture trước launch;
- một system có nhiều trust zones hoặc third-party dependencies;
- sau incident và cần tìm boundary/control đã thiếu thay vì chỉ patch symptom.

Không cần biến mọi feature nhỏ thành một workshop dài. Với change nhỏ, một lightweight threat-model pass vẫn có thể đủ: **asset → entry point → boundary → attack path → control**.

## Common Mistakes

- **Bắt đầu bằng danh sách CVE/vulnerability:** threat model nên bắt đầu từ architecture, assets và attack paths.
- **Threat = vulnerability:** threat là điều có thể xảy ra; vulnerability là weakness khiến nó khả thi.
- **Attack Surface = mọi code trong system:** attack surface là phần attacker/untrusted input có thể tương tác hoặc influence.
- **Tin rằng authentication đã giải quyết authorization:** user đã authenticated vẫn có thể không được phép thực hiện một privileged action.
- **Đặt mọi security decision trong LLM/application logic:** invariant quan trọng phải được enforce tại boundary sở hữu capability.
- **Cố loại bỏ mọi threat:** security engineering thường là ưu tiên risk và giảm blast radius, không phải đạt trạng thái “không còn threat”.
- **Vẽ attack path nhưng không xác định asset/impact:** nếu không biết impact cuối cùng, rất khó ưu tiên control.

## Decision Guide

Khi review một architecture, đi theo chuỗi câu hỏi này:

1. **Asset nào đáng bảo vệ nhất?** Data, money, production, availability hay privileged capability?
2. **Untrusted interaction bắt đầu ở đâu?** Public API, user content, file, webhook, third party hay model output?
3. **Trust/privilege thay đổi ở đâu?** Component nào có quyền cao hơn nguồn input?
4. **Attacker cần nối những bước nào để tạo impact?** Hãy mô tả attack path cụ thể.
5. **Control nào cắt path gần privileged boundary nhất?** Validation, policy enforcement, least privilege, approval, isolation hay revocation?
6. **Nếu control fail, blast radius còn bao nhiêu?** Defense-in-depth tốt làm failure của một control không đồng nghĩa full compromise.

Ưu tiên những path có **impact cao + exposure thực tế + ít boundary kiểm soát** trước những hypothetical weakness không nối được tới asset quan trọng.

## Practical Takeaway

Một threat model có thể bắt đầu rất nhỏ:

`Asset → Entry Point → Trust/Privilege Boundary → Attack Path → Control → Residual Risk`

Khi thiết kế hoặc review feature, hãy cố trả lời được sáu phần này bằng architecture cụ thể. Nếu một component nhận untrusted input nhưng lại sở hữu privileged capability, đó là tín hiệu mạnh để xem lại least privilege, policy enforcement và approval boundary.

Điểm quan trọng nhất: **security control nên thay đổi capability hoặc path mà attacker có thể đi, không chỉ làm architecture trông “có security”.**
