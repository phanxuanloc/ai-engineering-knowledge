# URL Shortener System Design

## TL;DR

<TLDR>
URL Shortener là bài toán **write mapping ít, read redirect rất nhiều**. Design nên tách create path khỏi redirect path, giữ mapping bền vững trong Database, đặt cache trên dominant read path và kiểm tra hot-key skew thay vì chỉ tính aggregate capacity.
</TLDR>

## Why It Matters

Một URL Shortener nhìn rất đơn giản: nhận long URL, trả short URL, rồi redirect. Nhưng khi traffic tăng, hai operation có workload hoàn toàn khác nhau. Create có thể chỉ vài nghìn writes/s trong khi redirect đạt hàng trăm nghìn reads/s, và một link viral có thể chiếm phần lớn traffic.

Nếu design coi cả hai như cùng một path, team dễ scale nhầm chỗ: tối ưu create logic trong khi bottleneck thật nằm ở redirect lookup, hoặc tăng Database capacity dù cache hit rate cao nhưng một cache shard đang bị hot key.

Bài toán này là ví dụ tốt cho nguyên tắc: **tách access path trước, rồi tối ưu path chịu pressure lớn nhất**.

## Mental Model

`long URL → unique ID → compact key → durable mapping`

Redirect path:

`short key → cache lookup → durable mapping khi miss → HTTP redirect`

<Principle label="Primary design pressure">Tối ưu dominant read path, nhưng không để fast path trở thành source of truth.</Principle>

## Core Concepts

### Create path và redirect path

Create path validate URL, cấp short key và ghi mapping bền vững. Redirect path lookup key với latency thấp rồi trả redirect response. Hai path nên capacity-plan độc lập vì read/write ratio có thể lệch vài bậc độ lớn.

### Key generation và collision boundary

Một hướng phổ biến là cấp unique identifier rồi encode bằng Base62. **ID generation** giải quyết uniqueness; **Base62** chỉ rút gọn representation. Nếu dùng random key, hash prefix hay cơ chế khác, design vẫn phải chỉ rõ collision được detect/retry ở đâu.

### Cache là fast copy

Cache giữ `short_key → original_url` cho repeated reads. Cache hit tránh Database; miss đọc source of truth rồi repopulate. Nếu mapping mutable, TTL/invalidation phải giới hạn stale window. Nếu mapping immutable, policy đơn giản hơn nhưng eviction và cold start vẫn còn.

### Hot key là vấn đề distribution

Một viral URL có thể chiếm 30–50% redirect traffic. Aggregate cluster capacity vẫn dư nhưng node/shard chứa key đó quá tải. Vì vậy review phải nhìn per-key/per-shard load, không chỉ tổng QPS và hit rate.

### Redirect status là product decision

`301` có thể khuyến khích caching mạnh hơn, giảm traffic quay lại service nhưng giảm control/visibility. `302` thường giữ request quay qua service nhiều hơn, hữu ích khi destination mutable hoặc analytics cần quan sát redirect. Chọn status từ semantics, không từ thói quen.

## Example

### Starting Point

Một service đơn giản ghi `short_key → long_url` vào Database và mọi redirect đều query Database.

### Requirement Changes

Traffic redirect tăng 100 lần, còn create traffic gần như giữ nguyên. Một số URL viral tạo skew rất lớn.

### Naive Fix

Scale Database theo tổng QPS. Cách này tốn kém và vẫn không giải quyết việc nhiều reads giống hệt nhau.

### Root Cause

Dominant path là repeated point lookup. Phần lớn request không cần một fresh Database read nếu mapping không đổi.

### Better Design

Redirect Service stateless đặt cache trước Database, repopulate khi miss và monitor key distribution. Create path vẫn persist mapping vào source of truth; key generation có explicit uniqueness/collision boundary.

### Why It Works

Repeated reads rời khỏi Database, service instances scale độc lập, còn durable mapping không phụ thuộc cache lifecycle. Hot-key monitoring giữ design trung thực với skew thay vì giả định traffic phân phối đều.

## When to Use

Dùng cache khi redirect read-heavy và mapping được đọc lặp lại; scale stateless Redirect Service khi request processing là bottleneck; đánh giá hot-key mitigation khi traffic skew cao; chọn redirect status từ caching, analytics và mutability requirements.

Một implementation nhỏ có traffic thấp có thể dùng Database trực tiếp trước. Cache không miễn phí: nó thêm invalidation, operational dependency và failure mode.

## Common Mistakes

- Thiết kế theo average URL và bỏ qua viral key.
- Dùng cache như durable store.
- Không chỉ rõ collision handling.
- Scale service nhưng giữ mapping state local.
- Chọn `301/302` theo thói quen thay vì product semantics.

## Decision Guide

1. Create QPS và redirect QPS lệch nhau bao nhiêu?
2. Mapping mutable hay immutable?
3. Key được cấp unique ở đâu, collision được xử lý ở đâu?
4. P50/P99 redirect latency target là gì?
5. Key distribution có skew lớn không?
6. Cache loss sẽ tăng backend load tới mức nào?
7. Browser/intermediary caching có làm mất analytics/control cần thiết không?

## Practical Takeaway

URL Shortener không cần một architecture đặc biệt bí ẩn. Hãy tách **write once** khỏi **read many**, giữ durable mapping ngoài process, dùng cache cho repeated lookup và capacity-plan theo distribution thực tế. Đây là pattern lặp lại ở nhiều read-heavy systems: tối ưu access path, không biến optimization layer thành source of truth.

## Self-test

1. Vì sao create path và redirect path nên được capacity-plan riêng?
2. Unique ID và Base62 encoding giải quyết hai việc khác nhau thế nào?
3. Cache miss và cache loss ảnh hưởng hệ thống khác nhau ra sao?
4. Vì sao aggregate cache capacity không chứng minh hệ thống chịu được viral URL?
5. Yêu cầu nào có thể làm lựa chọn giữa `301` và `302` thay đổi?

<details>
<summary>Answers</summary>

1. Chúng có traffic ratio, latency sensitivity và operation khác nhau.
2. ID cấp uniqueness; Base62 chỉ biểu diễn ID ngắn hơn.
3. Miss làm một request đọc Database; cache loss tạo nhiều miss nhưng mapping vẫn còn trong durable store.
4. Một key có thể tập trung traffic vào một shard/node.
5. Caching, analytics visibility, destination mutability và mức control muốn giữ tại service.

</details>
