# CPU Scheduling & Context Switching

## TL;DR
<TLDR>OS scheduler quyết định runnable thread nào nhận CPU time trên cores hữu hạn. **Context switch** có overhead và có thể giảm cache locality. Với CPU-bound work, tăng runnable workers vượt compute capacity có thể tăng latency mà throughput gần như không tăng.</TLDR>

<Principle label="Mental rule">CPU-bound parallelism bị giới hạn bởi compute capacity. Sau một điểm, thêm workers chủ yếu thêm scheduling overhead.</Principle>

## Core Concepts

### Scheduler
Machine có số cores hữu hạn nhưng có thể có nhiều runnable threads. Scheduler chọn subset nào chạy tại từng thời điểm; `100 threads` không có nghĩa `100 tasks` đang parallel.

### Context switching
Switching giữa executions cần save/restore state và có indirect cost như cache/TLB locality giảm. Context switches là normal; vấn đề là excessive runnable work làm system dành quá nhiều effort để rotate workers.

### CPU-bound worker sizing
Một starting mental model là bounded parallelism gần available compute capacity rồi đo throughput/latency. 8–16 workers có thể phù hợp hơn 128 workers trên machine 8 cores tùy runtime/workload.

### I/O-bound khác CPU-bound
I/O-bound tasks có thể có concurrency cao hơn số cores vì phần lớn thời gian đang chờ network/database/disk. Đây là lý do async I/O và CPU worker pools cần strategy khác nhau.

### Worker pool là capacity boundary
Bounded pool giới hạn số tasks cạnh tranh CPU; queue phía trước hấp thụ demand thay vì biến mọi pending task thành runnable worker.

## Example
Document parsing service trên 8 cores có 128 workers, CPU 98%, run queue/context switches rất cao, throughput gần ngang 16 workers nhưng latency tăng mạnh. Root cause phù hợp là excessive runnable CPU-bound workers. Trong cùng AI service, CPU-heavy preprocessing nên dùng bounded parallel workers, còn LLM/Vector DB/GitHub calls nên dùng async I/O + bounded concurrency.

## When to Use
- CPU gần saturation nhưng throughput không tăng khi thêm workers.
- Run queue/context switches tăng mạnh.
- Sizing CPU worker pools.
- Phân biệt CPU saturation với waiting problem.

## Common Mistakes
- **CPU cao → thêm threads:** có thể làm scheduler overhead tệ hơn.
- **CPU thấp → service khỏe:** threads có thể đang blocked/waiting.
- **N threads = N parallel tasks:** hardware/runtime giới hạn parallelism.
- **Dùng cùng strategy cho CPU-bound và I/O-bound:** bottleneck khác nhau.

3. CPU thấp nhưng latency cao gợi ý loại waiting nào?

<details><summary>Answers</summary>
1. Runnable là sẵn sàng; running là đang execute trên CPU.
2. Run queue, context switching và cache disruption tăng mà compute capacity không tăng.
3. I/O wait, lock contention, downstream latency hoặc blocked workers.
</details>
