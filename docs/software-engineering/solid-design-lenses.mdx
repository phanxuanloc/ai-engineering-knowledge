# SOLID as Design Lenses

## TL;DR

<TLDR>

SOLID là năm lens để phát hiện design làm thay đổi lan rộng: responsibility lẫn lộn, extension phải sửa core logic, implementation phá contract, interface ép capability giả, hoặc business logic phụ thuộc infrastructure detail. Đây là công cụ reasoning, không phải luật phải áp dụng cơ học.

</TLDR>

## Mental Model

Khi requirements đổi, dùng từng lens để hỏi “điểm nào sẽ phải sửa, và vì sao?” thay vì đếm interface hoặc design pattern.

<Principle label="Overall model">SOLID giúp giảm change impact và tăng maintainability; nhiều abstraction hơn không tự động có nghĩa design tốt hơn.</Principle>

## Core Concepts

- **SRP — Single Responsibility Principle:** một module không nên sở hữu các reasons to change không liên quan.
- **OCP — Open/Closed Principle:** recurring behavior dimension nên có extension point để thêm implementation mà không liên tục sửa core orchestration.
- **LSP — Liskov Substitution Principle:** implementation thay thế phải giữ behavioral promise của abstraction, không chỉ khớp method signature.
- **ISP — Interface Segregation Principle:** contract chỉ nên expose capability mà implementation thật sự support; không ép method vô nghĩa hoặc `throw unsupported`.
- **DIP — Dependency Inversion Principle:** high-level business logic phụ thuộc vào contract phù hợp thay vì concrete infrastructure detail.

## Example

Với notification có SendGrid, Twilio, Firebase và sau này có thể thêm provider:

```ts
interface NotificationSender {
  send(message: Notification): Promise<void>;
}

class NotificationService {
  constructor(private readonly sender: NotificationSender) {}

  notify(message: Notification) {
    return this.sender.send(message);
  }
}
```

Mỗi provider implement `NotificationSender`; core service không cần một chuỗi `if/else` theo vendor. Dùng Factory/Resolver chỉ khi implementation phải được chọn tại runtime. Nếu composition root đã biết sender cần dùng, Dependency Injection trực tiếp đơn giản hơn.

## When to Use

- Review module có nhiều reasons to change hoặc direct infrastructure dependency.
- Một behavior dimension thường xuyên thêm implementation mới.
- Implementation khớp type nhưng làm caller phải special-case behavior.
- Interface ép implementation support capability không có thật.
- Chọn giữa direct Dependency Injection và Factory/Resolver theo nhu cầu runtime selection.

## Common Mistakes

- **Memorize definition nhưng không nối với change impact:** SOLID mất practical value.
- **Factory ở mọi nơi:** Factory giải quyết runtime selection, không phải nghi thức bắt buộc của DI.
- **OCP cho mọi thay đổi giả định:** extension point chưa có recurring variability có thể là premature abstraction.
- **LSP chỉ kiểm tra compile:** behavioral promise vẫn có thể bị phá dù signature giống nhau.
- **Interface quá rộng:** implementation phải no-op hoặc throw cho capability không support.

## Self-test

1. SOLID nên được dùng như mental model nào?
2. LSP kiểm tra điều gì ngoài method signature?
3. Vì sao interface buộc implementation `throw unsupported` là ISP smell?
4. Khi nào cần Factory thay vì inject implementation trực tiếp?

<details>
<summary>Answers</summary>

1. Năm lens để giảm change impact và cải thiện maintainability.
2. Implementation có giữ behavioral promise mà caller dựa vào hay không.
3. Contract expose capability implementation không thể thực sự support.
4. Khi implementation phải được chọn dựa trên runtime input hoặc policy; nếu đã biết ở composition root, inject trực tiếp thường đủ.

</details>
