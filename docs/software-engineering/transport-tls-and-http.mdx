# Transport, TLS & HTTP

## TL;DR

<TLDR>

Một “API call” thực tế đi qua nhiều boundary: **transport → secure channel → HTTP semantics → application behavior**. TCP reliability không đảm bảo business exactly-once; TLS bảo vệ connection chứ không bảo vệ toàn bộ application; và một HTTP status như `401` cho biết request đã đi xa hơn rất nhiều so với một TCP timeout.

</TLDR>

## Why It Matters

Khi mọi lỗi đều bị gọi chung là “API fail”, team dễ retry sai, debug sai layer hoặc kết luận sai về security. `connection timeout`, `TLS handshake error`, `HTTP 401`, `HTTP 500` và “payment bị charge hai lần” là năm loại failure có boundary khác nhau.

Muốn debug nhanh và thiết kế retry an toàn, cần biết **layer nào đã thành công, layer nào chưa xảy ra, và guarantee của layer dưới không tự động nâng cấp thành guarantee của business operation**.

## Mental Model

Hãy tách một HTTPS request thành bốn câu hỏi:

1. **Transport:** hai endpoint có trao đổi byte/datagram được không?
2. **TLS:** secure authenticated channel có thiết lập được không?
3. **HTTP:** request/response semantics có được trao đổi không?
4. **Application:** operation có thành công, idempotent và authorized không?

<Principle label="Boundary rule">Mỗi signal chỉ chứng minh layer của nó. TCP success không chứng minh TLS/HTTP success; HTTP response không chứng minh business operation đúng; transport reliability không tạo business exactly-once.</Principle>

## Core Concepts

### TCP và UDP cung cấp transport semantics khác nhau

<Comparison items={[
  {title: 'TCP', description: 'Connection-oriented reliable ordered byte stream; có retransmission và flow/congestion control.'},
  {title: 'UDP', description: 'Datagram transport; không tự cung cấp cùng guarantee về delivery, ordering hay connection state.'},
]} />

HTTP/1.1 và HTTP/2 thường chạy trên TCP. HTTP/3 dùng QUIC trên UDP nhưng QUIC tự cung cấp nhiều transport guarantee ở user space. Điều này cho thấy **HTTP không đồng nghĩa TCP**.

### TCP reliability chỉ bảo vệ transport delivery

TCP cố gắng giao byte stream đáng tin cậy giữa hai endpoints. Nó không biết “charge payment” là một business operation.

Nếu server đã charge thành công nhưng connection đứt trước khi client nhận response, client không biết operation đã commit hay chưa. Retry có thể tạo charge thứ hai. Đây là lý do idempotency key tồn tại ở application layer.

### TLS tạo secure channel, không tạo secure application

TLS cung cấp ba property chính:

- confidentiality của data in transit;
- integrity của dữ liệu trên channel;
- peer authentication, phổ biến nhất là server authentication qua certificate.

TLS không sửa authorization sai, SQL injection, secret bị log, insecure business logic hay compromised endpoint.

### HTTP định nghĩa application protocol semantics

Request thường có method, path, query, headers và optional body. Response có status, headers và body.

Một HTTP status là signal rất mạnh về failure boundary:

- `401`/`403`: request đã tới HTTP/application boundary đủ xa để server trả policy result;
- `500`: server/application xử lý request và fail phía trong;
- connection timeout: có thể chưa có HTTP exchange nào;
- TLS handshake error: transport có thể đã nối nhưng secure channel chưa sẵn sàng.

### HTTP stateless không có nghĩa application không có state

HTTP request tự nó không giữ conversation state giữa các request. Identity/session được bổ sung bằng mechanisms như cookie, server-side session hoặc bearer token.

Cookie là storage/transmission mechanism của browser; session là application state của phiên; token là credential/claim representation. Chúng không phải cùng một khái niệm.

## Example

### Starting Point: payment API hoạt động bình thường

Client gửi:

```http
POST /payments
Idempotency-Key: pay_123
Authorization: Bearer ...
```

Server charge thành công và trả `201 Created`.

### Requirement Changes: response bị mất

Lần sau server charge thành công nhưng connection bị reset trước khi response tới client. Client chỉ thấy network error và retry cùng operation.

Naive implementation tạo một charge mới cho mỗi request sẽ duplicate payment. Nói “nhưng TCP reliable” không giải quyết được ambiguity này: TCP không biết business transaction đã commit.

### Root Cause

Failure xảy ra **sau side effect nhưng trước observation của client**. Client không thể phân biệt “server chưa xử lý” với “server xử lý xong nhưng response thất lạc” chỉ từ network error.

### Better Design

Client reuse cùng `Idempotency-Key` cho cùng logical operation. Server lưu result/operation identity và khi nhận retry cùng key, nó trả lại kết quả cũ thay vì tạo side effect mới.

### Why It Works

Idempotency được đặt đúng boundary nơi business identity tồn tại. Transport layer không cần biết “payment”; application layer mới có đủ context để nhận ra hai network requests thực ra là một logical operation.

## When to Use

- Debug connection timeout, TLS/certificate issue hoặc HTTP error.
- Thiết kế retry cho operation có side effect.
- Phân biệt transport guarantee với business guarantee.
- Review auth/session/cookie/token behavior ở HTTP layer.
- Điều tra vì sao browser/client có HTTP status nhưng team vẫn đang kiểm tra firewall.

## Common Mistakes

- **HTTP = TCP:** HTTP/3 là phản ví dụ rõ ràng.
- **TCP reliable = business exactly-once:** transport không biết logical operation identity.
- **HTTPS = application secure:** TLS chỉ bảo vệ channel trong scope của nó.
- **401 = network problem:** đã có HTTP response thì authentication/authorization thường đáng ưu tiên hơn routing.
- **Retry mọi network error bằng request mới:** side effect có thể đã commit trước khi response bị mất.
- **Cookie = session:** cookie có thể chỉ mang session ID; session state có thể nằm server-side.

## Decision Guide

Khi một HTTPS call fail, hỏi:

1. **Có connect tới destination port không?** Không → network/transport.
2. **TLS handshake hoàn tất không?** Không → certificate, protocol, SNI, trust chain hoặc TLS config.
3. **Có HTTP status không?** Có → network path và protocol stack đã đi đủ xa; đọc status/headers/body.
4. **Operation có side effect không?** Có → retry phải xét idempotency.
5. **Client có biết operation đã commit chưa?** Nếu ambiguous → dùng operation identity/idempotency thay vì đoán từ connection state.
6. **Security requirement thuộc channel hay application?** Encryption/authentication của peer ≠ authorization/business security.

## Practical Takeaway

<Principle label="Retry rule">Retry policy phải dựa trên semantics của operation, không chỉ dựa trên loại network error.</Principle>

Trong incident, map error vào boundary trước: `connect → TLS → HTTP → application`. Trong design review, map guarantee vào đúng layer: `transport delivery`, `channel security`, `protocol semantics`, `business idempotency`.

## Self-test

1. Nhận `401` chứng minh những layer nào đã hoạt động đủ xa?
2. Vì sao server charge thành công nhưng client timeout vẫn có thể dẫn tới double charge?
3. TLS bảo vệ điều gì và không bảo vệ điều gì?
4. HTTP stateless khác gì với “application không có session state”?

<details>
<summary>Answers</summary>

1. Network/transport và HTTP exchange đã đi đủ xa để server trả response; ưu tiên auth/application investigation.
2. Side effect có thể commit trước khi response bị mất; retry là một request mới nếu application không nhận diện cùng logical operation.
3. TLS bảo vệ confidentiality/integrity và peer authentication trên channel; không tự sửa authorization, injection hay business logic.
4. HTTP request không tự giữ state giữa calls, nhưng application vẫn có thể quản lý session qua cookie/token/server-side state.

</details>
