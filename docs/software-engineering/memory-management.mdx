# Memory Management

## TL;DR

<TLDR>
Thread execution thường có **stack** riêng cho call state; process data/objects thường nằm trong **heap** và có thể được nhiều threads truy cập. **Memory leak** là retained memory không còn hữu ích nhưng vẫn reachable; **OOM** là failure khi không cấp được memory cần thiết và không đồng nghĩa leak.
</TLDR>

## Why It Matters

Khi service bị OOM, nhiều team lập tức kết luận “memory leak”. Nhưng cùng một symptom có thể đến từ leak, traffic spike, oversized cache, quá nhiều concurrent requests, quá nhiều threads, large payload hoặc container limit quá thấp.

Debug memory hiệu quả cần phân biệt **memory nào đang tăng, vì sao nó còn sống, và peak working set có vượt capacity không**. Nếu không tách các failure modes này, bạn dễ tối ưu nhầm chỗ.

## Mental Model

<Principle label="Mental rule">
Memory tăng không tự chứng minh leak. Phân biệt stack exhaustion, retained baseline growth và peak working-set pressure.
</Principle>

## Core Concepts

### Stack và call frames

Function calls tạo frames theo LIFO. Recursion không dừng hoặc call chain quá sâu có thể vượt per-thread stack limit và gây **stack overflow** dù machine còn nhiều RAM.

### Heap và object lifetime

Heap chứa data có lifetime linh hoạt hơn call stack. Threads trong cùng process thường có thể truy cập cùng heap; mutable shared objects vì vậy vừa là memory concern vừa là concurrency concern.

### Garbage collection không loại bỏ mọi leak

GC chỉ reclaim objects không còn reachable theo runtime's reachability model. Nếu global cache, listener registry hoặc static collection vẫn giữ reference, object có thể không còn hữu ích cho business nhưng vẫn “alive” với GC.

### OOM là failure state, không phải diagnosis

OOM nghĩa là process/runtime không cấp được memory cần thiết. Leak là một nguyên nhân; peak load là nguyên nhân khác.

Ví dụ `10 MB/request × 500 concurrent requests ≈ 5 GB` working set có thể vượt container 2 GB dù mọi allocation cuối cùng đều được release. Không có leak vẫn có thể OOM.

### Virtual memory là address-space abstraction

OS + MMU map virtual pages tới physical frames. Hai processes có thể dùng cùng numeric virtual address nhưng map tới physical memory khác nhau. Đây là foundation cho process isolation và flexible memory mapping.

Swap/backing storage có thể hỗ trợ memory management nhưng không biến disk thành RAM tương đương. Heavy paging có thể gây thrashing vì page faults và storage latency.

### Baseline, peak và fragmentation là các signal khác nhau

- **Baseline sau GC tăng đều** → nghi retained objects/leak.
- **Peak tăng theo concurrency rồi hạ** → nghi working-set/capacity pressure.
- **RSS cao hơn live heap đáng kể** → có thể liên quan native memory, allocator fragmentation, stacks, mmap hoặc runtime overhead.

Không nên dùng một metric duy nhất để kết luận.

## Example

### Starting Point

Java service có container limit `2 GB`. Bình thường heap sau GC ổn định quanh `300 MB`.

### Requirement Changes

Traffic tăng nhưng request shape không đổi. Sau vài giờ, heap after-GC tăng dần `300 MB → 900 MB → 1.8 GB` dù traffic đã trở lại bình thường.

### Naive Diagnosis

“RAM tăng nên tăng container lên 4 GB.” Cách này chỉ kéo dài thời gian trước failure nếu retained baseline vẫn tiếp tục tăng.

### Root Cause

Heap dump cho thấy global `Map` giữ hàng triệu entries của completed jobs. Objects không còn hữu ích nhưng vẫn reachable, nên GC không reclaim.

### Better Design

Bound cache bằng size/TTL hoặc remove lifecycle-owned entries khi job complete. Sau fix, kiểm tra **post-GC baseline** có trở về vùng ổn định không.

### Why It Works

Fix không “ép GC chạy mạnh hơn”; nó sửa object lifetime ownership để obsolete objects trở nên unreachable. Khi reachability đúng, GC mới có thể reclaim.

Ngược lại, nếu memory chỉ spike theo `concurrency × per-request working set` rồi giảm, hướng xử lý hợp lý hơn có thể là bounded concurrency, streaming, smaller buffers hoặc capacity sizing.

## When to Use

- Process/container bị OOM.
- Heap baseline sau GC tăng dần.
- Recursion/deep call chain gây stack overflow.
- Sizing concurrency theo per-request memory.
- Phân biệt heap pressure với native/RSS pressure.

## Common Mistakes

- **GC language không leak:** retained references vẫn giữ memory.
- **OOM = leak:** peak workload cũng có thể vượt capacity.
- **Stack overflow = hết machine RAM:** stack có limit riêng.
- **Virtual memory = RAM + disk:** cốt lõi là address-space abstraction/mapping.
- **RSS = live heap:** process memory còn stacks, native allocations, mapped files và runtime overhead.

## Decision Guide

Khi memory tăng, đi theo signal:

1. **Stack overflow?** → xem recursion/call depth và per-thread stack.
2. **Heap after-GC baseline tăng đều?** → inspect retention path, caches, listeners, collections.
3. **Memory tăng cùng traffic rồi giảm?** → tính `concurrency × working set` trước khi gọi là leak.
4. **Heap ổn nhưng RSS cao?** → kiểm tra native memory, thread stacks, mmap, allocator/runtime behavior.
5. **Container bị kill?** → phân biệt runtime OOM với cgroup/container memory limit.

## Practical Takeaway

Đừng hỏi “memory có tăng không?”; hãy hỏi “**memory nào**, **baseline hay peak**, **object còn reachable vì đâu**, và **capacity limit nào bị vượt**?”. Bốn câu này thường rút ngắn đáng kể đường debug OOM.

## Self-test

1. Stack overflow khác OOM thế nào?
2. Vì sao GC không reclaim object trong unbounded global cache?
3. OOM do traffic spike có đủ chứng minh leak không?
4. Virtual memory giúp process isolation thế nào?

<details>
<summary>Answers</summary>

1. Stack overflow là một stack vượt limit; OOM là không cấp được memory cần thiết.
2. Cache vẫn giữ references nên objects còn reachable.
3. Không; peak concurrency × working set có thể vượt limit.
4. Mỗi process có virtual address space và mappings riêng.

</details>
