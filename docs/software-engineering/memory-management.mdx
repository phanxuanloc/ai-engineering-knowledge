# Memory Management

## TL;DR
<TLDR>Thread execution thường có **stack** riêng cho call state; process data/objects thường nằm trong **heap** và có thể được nhiều threads truy cập. **Memory leak** là retained memory không còn hữu ích nhưng vẫn reachable; **OOM** là failure khi không cấp được memory cần thiết và không đồng nghĩa leak.</TLDR>

<Principle label="Mental rule">Memory tăng không tự chứng minh leak. Phân biệt stack exhaustion, retained baseline growth và peak working-set pressure.</Principle>

## Core Concepts

### Stack và call frames
Function calls tạo frames theo LIFO. Recursion không dừng có thể vượt per-thread stack limit và gây **stack overflow** dù machine còn RAM.

### Heap và shared process data
Heap chứa data có lifetime linh hoạt hơn call stack. Threads trong cùng process thường có thể truy cập cùng heap; mutable shared objects vì vậy cũng là concurrency concern.

### OOM và peak memory pressure
OOM là failure state, không phải diagnosis. Leak, unbounded cache, large object, traffic spike, excessive concurrency, too many threads hoặc container limit thấp đều có thể dẫn tới OOM. Ví dụ `10 MB/request × 500 concurrent requests ≈ 5 GB` working set có thể vượt container 2 GB dù memory cuối cùng được release.

### Virtual memory, paging và swap
OS + MMU map virtual pages tới physical frames. Hai processes có thể dùng cùng numeric virtual address nhưng map tới memory khác nhau. Swap/backing storage có thể hỗ trợ memory management, nhưng storage chậm hơn RAM; heavy page-in/page-out có thể gây thrashing.

## Example
Một Java service có baseline sau GC tăng đều từ 300 MB lên 1.8 GB trong khi traffic ổn định; heap dump cho thấy global `Map` giữ hàng triệu obsolete objects. Đây là strong signal của retained-reference leak. Ngược lại, memory chỉ spike cùng traffic/concurrency cần được điều tra như capacity problem trước.

## When to Use
- Process/container bị OOM.
- Heap baseline sau GC tăng dần.
- Recursion/deep call chain gây stack overflow.
- Sizing concurrency theo per-request memory.

## Common Mistakes
- **GC language không leak:** retained references vẫn giữ memory.
- **OOM = leak:** peak workload cũng có thể vượt capacity.
- **Stack overflow = hết machine RAM:** stack có limit riêng.
- **Virtual memory = RAM + disk:** cốt lõi là address-space abstraction/mapping.

## Self-test
1. Stack overflow khác OOM thế nào?
2. Vì sao GC không reclaim object trong unbounded global cache?
3. OOM do traffic spike có đủ chứng minh leak không?
4. Virtual memory giúp process isolation thế nào?

<details><summary>Answers</summary>
1. Stack overflow là một stack vượt limit; OOM là không cấp được memory cần thiết.
2. Cache vẫn giữ references nên objects còn reachable.
3. Không; peak concurrency × working set có thể vượt limit.
4. Mỗi process có virtual address space và mappings riêng.
</details>
