# Distributed Rate Limiter System Design

## TL;DR

<TLDR>
Distributed Rate Limiter phải trả lời ba câu hỏi: quota tính theo **identity nào**, trong **time model nào**, và nhiều server cùng consume allowance ra sao. Shared state tạo global view, nhưng chỉ atomic allowance decision mới bảo vệ quota dưới concurrency.
</TLDR>

## Why It Matters

Rate limiting thường được mô tả như “đếm request rồi trả 429 khi quá số lượng”. Trong một process, mental model đó tạm đủ. Khi traffic đi qua nhiều API instances, nó nhanh chóng sai.

Nếu 10 instances mỗi máy giữ local counter `100 req/min/user`, một user có thể tiêu thụ gần `1,000 req/min` khi Load Balancer phân phối request. Chuyển counter sang Redis cũng chưa đủ nếu logic vẫn là `GET count → if count < limit → SET count+1`, vì nhiều instances có thể cùng đọc cùng một giá trị trước khi update.

Vấn đề cốt lõi không phải “đếm nhanh”, mà là **nhiều decision makers phải cùng enforce một invariant có scope toàn cục**.

## Mental Model

`request identity → policy → atomic allowance decision → allow / reject`

<Principle label="Correctness boundary">Global limit cần global coordination; local counters chỉ enforce local limits.</Principle>

## Core Concepts

### Policy cần scope rõ ràng

Một policy tối thiểu cần **identity**, **allowance**, **time model** và **action khi hết allowance**. `100 requests/minute` chưa đủ nếu không biết đó là per user, per tenant, per API key hay per IP.

### Enforcement nên ở trước resource đắt

Limiter gần API Gateway/edge có thể reject request trước khi nó lấy Database connection, gọi paid model API hoặc tiêu thụ downstream quota. Nhưng vị trí sớm không cứu được một policy dùng identity sai.

### Local state và global invariant

Local counters rẻ và nhanh nhưng chỉ phù hợp nếu limit thực sự local hoặc approximate. Khi product hứa quota toàn cục, state/coordination phải có scope tương ứng.

### Shared state vẫn cần atomicity

Counter đang `99/100`. Hai servers cùng đọc 99, cùng allow rồi cùng increment. Final value có thể là 100 hoặc 101 tùy mechanism, nhưng business invariant đã bị vi phạm vì cả hai request đều đi qua. Check và consume allowance phải là một atomic decision hoặc primitive tương đương.

### Algorithm định nghĩa burst semantics

**Fixed Window** đơn giản nhưng có thể cho burst ở ranh giới hai window. **Token Bucket** tách `bucket capacity` khỏi `refill rate`: capacity quyết định burst ngắn hạn, refill quyết định sustained rate. Chọn algorithm từ product semantics, không từ độ phổ biến.

### Availability và quota correctness có thể xung đột

Nếu coordination store unavailable, **fail-open** giữ availability nhưng có thể vượt quota; **fail-closed** bảo vệ quota nhưng từ chối traffic hợp lệ. Login protection, inference API đắt tiền và low-risk read endpoint có thể cần policy khác nhau.

## Example

### Starting Point

Một API server dùng in-memory counter cho `100 req/min/user`. Design ổn khi chỉ có một instance.

### Requirement Changes

Traffic tăng và service scale lên 10 instances sau Load Balancer.

### Naive Fix

Giữ cùng counter logic ở mỗi instance. Effective global allowance tăng theo số server. Sau đó team chuyển counter sang Redis nhưng vẫn dùng `GET` rồi `SET` riêng.

### Root Cause

Quota là invariant toàn cục nhưng decision đang được thực hiện trên state cục bộ hoặc bằng non-atomic read-modify-write.

### Better Design

Gateway xác định stable identity, Rate Limiter resolve policy, coordination store thực hiện atomic check-and-consume theo key/window hoặc token-bucket state. Failure behavior được định nghĩa theo risk của endpoint.

### Why It Works

Mọi instance cùng nhìn một allowance state và không có race window giữa check với consume. Algorithm biểu diễn đúng burst semantics, còn fail-open/fail-closed trở thành explicit product trade-off thay vì hành vi ngẫu nhiên khi outage.

## When to Use

Dùng distributed rate limiting để bảo vệ shared capacity, paid API/model cost, quota và fairness trên nhiều instances. Nếu chỉ cần per-process protection hoặc approximate shedding, local limiter có thể đủ và đơn giản hơn.

## Common Mistakes

- Local counter cho một global policy.
- Shared counter nhưng read-modify-write không atomic.
- Không định nghĩa identity/scope.
- Nhầm bucket capacity với refill rate.
- Không định nghĩa behavior khi coordination store lỗi.
- Dùng IP làm identity mặc định dù NAT/shared networks làm fairness sai.

## Decision Guide

1. Quota là per user, tenant, API key, IP hay resource?
2. Guarantee cần strict hay approximate?
3. Burst được phép bao nhiêu và sustained rate bao nhiêu?
4. Enforcement cần global qua bao nhiêu regions/instances?
5. Coordination latency nằm trong request budget không?
6. Hot tenant/key có thể tạo hotspot không?
7. Store outage phải ưu tiên availability hay quota correctness?

## Practical Takeaway

Distributed Rate Limiter là bài toán **coordination scope + atomicity + product semantics**. Đừng bắt đầu từ Redis hay một algorithm cụ thể. Hãy định nghĩa invariant trước, đặt enforcement trước resource cần bảo vệ, rồi chọn state model đủ mạnh để mọi decision maker cùng enforce invariant đó.

## Self-test

1. Vì sao 10 local counters không enforce một global limit?
2. Shared counter vẫn sai trong race `99 → 100` như thế nào?
3. Fixed Window và Token Bucket khác nhau ở burst semantics nào?
4. Vì sao fail-open/fail-closed không có một default đúng cho mọi API?

<details><summary>Answers</summary>
1. Mỗi instance cấp allowance riêng. 2. Hai server có thể cùng đọc 99 và cùng allow; check-and-consume phải atomic. 3. Fixed Window có boundary burst; Token Bucket biểu diễn burst bằng capacity và sustained rate bằng refill. 4. Hai lựa chọn đánh đổi availability với quota/security/cost correctness khác nhau.
