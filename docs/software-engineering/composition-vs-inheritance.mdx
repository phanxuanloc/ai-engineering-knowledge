# Composition vs Inheritance

## TL;DR

<TLDR>

**Inheritance** phù hợp khi subtype thật sự có quan hệ **IS-A** ổn định và giữ đúng behavioral contract của parent. **Composition** phù hợp khi object được lắp từ các **replaceable capabilities** theo quan hệ **HAS-A / USES-A**.

Heuristic “favor composition over inheritance” không có nghĩa inheritance là anti-pattern. Câu hỏi quan trọng hơn là: **behavior này thuộc identity ổn định của một subtype, hay chỉ là capability/configuration có thể thay đổi độc lập?**

</TLDR>

## Why It Matters

Composition và inheritance đều có thể tạo code chạy đúng. Khác biệt thường chỉ lộ ra khi requirement bắt đầu thay đổi.

Một hierarchy ban đầu rất gọn có thể dần phải encode OCR, embedding, storage provider, feature flag và nhiều tổ hợp runtime khác nhau. Khi đó mỗi feature mới không chỉ thêm behavior — nó còn làm **type hierarchy phình ra** và kéo theo coupling giữa parent/child.

Ngược lại, chuyển mọi thứ sang composition cũng không tự động tạo design tốt. Nếu một object inject hàng chục dependency, biết trực tiếp vendor SDK và dùng interface cho cả những detail không có change pressure, design chỉ đổi từ “deep hierarchy” sang “indirection everywhere”.

Vì vậy bài toán không phải:

> “Composition hay inheritance cái nào tốt hơn?”

Mà là:

> **Đâu là identity ổn định của object, đâu là capability có thể thay thế, và change pressure sẽ đi qua design này như thế nào?**

Hãy hình dung **inheritance** như khai báo “object này thuộc cùng một family và phải giữ lời hứa của parent”. Khi `CleanupJob extends Job`, caller kỳ vọng `CleanupJob` thật sự có thể được dùng như một `Job`.

Còn **composition** giống lắp một hệ thống từ các bộ phận. `DocumentProcessor` dùng `Parser`, `OcrEngine`, `Embedder` và `VectorStore`; đổi một bộ phận không nhất thiết làm identity của processor thay đổi.

<Principle label="Default question">Behavior này là identity ổn định của subtype, hay chỉ là capability/configuration mà object đang sử dụng?</Principle>

## Core Concepts

### Inheritance model subtype identity

Inheritance không chỉ reuse code. Child còn nhận relationship với parent: contract, lifecycle, protected behavior và ảnh hưởng từ những thay đổi ở parent.

Một inheritance relationship có ý nghĩa khi:

- child thật sự là một subtype của parent;
- caller có thể dùng child ở nơi cần parent mà không special-case;
- behavioral contract của parent vẫn đúng với child;
- hierarchy phản ánh domain/lifecycle ổn định, không phải một tập feature tùy chọn.

### Composition assemble behavior từ collaborators

Composition tạo behavior bằng cách để object **HAS-A / USES-A** các collaborator khác.

```ts
class DocumentProcessor {
  constructor(
    private readonly parser: Parser,
    private readonly ocr: OcrEngine | null,
    private readonly embedder: Embedder | null,
    private readonly vectorStore: VectorStore,
  ) {}
}
```

`DocumentProcessor` không phải `Parser`, `OcrEngine` hay `VectorStore`. Nó **dùng** các capability đó để hoàn thành workflow.

### Replaceable capability khác subtype identity

Một capability thường có change pressure riêng: OCR provider có thể đổi, embedding model có thể đổi, vector store có thể đổi, hoặc capability có thể bật/tắt theo tenant.

Nếu thay capability không làm object trở thành “một loại object khác” về mặt semantic, capability đó thường phù hợp với composition hơn inheritance.

### Substitutability là điều kiện của inheritance

`Child extends Parent` chỉ chứng minh relationship ở syntax. Design chỉ đúng về semantic nếu child giữ được behavioral expectations của parent.

Nếu caller phải hỏi “đây là subtype nào?” rồi special-case, hoặc child phải throw `unsupported` cho behavior parent promise, quan hệ IS-A đang đáng nghi.

### Composition không đồng nghĩa abstraction everywhere

Composition mô tả cách assemble object; nó **không bắt mọi collaborator phải có interface**.

Nếu một dependency nhỏ, ổn định và chỉ có một implementation, dùng concrete collaborator vẫn là composition:

```ts
class DocumentProcessor {
  constructor(
    private readonly parser: PdfParser,
    private readonly vectorStore: VectorStore,
  ) {}
}
```

## Example

Ta sẽ dùng một document-processing pipeline xuyên suốt để thấy requirement thay đổi làm design chịu pressure như thế nào.

### Starting Point — một hierarchy nhỏ vẫn có thể hợp lý

Ban đầu hệ thống chỉ cần xử lý PDF:

```ts
class DocumentProcessor {
  process(file: File): Promise<Document> {
    // shared processing flow
  }
}

class PdfProcessor extends DocumentProcessor {
  process(file: File): Promise<Document> {
    // parse PDF
  }
}
```

Ở thời điểm này chưa có đủ lý do để kết luận hierarchy là sai. Nếu `PdfProcessor` thật sự là một loại `DocumentProcessor`, contract ổn định và không có variability đáng kể, design này có thể hoàn toàn chấp nhận được.

Điểm quan trọng là **không cargo-cult composition trước khi pressure xuất hiện**.

### Requirement Changes — feature bắt đầu trở thành tổ hợp

Product yêu cầu OCR cho scanned PDF:

```ts
class OcrPdfProcessor extends PdfProcessor {
  // parse PDF + OCR
}
```

Sau đó cần embeddings:

```ts
class EmbeddingOcrPdfProcessor extends OcrPdfProcessor {
  // parse + OCR + embed
}
```

Rồi requirement tiếp tục mở rộng:

- một số PDF cần OCR, một số không;
- DOCX dùng parser khác;
- embeddings có nhiều provider;
- vector store có thể là Pinecone, Qdrant hoặc pgvector;
- OCR có thể bật/tắt theo tenant;
- một pipeline chỉ parse + index, pipeline khác parse + OCR + embed + index.

Hierarchy bắt đầu phải biểu diễn **mọi tổ hợp feature**:

```text
DocumentProcessor
├─ PdfProcessor
│  ├─ OcrPdfProcessor
│  │  ├─ EmbeddingOcrPdfProcessor
│  │  └─ QdrantEmbeddingOcrPdfProcessor
│  └─ EmbeddingPdfProcessor
└─ DocxProcessor
   └─ EmbeddingDocxProcessor
```

Đây là signal quan trọng: tree không còn chủ yếu model subtype identity. Nó đang model **configuration space**.

### Root Cause — capability bị đóng cứng vào type hierarchy

OCR, embedding và vector store không phải identity cốt lõi của `DocumentProcessor`. Chúng là capabilities có lifecycle và variability riêng.

Khi những capability này bị encode vào class name/type tree, mỗi combination mới có xu hướng sinh thêm subclass. Hậu quả không chỉ là “nhiều class hơn”:

- behavior bị phân tán qua nhiều parent/child layers;
- parent change có blast radius xuống descendants;
- khó test capability độc lập;
- runtime configuration trở nên vụng về;
- trace “processor này thực sự làm gì” đòi hỏi đọc cả hierarchy;
- số subtype có thể tăng theo số tổ hợp feature thay vì theo domain identity.

### Better Design — giữ orchestration ổn định, compose capability

Thay vì biến từng feature combination thành một subtype, `DocumentProcessor` giữ orchestration và nhận các collaborator:

```ts
class DocumentProcessor {
  constructor(
    private readonly parser: Parser,
    private readonly ocr: OcrEngine | null,
    private readonly embedder: Embedder | null,
    private readonly vectorStore: VectorStore,
  ) {}

  async process(file: File) {
    let document = await this.parser.parse(file);

    if (this.ocr) {
      document = await this.ocr.enrich(document);
    }

    const embedding = this.embedder
      ? await this.embedder.embed(document)
      : null;

    await this.vectorStore.save(document, embedding);
  }
}
```

Relationship bây giờ là:

```text
DocumentProcessor
  USES Parser
  USES OcrEngine
  USES Embedder
  USES VectorStore
```

Không cần tạo subtype mới chỉ vì đổi OCR provider hoặc vector store.

### Why It Works — change đi vào capability boundary thay vì type tree

Giả sử đổi OCR engine từ Tesseract sang cloud OCR:

```ts
const processor = new DocumentProcessor(
  new PdfParser(),
  new CloudOcrEngine(),
  new OpenAIEmbedder(),
  new QdrantVectorStore(),
);
```

`DocumentProcessor` không đổi.

Đổi vector store:

```ts
const processor = new DocumentProcessor(
  new PdfParser(),
  new CloudOcrEngine(),
  new OpenAIEmbedder(),
  new PgVectorStore(),
);
```

Orchestration vẫn không đổi. Change được cô lập vào capability boundary tương ứng.

Lợi ích cốt lõi không phải “ít class” hay “nhiều interface”, mà là:

> **Feature variability không còn bắt type hierarchy phải tăng theo mọi combination.**

### Một ví dụ tương tự trong AI Agent

AI Agent thường tự nhiên phù hợp với composition:

```text
Agent
├─ LLM
├─ Tools
├─ Memory
└─ Retriever
```

Agent **uses** các capability này. Một coding agent có thể đổi model, tool set, memory strategy, retriever hoặc sandbox/runtime mà vẫn là cùng một loại agent về mặt orchestration.

Nếu mỗi combination trở thành subtype:

```text
BaseAgent
└─ ToolAgent
   └─ MemoryToolAgent
      └─ RagMemoryToolAgent
         └─ ClaudeRagMemoryToolAgent
```

hierarchy nhanh chóng phản ánh configuration thay vì identity.

Composition cho phép assemble runtime:

```ts
const agent = new Agent({
  model,
  tools,
  memory,
  retriever,
});
```

Đó là cùng một reasoning: capability có thể thay đổi độc lập thì thường nên được compose thay vì encode vào subtype name.

## When to Use

Ưu tiên **composition** khi:

- behavior là capability độc lập;
- implementation có thể thay đổi riêng;
- nhiều combination/configuration cần tồn tại;
- runtime assembly là requirement;
- hierarchy bắt đầu tăng theo feature combinations;
- muốn test collaborators độc lập.

**Inheritance** vẫn phù hợp khi:

- có subtype relationship thật;
- subtype contract ổn định;
- child substitutable cho parent;
- shared lifecycle/polymorphism là bản chất của model;
- hierarchy nông và dễ reasoning.

Ví dụ một framework có lifecycle chung:

```ts
abstract class Job {
  abstract execute(): Promise<void>;

  async run() {
    await this.beforeExecute();
    await this.execute();
    await this.afterExecute();
  }

  protected async beforeExecute() {}
  protected async afterExecute() {}
}
```

Nếu `CleanupJob`, `ReindexJob` và `ReportJob` đều thật sự là `Job`, giữ lifecycle contract và caller có thể đối xử với chúng như `Job`, inheritance diễn đạt model rất tự nhiên.

Trước khi chọn inheritance, kiểm tra:

- subtype có giữ preconditions/postconditions hợp lý không?
- caller có cần check subtype trước khi dùng không?
- child có throw `unsupported` cho behavior parent promise không?
- parent change có phá assumptions của child không?

Nếu có các signal này, “IS-A” trên class diagram có thể chỉ đúng về syntax, không đúng về behavior.

## Common Mistakes

### Dùng inheritance chỉ để reuse code

Hai class dùng chung code không chứng minh chúng có quan hệ IS-A.

Nếu chỉ cần reuse formatter/helper, có thể extract collaborator hoặc function:

```ts
class InvoiceExporter {
  constructor(private readonly formatter: CsvFormatter) {}
}

class UserExporter {
  constructor(private readonly formatter: CsvFormatter) {}
}
```

Không cần tạo:

```text
BaseCsvThing
├─ InvoiceExporter
└─ UserExporter
```

Inheritance tạo coupling mạnh hơn reuse đơn thuần vì child còn phụ thuộc vào parent contract, protected state, lifecycle và behavior evolution.

### Coi composition luôn thắng

Một stable subtype hierarchy với contract rõ ràng có thể đơn giản hơn rất nhiều so với object graph có quá nhiều collaborator.

Heuristic “favor composition” là cảnh báo chống lạm dụng inheritance, không phải lệnh cấm inheritance.

### Composition nhưng vẫn leak vendor detail

```ts
class DocumentProcessor {
  constructor(
    private readonly awsTextract: AwsTextractClient,
    private readonly pinecone: PineconeClient,
    private readonly openAI: OpenAIClient,
  ) {}
}
```

Đây vẫn là composition về object structure, nhưng core processor biết trực tiếp vendor mechanics.

Nếu những mechanics đó thay đổi độc lập với orchestration, meaningful capability boundaries có thể tốt hơn:

```ts
class DocumentProcessor {
  constructor(
    private readonly ocr: OcrEngine,
    private readonly embedder: Embedder,
    private readonly vectorStore: VectorStore,
  ) {}
}
```

Composition không thay thế reasoning về [Abstraction & Encapsulation](./abstraction-and-encapsulation.mdx) hay [Coupling & Cohesion](./coupling-and-cohesion.mdx).

### Interface hóa mọi collaborator

Một collaborator concrete, nhỏ và ổn định không cần abstraction chỉ để “đúng composition”. Hãy thêm boundary khi variability, ownership hoặc change pressure thực sự cần nó.

### Confuse configuration với identity

“OCR-enabled”, “Redis-backed”, “Qdrant-backed” hay “GPT-powered” thường mô tả configuration/capability. Chỉ vì một object có feature khác không có nghĩa nó cần trở thành subtype mới.

## Decision Guide

Khi chọn giữa composition và inheritance, hỏi:

1. Đây có thật sự là **IS-A**, hay chỉ là **USES-A / HAS-A**?
2. Caller có thể thay subtype vào parent mà không special-case không?
3. Behavior này là identity ổn định hay capability có thể đổi?
4. Requirement mới có làm sinh thêm subclass chỉ vì feature combination không?
5. Parent change có blast radius lớn xuống descendants không?
6. Capability có cần runtime configuration, independent testing hoặc provider replacement không?
7. Mình đang dùng inheritance vì domain model hay chỉ vì code reuse thuận tiện?
8. Nếu dùng composition, collaborator này có thật sự cần abstraction hay concrete dependency đã đủ?

Một rule thực dụng:

| Signal | Nghiêng về |
| --- | --- |
| Stable subtype identity + substitutability | Inheritance |
| Shared lifecycle là bản chất của model | Inheritance |
| Replaceable capability / provider | Composition |
| Runtime configuration | Composition |
| Feature combinations làm subclass tăng nhanh | Composition |
| Chỉ cần reuse helper/algorithm | Extract function/module hoặc composition |

## Practical Takeaway

Đừng bắt đầu review bằng câu “có nên dùng inheritance không?”. Hãy bắt đầu bằng **change pressure** và **semantic relationship**.

Một workflow ngắn:

1. Xác định object đang đại diện cho identity gì.
2. Liệt kê behavior nào là capability có thể thay đổi độc lập.
3. Kiểm tra subtype có substitutable thật không.
4. Nhìn requirement tương lai gần: feature mới tạo subtype mới hay chỉ đổi collaborator?
5. Chọn design có blast radius nhỏ nhất mà vẫn đủ đơn giản cho pressure hiện tại.

<Principle label="Design heuristic">Dùng inheritance để model stable subtype identity; dùng composition để assemble independently changing capabilities. Đừng dùng cả hai chỉ vì “best practice”.</Principle>

## Self-test

1. Signal nào cho thấy inheritance hierarchy đang model feature combinations thay vì subtype identity?
2. Vì sao code reuse không đủ để chứng minh quan hệ IS-A?
3. Composition có bắt mọi collaborator phải có interface không?
4. Khi nào inheritance vẫn là lựa chọn hợp lý?
5. Nếu `Agent` đổi từ Qdrant sang pgvector nhưng orchestration không đổi, đây là signal về identity hay capability?
