# Release Safety & Traceability

## TL;DR

<TLDR>
Một release an toàn phải test đúng integrated snapshot sẽ được deploy, có chiến lược phục hồi phù hợp và trace được từ version tới artifact đang chạy. PR CI pass riêng lẻ hoặc QA pass trên một tổ hợp khác không chứng minh production candidate an toàn.
</TLDR>

## Mental Model

<Principle label="Release invariant">{'Test what you ship, ship what you tested, và luôn biết chính xác artifact nào đang chạy.'}</Principle>

## Core Concepts

### CI, protected main and merge queue

Feature lớn không nhất thiết cần branch lớn. Có thể chia thành nhiều atomic change và dùng feature flag hoặc backward-compatible change để merge sớm. Với schema/API migration, pattern đã học là **expand → migrate → contract**: thêm shape mới tương thích trước, migrate consumer/data, cuối cùng mới xóa shape cũ.

### Rollback, revert and roll forward

`git revert` sửa source history bằng một commit đảo thay đổi. **Deployment rollback** đưa production về artifact/version trước. Chúng là hai việc khác nhau.

### Tag, SemVer and release traceability

Trong Semantic Versioning, `fix` tăng `PATCH`, `feat` tăng `MINOR`, còn breaking change tăng `MAJOR`.

Pre-release có thể dùng `alpha`, `beta`, `rc`, ví dụ `v5.0.0-rc.1 → v5.0.0-rc.2 → v5.0.0`. Git tag là mốc cố định vào một commit; release chính thức thường phù hợp với annotated tag.

Conventional Commits như `fix:`, `feat:` và `BREAKING CHANGE` có thể cung cấp metadata để automation tính version/changelog. Branch naming như `feat/*`, `fix/*`, `docs/*`, `chore/*` là team convention; tên branch không tự quyết định workflow.

## Example

Một team có `main` và shared `testing` branch. Feature 1, 2, 3 được merge vào `testing` để QA, nhưng sau đó chỉ feature 1 và 3 được merge riêng vào `main`.

Rủi ro là trạng thái đã test là `main + 1 + 2 + 3`, còn trạng thái release là `main + 1 + 3`. Final release candidate phải được test đúng với tổ hợp code sẽ release.

## When to Use

- Dùng merge queue khi nhiều PR có thể pass riêng nhưng xung đột trên latest `main`.
- Re-test integrated state trước deployment khi release được tạo từ nhiều change độc lập.
- Rollback artifact khi có known-good version và rollback tương thích với data/schema hiện tại.
- Roll forward khi rollback rủi ro nhưng fix mới nhỏ, rõ và nhanh hơn.
- Dùng immutable digest và release metadata khi cần audit hoặc điều tra production.

## Common Mistakes

- Test một tổ hợp trên shared testing branch nhưng release một tổ hợp khác mà không có final validation.
- Nhầm deployment rollback với `git revert`.
- Tin PR CI riêng lẻ mà không kiểm tra trạng thái tích hợp cuối.
- Chỉ dùng mutable Docker tag như `latest` mà không trace được release → tag → commit → immutable artifact.

## Self-test

1. Vì sao PR CI pass chưa chắc đủ khi nhiều PR merge gần nhau?
2. Deployment rollback và `git revert` khác nhau thế nào?
3. Vì sao testing snapshot khác release snapshot là một rủi ro?
4. Release traceability tốt cần nối được những mốc nào?

<details>
<summary>Answers</summary>

1. Các PR có thể pass riêng nhưng tổ hợp cuối trên main lại xung đột logic; merge queue/main CI kiểm tra integrated state mới nhất.
2. Deployment rollback đổi artifact đang chạy; `git revert` tạo commit mới để sửa source history.
3. Dependency hoặc interaction với feature bị loại có thể khiến tổ hợp production chưa từng được QA xác nhận.
4. Ít nhất cần trace release version → Git tag → commit SHA → immutable artifact/image digest → production runtime.

</details>
