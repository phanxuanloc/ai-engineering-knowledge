# Release Safety & Traceability

## TL;DR

<TLDR>
Release an toàn không chỉ là “CI xanh”. Team phải chứng minh đúng integrated snapshot sẽ được deploy, biết cách phục hồi khi production lỗi, và trace được từ release version tới source commit rồi tới immutable artifact đang chạy. PR CI pass riêng lẻ hoặc QA pass trên một tổ hợp code khác không đủ để chứng minh production candidate an toàn.
</TLDR>

## Why It Matters

Một change có thể pass unit test, pass PR CI và thậm chí QA pass, nhưng production vẫn lỗi nếu artifact cuối cùng không phải đúng snapshot đã được kiểm tra. Đây là lỗi về **release integrity**, không chỉ là lỗi test coverage.

Một release pipeline tốt cần trả lời được ba câu hỏi:

1. **What exactly did we test?** — commit hoặc integrated snapshot nào đã được validate?
2. **What exactly did we ship?** — artifact immutable nào được deploy?
3. **How do we recover?** — rollback artifact, revert source hay roll forward bằng fix mới?

Nếu không trả lời được ba câu này, production đang phụ thuộc vào giả định thay vì traceable evidence.

## Mental Model

<Principle label="Release invariant">{'Test what you ship, ship what you tested, và luôn biết chính xác artifact nào đang chạy.'}</Principle>

Hãy hình dung release như một chuỗi custody:

```text
Source change → integrated commit → CI result → immutable artifact → deployment → runtime
```

Mỗi bước phải chỉ tới bước trước một cách xác định được. Nếu pipeline build lại artifact khác sau QA, nếu deploy bằng mutable tag như `latest`, hoặc nếu shared testing branch chứa tổ hợp khác production candidate, chuỗi custody bị đứt.

## Core Concepts

### Build once, promote the same artifact

Một anti-pattern phổ biến là build artifact mới ở từng environment. Source commit có thể giống nhau nhưng dependency resolution, build timestamp, generated files hoặc base image có thể khác.

Model an toàn hơn là:

```text
commit A → build image digest D → test D → staging D → production D
```

Environment config có thể khác, nhưng **artifact identity không đổi**. Điều này làm cho câu “ship what you tested” có ý nghĩa kỹ thuật thật sự.

### Rollback, revert và roll forward là ba cơ chế khác nhau

- **Deployment rollback**: production chạy lại artifact/version trước đó.
- **Git revert**: tạo commit mới đảo source change.
- **Roll forward**: build và deploy version mới chứa fix.

Rollback thường nhanh nhất khi artifact cũ còn tương thích với data/schema hiện tại. Roll forward có thể an toàn hơn khi schema đã migrate theo chiều không backward-compatible hoặc fix mới rất nhỏ và rõ.

### Feature flag tách deploy khỏi release

Với Trunk-Based Development, code có thể được merge và deploy sớm nhưng capability vẫn ẩn sau feature flag. Điều này giảm branch lifetime mà vẫn cho phép business release vào thời điểm riêng.

Feature flag không thay thế testing. Nó chỉ giảm blast radius và cho phép activation/deactivation độc lập với source integration.

### Backward-compatible migration giảm rollback risk

Khi đổi API hoặc database schema, pattern **expand → migrate → contract** giúp old/new code cùng tồn tại trong giai đoạn chuyển tiếp:

1. **Expand** — thêm field/table/API shape mới nhưng giữ compatibility.
2. **Migrate** — chuyển data/consumer dần sang shape mới.
3. **Contract** — chỉ xóa shape cũ sau khi không còn dependency.

Nếu deploy theo kiểu “rename/drop ngay”, artifact cũ có thể không còn chạy được và rollback trở nên nguy hiểm.

### Starting Point

Một team có `main` và shared `testing` branch. Feature 1, 2, 3 được merge vào `testing` để QA.

### Root Cause

QA evidence gắn với `main + 1 + 2 + 3`, trong khi production candidate là `main + 1 + 3`. Team đã kiểm thử **feature presence**, nhưng không kiểm thử **release identity**.

### Better Design

Tạo final release candidate trước, chạy required integration/QA checks trên đúng candidate đó, build immutable artifact một lần rồi promote chính artifact ấy tới production.

Nếu team cần chọn scope linh hoạt, short-lived branch + feature flags thường an toàn hơn một shared testing branch dùng như “giỏ feature”.

### Why It Works

Release candidate, test result và artifact identity đều nối tới cùng một source state. Khi incident xảy ra, team biết chính xác release nào đang chạy và có thể quyết định rollback hay roll forward dựa trên compatibility thực tế thay vì đoán.

## When to Use

- Dùng **merge queue** khi nhiều PR merge gần nhau và latest-main interaction có thể tạo lỗi.
- Re-test **integrated state** khi production candidate được hình thành từ nhiều change độc lập.
- Dùng **build once, promote** khi cần confidence rằng staging và production dùng cùng binary/image.
- Dùng **feature flag** khi muốn merge/deploy sớm nhưng release business độc lập.
- Dùng **rollback artifact** khi known-good version còn tương thích với data/schema hiện tại.
- **Roll forward** khi rollback rủi ro hơn một fix mới nhỏ và rõ.
- Ghi **version + commit SHA + artifact digest + deployment metadata** khi cần audit và incident traceability.

## Common Mistakes

- Test một tổ hợp trên shared testing branch nhưng release một tổ hợp khác mà không có final validation.
- Build lại artifact riêng cho production sau khi staging đã test artifact khác.
- Nhầm deployment rollback với `git revert`.
- Tin PR CI riêng lẻ nhưng không kiểm tra integrated state cuối cùng.
- Dùng mutable Docker tag như `latest` làm release identity duy nhất.
- Thiết kế migration khiến version cũ không còn tương thích nhưng vẫn giả định “rollback luôn an toàn”.
- Dùng feature flag như lý do để bỏ qua integration test hoặc observability.

## Decision Guide

Trước khi deploy, kiểm tra:

1. **Candidate identity** — commit SHA hoặc release branch/tag nào đang được release?
2. **Validation identity** — CI/QA đã chạy trên đúng candidate đó chưa?
3. **Artifact identity** — artifact/image digest nào được build và test?
4. **Promotion integrity** — staging và production có dùng cùng artifact không?
5. **Recovery path** — rollback artifact có tương thích schema/data không? Nếu không, roll forward plan là gì?
6. **Runtime traceability** — từ production có truy ngược được version → commit → artifact không?

## Practical Takeaway

Release safety là bài toán **identity + validation + recovery**. Team trưởng thành không chỉ hỏi “test pass chưa?” mà hỏi “đúng cái sẽ ship đã pass chưa?”.

Một release pipeline tốt nên giữ invariant:

```text
validated source state == artifact source state == deployed artifact identity
```

Khi invariant này rõ ràng, rollback, incident investigation và audit đều đơn giản hơn đáng kể.

## Self-test

1. Vì sao hai PR cùng pass CI vẫn có thể làm `main` lỗi sau khi merge?
2. Deployment rollback và `git revert` khác nhau thế nào?
3. Vì sao build lại image cho production làm yếu traceability dù source commit giống staging?
4. Shared testing branch đã QA pass nhưng production release subset feature khác. Cần làm gì trước deploy?

<details>
<summary>Answers</summary>

1. Chúng có thể xung đột logic khi cùng tồn tại trên latest integration state; merge queue/main CI kiểm tra tổ hợp cuối.
2. Rollback đổi artifact đang chạy; `git revert` tạo commit mới để sửa source history.
3. Build mới có thể khác dependency/base image/generated output; staging evidence không còn gắn chắc với production artifact.
4. Tạo đúng final candidate, chạy validation/QA trên candidate đó, build immutable artifact và deploy chính artifact đã được xác nhận.

</details>
