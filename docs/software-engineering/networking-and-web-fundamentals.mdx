# Networking & Web Fundamentals

## TL;DR

<TLDR>

Một web request có thể được debug theo hành trình: **Resolve Destination → Reach Destination → Establish Communication → Process Request → Response**. Mỗi boundary trả lời một câu hỏi khác nhau; xác định request dừng ở đâu giúp tránh debug nhầm layer.

</TLDR>

Flow trên mô tả **logical request lifecycle**. `Routing`, network policy/firewall và `NAT` là các responsibility trong network path; chúng không mặc định tương ứng với ba physical device nối tiếp. Tương tự, proxy/load balancer, application, cache và database phụ thuộc kiến trúc triển khai cụ thể.

Bốn boundary chính trả lời bốn câu hỏi debug:

### Cách dùng flow để debug

Đi theo request lifecycle và dừng ở boundary đầu tiên chưa thành công:

```text
Domain không resolve?
→ Resolve: DNS / name resolution

Resolve được nhưng IP:443 timeout?
→ Reach / Connect: route, firewall, NAT, TCP

TCP được nhưng TLS fail?
→ Connect: certificate / TLS / protocol boundary

Đã nhận HTTP 401 / 403 / 500?
→ Process: request đã đi đủ xa để server trả HTTP response

Backend đúng nhưng browser vẫn stale?
→ kiểm tra cache / CDN / browser behavior phía trên lifecycle cơ bản
```

Success ở boundary trước chỉ mở đường cho boundary sau. DNS success chưa chứng minh TCP thông; TCP thông chưa chứng minh TLS/authentication đúng; HTTP `200` cũng chưa chứng minh dữ liệu client thấy là fresh.

## Example

Khi gọi partner API:

```text
DNS                        ✓
Route                      ✓
TCP destination:443        timeout
Private IP                 10.10.1.15
Outbound NAT IP            14.1.2.9
Partner allowlist          14.1.2.3 only
```

Đừng sửa `/orders` hoặc JSON trước. Request đang fail ở Reach/Connect boundary; outbound IP cũng không khớp allowlist.

## When to Use

- Khi API/service call timeout hoặc connection refused.
- Khi cần phân biệt DNS/routing/firewall với TLS/HTTP/application failure.
- Khi browser fail nhưng curl/Postman thành công.
- Khi thiết kế service sau proxy/load balancer.
- Khi backend data đúng nhưng client vẫn thấy dữ liệu stale.

## Common Mistakes

- **Hiểu logical flow như physical topology:** responsibility không đồng nghĩa với một thiết bị riêng.
- **Bung mọi responsibility thành node nối tiếp:** routing/firewall/NAT hoặc proxy/LB/data layer không phải lúc nào cũng có strict ordering/topology giống nhau.
- **Gọi mọi failure là “API lỗi”:** nhiều failure xảy ra trước HTTP/application.
- **Debug sai layer:** có `401` mà vẫn bắt đầu từ DNS/firewall, hoặc TCP timeout mà sửa JSON.
- **Trộn responsibility:** DNS tìm destination; routing đưa traffic về phía destination; TCP tạo connection; TLS bảo vệ channel; HTTP định nghĩa web request/response.

## Self-test

1. DNS trả về `203.0.113.20`. DNS đã cho bạn biết **đường đi** tới IP đó chưa?
2. Domain resolve đúng nhưng `IP:443` timeout: nên ưu tiên phase nào?
3. Nhận `HTTP 401`: request đã vượt qua những phase nền tảng nào?
4. Curl thành công nhưng browser báo CORS: failure thuộc network connectivity hay browser policy?

<details>
<summary>Answers</summary>

1. Chưa. DNS chỉ resolve destination; routing quyết định path/next hop.
2. Reach Destination / Establish Communication: routing, network policy và TCP connectivity trước application body.
3. Resolve/Reach/transport đã tiến đủ xa để nhận HTTP response; ưu tiên authentication/application boundary.
4. Browser CORS/Same-Origin Policy.

</details>
