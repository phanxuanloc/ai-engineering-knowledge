# Networking & Web Fundamentals

## TL;DR

<TLDR>

Một web request có thể được debug như **một logical flow qua 4 boundary**: **Resolve Destination → Reach Destination → Establish Communication → Process Request**. Đây là flow theo responsibility/failure boundary, không phải sơ đồ các physical device bắt buộc phải đứng nối tiếp nhau.

</TLDR>

### Vì sao flow này không bị sai như bản cũ?

Flow chỉ nối **các boundary có progression thật**. Nó không vẽ `Routing → Firewall → NAT` thành ba hop, vì ba responsibility đó có thể cùng nằm trên một gateway/firewall appliance hoặc có topology khác nhau tùy hệ thống. Tương tự, `Proxy/LB → Application → Cache/Data` được giữ như mô tả bên trong phase **Process Request**, không bị biến thành topology bắt buộc của mọi web request.

Bốn phase trả lời bốn câu hỏi debug:

<ConceptGrid>
  <ConceptCard title="1 · Resolve Destination">
    **Đích là đâu?**

    `api.company.com` → DNS → `203.0.113.20`

    Output là **destination IP**. DNS chưa chứng minh server reachable.
  </ConceptCard>

  <ConceptCard title="2 · Reach Destination">
    **Traffic có thể đi tới destination IP:port không?**

    Routing chọn path/next hop. Firewall/security policy có thể allow/block. NAT có thể translate address khi cần.
  </ConceptCard>

  <ConceptCard title="3 · Establish Communication">
    **Hai endpoint đã nói chuyện được chưa?**

    TCP thiết lập connection tới `IP:port`; với HTTPS, TLS tạo secure channel.
  </ConceptCard>

  <ConceptCard title="4 · Process Request">
    **Web request được xử lý ra sao?**

    HTTP request đi vào server-side boundary, có thể qua proxy/load balancer, application và data layer tùy kiến trúc.
  </ConceptCard>
</ConceptGrid>

### Cách dùng flow để debug

Đi theo flow từ trái sang phải và dừng ở boundary đầu tiên chưa thành công:

```text
Domain không resolve?
→ 1 · Resolve: DNS / name resolution

Resolve được nhưng IP:443 timeout?
→ 2–3 · Reach / Connect: route, firewall, NAT, TCP

TCP được nhưng TLS fail?
→ 3 · Connect: certificate / TLS / protocol boundary

Đã nhận HTTP 401 / 403 / 500?
→ 4 · Process: request đã đi đủ xa để server trả HTTP response

Backend đúng nhưng browser vẫn stale?
→ kiểm tra cache / CDN / browser behavior phía trên lifecycle cơ bản
```

Điểm quan trọng: **success ở boundary trước chỉ mở đường cho boundary sau**. DNS success chưa chứng minh TCP thông; TCP thông chưa chứng minh TLS/authentication đúng; HTTP `200` cũng chưa chứng minh dữ liệu client thấy là fresh.

## Example

Khi gọi partner API:

```text
DNS                        ✓
Route                      ✓
TCP destination:443        timeout
Private IP                 10.10.1.15
Outbound NAT IP            14.1.2.9
Partner allowlist          14.1.2.3 only
```

Đừng sửa `/orders` hoặc JSON trước. Request đang fail ở Reach/Connect boundary; outbound IP cũng không khớp allowlist.

## When to Use

- Khi API/service call timeout hoặc connection refused.
- Khi cần phân biệt DNS/routing/firewall với TLS/HTTP/application failure.
- Khi browser fail nhưng curl/Postman thành công.
- Khi thiết kế service sau proxy/load balancer.
- Khi backend data đúng nhưng client vẫn thấy dữ liệu stale.

## Common Mistakes

- **Hiểu phase flow như physical topology:** phase mô tả responsibility/failure boundary, không khẳng định số lượng thiết bị.
- **Bung mọi responsibility thành node nối tiếp:** routing/firewall/NAT hoặc proxy/LB/data layer không phải lúc nào cũng có strict ordering/topology giống nhau.
- **Gọi mọi failure là “API lỗi”:** nhiều failure xảy ra trước HTTP/application.
- **Debug sai layer:** có `401` mà vẫn bắt đầu từ DNS/firewall, hoặc TCP timeout mà sửa JSON.
- **Trộn responsibility:** DNS tìm destination; routing đưa traffic về phía destination; TCP tạo connection; TLS bảo vệ channel; HTTP định nghĩa web request/response.

## Self-test

1. DNS trả về `203.0.113.20`. DNS đã cho bạn biết **đường đi** tới IP đó chưa?
2. Domain resolve đúng nhưng `IP:443` timeout: nên ưu tiên phase nào?
3. Nhận `HTTP 401`: request đã vượt qua những phase nền tảng nào?
4. Curl thành công nhưng browser báo CORS: failure thuộc network connectivity hay browser policy?

<details>
<summary>Answers</summary>

1. Chưa. DNS chỉ resolve destination; routing quyết định path/next hop.
2. Reach Destination / Establish Communication: routing, network policy và TCP connectivity trước application body.
3. Resolve/Reach/transport đã tiến đủ xa để nhận HTTP response; ưu tiên authentication/application boundary.
4. Browser CORS/Same-Origin Policy.

</details>
