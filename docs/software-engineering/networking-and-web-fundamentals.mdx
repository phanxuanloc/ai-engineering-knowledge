## TL;DR

<TLDR>

Đừng hiểu networking như 11 thiết bị mà một packet lần lượt chui qua. Mental model hữu ích hơn là **4 phase**: **Resolve Destination → Reach Destination → Establish Communication → Process Request**. Mỗi phase gồm các responsibility khác nhau để một web request hoàn thành.

</TLDR>

### Cách đọc diagram

**1 · Resolve Destination — “Đích là đâu?”**

Client bắt đầu với domain như `api.company.com`. DNS resolve tên đó thành destination IP, ví dụ `203.0.113.20`. DNS làm nhiệm vụ **name → IP**; nó không quyết định packet sẽ đi qua router nào.

**2 · Reach Destination — “Đi đường nào tới IP đó?”**

Khi đã biết destination IP, operating system/network dùng routing để chọn path/next hop. Trên đường đi, firewall/security policy có thể allow hoặc block traffic; NAT có thể translate private source IP thành outbound IP. Routing, firewall và NAT là các **network responsibilities** và có thể cùng tồn tại trên một router/gateway/firewall appliance — không nhất thiết là ba máy đứng nối tiếp nhau.

**3 · Establish Communication — “Hai endpoint nói chuyện được chưa?”**

Client thiết lập TCP connection tới `destination IP:port`, ví dụ `203.0.113.20:443`. Với HTTPS, TLS handshake sau đó tạo secure channel. Khi transport/security boundary đã sẵn sàng, HTTP request mới được trao đổi qua channel đó.

**4 · Process Request — “Server xử lý request thế nào?”**

HTTP request có thể tới reverse proxy/load balancer trước, được route tới application instance, rồi application thực hiện authentication/business logic và đọc/ghi cache hoặc database. Response sau đó quay trở lại client qua communication path.

Mental model debug tương ứng:

```text
1. Resolve destination   Domain → DNS → Destination IP
2. Reach destination     IP → Routing → Firewall/NAT → destination:port
3. Establish communication   TCP → TLS → HTTP request
4. Process request       Proxy/LB → Application → Cache/Data
```

Điểm quan trọng: đây là **logical request lifecycle**, không phải danh sách 11 physical hops. DNS success chưa chứng minh route/TCP thông; TCP thông chưa chứng minh TLS/authentication đúng; HTTP `200` cũng chưa chứng minh dữ liệu client thấy là fresh.

## Example

Khi gọi partner API:

```text
DNS                        ✓
Route                      ✓
TCP destination:443        timeout
Private IP                 10.10.1.15
Outbound NAT IP            14.1.2.9
Partner allowlist          14.1.2.3 only
```

Đừng sửa `/orders` hoặc JSON trước. Request đang fail ở network/TCP boundary; outbound IP cũng không khớp allowlist.

## When to Use

- Khi API/service call timeout hoặc connection refused.
- Khi cần phân biệt DNS/routing/firewall với TLS/HTTP/application failure.
- Khi browser fail nhưng curl/Postman thành công.
- Khi thiết kế service sau proxy/load balancer.
- Khi backend data đúng nhưng client vẫn thấy dữ liệu stale.

## Common Mistakes

- **Hiểu diagram như physical topology:** các box mô tả responsibility/giai đoạn; router, firewall và NAT có thể nằm trên cùng infrastructure component.
- **Gọi mọi failure là “API lỗi”:** nhiều failure xảy ra trước HTTP/application.
- **Debug sai layer:** có `401` mà vẫn bắt đầu từ DNS/firewall, hoặc TCP timeout mà sửa JSON.
- **Trộn responsibility:** DNS tìm destination; routing tìm path; TCP tạo connection; TLS bảo vệ channel; HTTP định nghĩa web request/response.

## Self-test

1. DNS trả về `203.0.113.20`. DNS đã cho bạn biết **đường đi** tới IP đó chưa?
2. Domain resolve đúng nhưng `IP:443` timeout: nên ưu tiên phase nào?
3. Nhận `HTTP 401`: request đã vượt qua những phase nền tảng nào?
4. Curl thành công nhưng browser báo CORS: failure thuộc network connectivity hay browser policy?

<details>
<summary>Answers</summary>

1. Chưa. DNS chỉ resolve destination; routing quyết định path/next hop.
2. Reach Destination / Establish Communication: routing, network policy và TCP connectivity trước application body.
3. Resolve/Reach/transport đã tiến đủ xa để nhận HTTP response; ưu tiên authentication/application boundary.
4. Browser CORS/Same-Origin Policy.

</details>
