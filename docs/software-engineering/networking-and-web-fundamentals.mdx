# Networking & Web Fundamentals

## TL;DR

<TLDR>

Đừng hiểu networking như một packet phải lần lượt đi qua 11 box. Mental model hữu ích hơn là **một web request phải vượt qua 4 câu hỏi độc lập**: **đích là đâu? → có tới được đích không? → hai endpoint nói chuyện được chưa? → server xử lý request thế nào?**

</TLDR>

## Mental Model

### Một web request = 4 câu hỏi debug

<ConceptGrid>
  <ConceptCard title="1 · Resolve Destination">
    **Đích là đâu?**

    `api.company.com` → DNS → `203.0.113.20`

    Output của phase này là **destination IP**. DNS không quyết định packet sẽ đi qua router nào và cũng chưa chứng minh server reachable.
  </ConceptCard>

  <ConceptCard title="2 · Reach Destination">
    **Traffic có tới được destination IP:port không?**

    Routing chọn next hop/path. Firewall có thể allow/block. NAT có thể translate source/destination address.

    Đây là **network reachability**, không phải một chuỗi bắt buộc `Router → Firewall → NAT`.
  </ConceptCard>

  <ConceptCard title="3 · Establish Communication">
    **Hai endpoint đã có channel để nói chuyện chưa?**

    TCP kết nối tới `IP:port`; với HTTPS, TLS tạo secure channel; sau đó HTTP message mới được trao đổi trên channel đó.

    TCP success không có nghĩa TLS, authentication hay business logic đã đúng.
  </ConceptCard>

  <ConceptCard title="4 · Process Request">
    **Server xử lý request ra sao?**

    Request có thể qua reverse proxy/load balancer, tới application, rồi đọc/ghi cache hoặc database trước khi response quay lại client.

    Những component này mô tả **responsibility**, không phải lúc nào cũng là các physical hop riêng biệt.
  </ConceptCard>
</ConceptGrid>

### Story của một request

Đừng bắt đầu bằng topology. Hãy theo dõi **state mà client biết được sau mỗi phase**:

```text
User types https://api.company.com/users

        ↓ 1. Resolve destination
Known: destination IP = 203.0.113.20
Unknown: route / reachability / application health

        ↓ 2. Reach destination
Known: traffic can reach 203.0.113.20:443
Unknown: secure session / HTTP result

        ↓ 3. Establish communication
Known: TCP + TLS channel is ready
Unknown: authorization / business result

        ↓ 4. Process request
Known: HTTP request reached server-side processing
Result: response or application-level failure
```

Mental model này cố tình **không vẽ DNS → Router → Firewall → NAT → TCP → TLS → HTTP như một physical pipeline**. Một router/gateway có thể đồng thời làm routing, firewall và NAT; proxy/load balancer có thể nằm ở nhiều deployment boundary khác nhau. Điều cần giữ là **responsibility và failure boundary**, không phải số lượng box.

### Cách dùng mental model để debug

```text
Domain không resolve?
→ Phase 1: DNS / name resolution

Resolve được nhưng IP:port timeout?
→ Phase 2–3: route / firewall / NAT / TCP

TCP được nhưng TLS fail?
→ Phase 3: certificate / protocol / TLS boundary

Đã nhận HTTP 401 / 403 / 500?
→ Phase 4: request đã đi đủ xa để server trả HTTP response

Backend đúng nhưng browser vẫn stale?
→ phía trên request lifecycle cơ bản: cache / CDN / browser behavior
```

Điểm quan trọng: **success ở phase trước chỉ mở đường cho phase sau**. DNS success chưa chứng minh TCP thông; TCP thông chưa chứng minh TLS/authentication đúng; HTTP `200` cũng chưa chứng minh dữ liệu client thấy là fresh.

## Example

Khi gọi partner API:

```text
DNS                        ✓
Route                      ✓
TCP destination:443        timeout
Private IP                 10.10.1.15
Outbound NAT IP            14.1.2.9
Partner allowlist          14.1.2.3 only
```

Đừng sửa `/orders` hoặc JSON trước. Request đang fail ở network/TCP boundary; outbound IP cũng không khớp allowlist.

## When to Use

- Khi API/service call timeout hoặc connection refused.
- Khi cần phân biệt DNS/routing/firewall với TLS/HTTP/application failure.
- Khi browser fail nhưng curl/Postman thành công.
- Khi thiết kế service sau proxy/load balancer.
- Khi backend data đúng nhưng client vẫn thấy dữ liệu stale.

## Common Mistakes

- **Hiểu diagram như physical topology:** responsibility có thể cùng nằm trên một infrastructure component; đừng suy ra một chuỗi physical hop chỉ từ tên layer.
- **Gọi mọi failure là “API lỗi”:** nhiều failure xảy ra trước HTTP/application.
- **Debug sai layer:** có `401` mà vẫn bắt đầu từ DNS/firewall, hoặc TCP timeout mà sửa JSON.
- **Trộn responsibility:** DNS tìm destination; routing tìm path; TCP tạo connection; TLS bảo vệ channel; HTTP định nghĩa web request/response.

## Self-test

1. DNS trả về `203.0.113.20`. DNS đã cho bạn biết **đường đi** tới IP đó chưa?
2. Domain resolve đúng nhưng `IP:443` timeout: nên ưu tiên phase nào?
3. Nhận `HTTP 401`: request đã vượt qua những phase nền tảng nào?
4. Curl thành công nhưng browser báo CORS: failure thuộc network connectivity hay browser policy?

<details>
<summary>Answers</summary>

1. Chưa. DNS chỉ resolve destination; routing quyết định path/next hop.
2. Reach Destination / Establish Communication: routing, network policy và TCP connectivity trước application body.
3. Resolve/Reach/transport đã tiến đủ xa để nhận HTTP response; ưu tiên authentication/application boundary.
4. Browser CORS/Same-Origin Policy.

</details>
