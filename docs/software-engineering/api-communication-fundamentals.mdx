# API Communication Fundamentals

## TL;DR

REST, gRPC và GraphQL không phải ba phiên bản tốt–xấu của cùng một thứ. Chúng tối ưu cho những **communication problem** khác nhau:

- **REST → Resource:** caller thao tác resource nào qua HTTP semantics?
- **gRPC → Service / Method:** service đang gọi typed remote method nào?
- **GraphQL → Data Shape:** client cần chính xác fields và relationships nào?

Đừng chọn một API style cho toàn hệ thống rồi ép mọi boundary đi theo. Hãy nhìn **consumer, contract, runtime behavior, data shape, failure model và operational cost** của từng boundary. Một system hoàn toàn có thể dùng REST hoặc GraphQL ở client-facing boundary và gRPC giữa internal services.

## Why It Matters

Một API không chỉ là syntax để gửi JSON từ A sang B. Nó là **contract tại một communication boundary**.

Contract đó ảnh hưởng trực tiếp đến:

- client phải biết gì để gọi đúng;
- server expose capability dưới dạng resource, method hay schema;
- payload được shape ở phía nào;
- compatibility được duy trì ra sao khi hệ thống evolve;
- timeout, retry, streaming và remote failure được xử lý thế nào;
- team phải quan sát, debug và vận hành interaction đó ra sao.

Ví dụ, một e-commerce platform có thể đồng thời có ba nhu cầu:

1. third-party developers cần một public CRUD API dễ hiểu;
2. `Order Service` cần gọi `Payment Service` với typed contract giữa Java và Go;
3. mobile dashboard cần lấy User, Order và Reward với data shape thay đổi theo từng screen.

Nếu chỉ hỏi “REST, gRPC hay GraphQL cái nào tốt hơn?”, câu hỏi đã thiếu context. Câu hỏi đúng hơn là:

> **Boundary này đang tối ưu cho kiểu communication nào, và trade-off nào quan trọng nhất?**

Một distinction quan trọng khác:

- **API shape** trả lời caller nhìn thấy contract gì.
- **Runtime behavior** trả lời message thật sự chạy qua network như thế nào.
- **System topology** trả lời component nào kết nối với component nào.

Ba góc nhìn này liên quan nhưng không phải một. Ví dụ generated gRPC stub có thể làm call site trông giống local method, nhưng runtime vẫn là remote call với latency, timeout và service unavailable.

## Core Concepts

### REST: Resource-oriented API

REST thường dùng URL để biểu diễn resource và HTTP method để biểu diễn operation.

```http
GET    /orders/123
POST   /orders
PATCH  /orders/123
DELETE /orders/123
```

Dùng HTTP + JSON không tự động biến một API thành RESTful. Ví dụ `POST /createOrder` hoặc `POST /getUser` thiên về action/RPC-style hơn vì action nằm ngay trong URL.

Một mental model thực dụng cho request shape:

- **Path** xác định resource hoặc scope cụ thể, ví dụ `/users/123/orders`.
- **Query** dùng cho filter, sort, pagination hoặc option, ví dụ `?status=PAID&page=2`.
- **Body** chứa data dùng để tạo hoặc thay đổi resource.

`PUT` và `PATCH` cũng cần phân biệt: `PUT` mang replacement semantics, còn `PATCH` phù hợp khi chỉ cập nhật một phần resource.

REST không cấm domain action. `POST /orders/123/cancel` có thể hợp lý khi `cancel` là một state transition có domain meaning, thay vì cố ép mọi behavior thành CRUD thuần túy.

### Idempotency

Một operation là **idempotent** khi thực hiện cùng operation nhiều lần vẫn dẫn đến cùng final state như thực hiện một lần.

Ví dụ `PUT /users/123` với cùng representation hoặc `DELETE /users/123` có thể giữ idempotent semantics. Response của lần gọi sau có thể khác, nhưng final state không đổi.

`POST` không mặc định idempotent. Với payment, retry sau timeout có thể gây double charge nếu server coi mỗi request là operation mới. Một pattern phổ biến là gửi `Idempotency-Key` để server nhận diện retry của cùng một logical operation và không charge lại.

### HTTP status code mental model

Không cần học thuộc mọi status code ngay từ đầu. Có thể bắt đầu với family:

- **2xx:** success.
- **4xx:** request/client-side problem.
- **5xx:** server-side problem.

Một vài distinction quan trọng:

- `201 Created`: tạo resource thành công.
- `401 Unauthorized`: chưa authenticate được hoặc credential không hợp lệ.
- `403 Forbidden`: đã biết caller là ai nhưng caller không có quyền thực hiện operation.

### gRPC: Service/method-oriented RPC

gRPC thường được mô hình hóa quanh service và RPC method:

```proto
service PaymentService {
  rpc GetPayment(GetPaymentRequest)
      returns (GetPaymentResponse);
}
```

File `.proto` là shared contract. `service` và `rpc` định nghĩa operation; `message` định nghĩa typed request/response. Từ contract này có thể generate client/server code cho nhiều ngôn ngữ, ví dụ Java và Go.

Một generated call có thể trông giống local method call:

```java
paymentClient.getPayment(request);
```

nhưng vẫn là remote call qua network. Vì vậy latency, timeout, service unavailable và network failure vẫn phải được xử lý như mọi distributed-system interaction khác.

### Protobuf và schema evolution

Trong Protobuf:

```proto
message Payment {
  int64 id = 1;
  string status = 2;
}
```

`1` và `2` là field numbers/tags của wire contract, không phải default values. Không nên reuse một field number cũ cho field mang ý nghĩa khác.

Additive change thường an toàn hơn breaking change. Khi field đã bị loại bỏ, có thể dùng `reserved` để tránh vô tình reuse number hoặc name cũ.

### gRPC streaming

gRPC hỗ trợ bốn interaction pattern cơ bản:

- **Unary:** một request → một response.
- **Server streaming:** một request → nhiều response.
- **Client streaming:** nhiều request → một response.
- **Bidirectional streaming:** nhiều request ↔ nhiều response.

Ví dụ transcription service có thể dùng server streaming khi client gửi một request và server trả transcript chunks dần theo thời gian. Nếu client vừa upload audio chunks vừa nhận transcript chunks, bidirectional streaming có thể phù hợp hơn.

gRPC thường chạy trên HTTP/2, nơi multiplexing và streaming hỗ trợ tốt các RPC workload.

### GraphQL: Client-driven data shape

GraphQL cho client mô tả chính xác fields và relationships nó cần:

```graphql
query {
  user(id: "123") {
    name
    orders {
      id
      total
    }
  }
}
```

**Schema** trả lời “client được phép hỏi gì?”, còn **Resolver** trả lời “field này lấy dữ liệu bằng cách nào?”. Resolver có thể đọc database, cache, gọi REST API hoặc gọi gRPC service.

`Query` thường dùng cho read operation, còn `Mutation` dùng khi operation làm thay đổi data. Với mutation, client vẫn có thể chọn response fields muốn nhận lại.

### N+1 trong GraphQL

Một GraphQL request từ client không đồng nghĩa backend chỉ thực hiện một DB/service call.

Ví dụ query 100 users rồi mỗi `orders` resolver lại query riêng có thể tạo:

```text
1 query lấy users
+ 100 query lấy orders
= 101 queries
```

Đây là **N+1 problem**. Batching và DataLoader-style loading là những pattern thường dùng để giảm số lần data fetching lặp lại.

GraphQL mang lại flexibility cho client nhưng cũng khiến backend phải quan tâm nhiều hơn tới resolver efficiency, query complexity, authorization và observability.

## Example

Cùng theo dõi một e-commerce system thay vì nhìn ba công nghệ như ba lựa chọn tách rời.

### Starting Point — public API cho third-party developers

Ban đầu platform chỉ cần expose Orders cho external developers. Resource model rõ, HTTP ecosystem phổ biến và consumer cần một interface dễ thử bằng browser tooling hoặc `curl`.

```http
GET /orders/123
POST /orders
```

Ở boundary này, **REST là default hợp lý**. Không có pressure rõ ràng để thêm GraphQL chỉ vì client có thể chọn fields, cũng chưa có lý do buộc external consumer phải dùng generated gRPC client.

### Requirement Changes — service-to-service typed contract

Sau đó `Order Service` cần gọi `Payment Service`. Hai service dùng Java và Go, contract cần strongly typed, code generation hữu ích và interaction có thể phát triển sang streaming.

Boundary này có pressure khác public API. **gRPC trở thành lựa chọn tự nhiên** vì service/method contract và Protobuf phù hợp hơn với nhu cầu nội bộ đó.

Nhưng call site đẹp không loại bỏ remote failure: timeout, retry, deadline và idempotency vẫn phải được thiết kế như distributed-system behavior.

### Requirement Changes Again — mobile dashboard cần data shape linh hoạt

Mobile app xuất hiện nhiều screen khác nhau. Có screen chỉ cần user name và reward points; screen khác cần user, recent orders và payment status. Nếu client phải gọi nhiều endpoint cố định rồi tự compose, network chatter và client orchestration có thể tăng.

Ở client-facing boundary này, **GraphQL đáng cân nhắc** vì client có thể yêu cầu đúng data shape nó cần, còn server resolver layer chịu trách nhiệm compose dữ liệu.

Nhưng flexibility không miễn phí. Nếu resolver fetch từng child record riêng lẻ, một query đẹp phía client có thể biến thành N+1 problem phía backend.

**Why it works:** mỗi boundary được tối ưu theo consumer và pressure thật của nó. ## When to Use

Chọn **REST** khi:

- resource model rõ và CRUD/domain action map tốt vào HTTP;
- public API cần interoperability và ease of consumption;
- caching, HTTP tooling và conventional semantics mang lại nhiều giá trị;
- client không có pressure lớn về flexible data composition.

Chọn **gRPC** khi:

- internal service-to-service communication cần strongly typed contract;
- code generation giữa nhiều language giúp giảm integration ambiguity;
- compact binary payload hoặc streaming là requirement thực tế;
- consumer chấp nhận generated client và RPC-oriented contract.

Chọn **GraphQL** khi:

- nhiều client có data needs khác nhau;
- client cần chọn fields/relationships hoặc compose nhiều nguồn dữ liệu;
- giảm client-side orchestration đáng giá hơn complexity thêm ở server;
- team sẵn sàng xử lý query complexity, resolver performance, authorization và observability.

Không cần ép toàn hệ thống dùng cùng một API style. Boundary khác constraint thì interface khác cũng có thể là thiết kế tốt.

## Common Mistakes

- **“HTTP + JSON = REST”:** HTTP transport không tự động tạo resource-oriented design.
- **“GraphQL luôn tốt hơn REST”:** với CRUD đơn giản, GraphQL có thể thêm schema/resolver/operational complexity không cần thiết.
- **“Một GraphQL request = một DB query”:** resolver layer vẫn có thể phát sinh nhiều query hoặc service call và gây N+1.
- **“gRPC call giống local method nên reliability cũng giống local”:** gRPC vẫn là network call và phải xử lý distributed-system failures.
- **Reuse Protobuf field numbers:** đổi ý nghĩa của tag đã deploy có thể phá wire compatibility.
- **“Internal service thì luôn phải dùng gRPC”:** REST có thể hoàn toàn đủ nếu contract đơn giản và interoperability/tooling quan trọng hơn RPC optimization.
- **“Streaming nghe nhanh hơn nên nên dùng”:** streaming thêm lifecycle, backpressure, cancellation và observability complexity; chỉ dùng khi interaction thật sự cần nhiều message theo thời gian.
- **Chọn theo benchmark chung chung:** latency/throughput phụ thuộc payload, network, implementation và workload. Không nên biến claim marketing thành decision rule nếu chưa đo workload thật.

## Decision Guide

Khi chọn API style cho một boundary, đi theo các câu hỏi này thay vì hỏi “technology nào hiện đại hơn?”:

1. **Consumer là ai?** Browser/mobile, third-party developer hay trusted internal service?
2. **Caller nghĩ theo resource, operation hay data shape?** Contract nào tự nhiên nhất cho domain interaction?
3. **Data need có ổn định không?** Fixed response đủ dùng hay nhiều client liên tục cần shape khác nhau?
4. **Typing và code generation có giá trị bao nhiêu?** Có nhiều language/service team cần shared schema mạnh không?
5. **Interaction pattern là gì?** Unary request-response hay thật sự cần server/client/bidirectional streaming?
6. **Failure model cần gì?** Timeout, retry, idempotency, partial failure và cancellation được thể hiện/quan sát thế nào?
7. **Evolution cost ở đâu?** HTTP contract, Protobuf schema hay GraphQL schema/resolver sẽ được version và migrate ra sao?
8. **Operational complexity có đáng không?** Team có tooling và observability đủ cho GraphQL resolver fan-out hoặc gRPC fleet không?

Nếu hai option đều đáp ứng requirement, ưu tiên option **đơn giản hơn cho boundary hiện tại**. Đừng mua complexity để giải một future problem chưa xuất hiện.

## Practical Takeaway

Một rule thực dụng:

> **REST cho resource-oriented interoperability, gRPC cho typed RPC communication, GraphQL cho client-driven data composition — nhưng boundary constraint mới là source of truth.**

Khi review một API design, đừng chỉ nhìn endpoint/query/proto. Hãy trace toàn flow:

`consumer need → contract shape → runtime call → failure behavior → evolution cost → operational burden`

Nếu lựa chọn chỉ được giải thích bằng “REST phổ biến”, “gRPC nhanh”, hoặc “GraphQL flexible”, reasoning vẫn chưa đủ. Một engineering decision tốt phải nói rõ **boundary nào**, **pressure nào** và **trade-off nào** đang được tối ưu.

## Self-test

1. Mental model ngắn nhất để phân biệt REST, gRPC và GraphQL là gì?
2. Vì sao `POST /createOrder` dùng HTTP nhưng không phải ví dụ RESTful điển hình?
3. Payment retry sau timeout có thể gây lỗi gì, và `Idempotency-Key` giúp như thế nào?
4. Vì sao generated gRPC call vẫn cần timeout/retry/error handling?
5. GraphQL Schema và Resolver khác nhau ở đâu?
6. Một GraphQL request duy nhất có thể gây N+1 như thế nào?
7. Với public CRUD API, internal typed microservices và flexible mobile dashboard, bạn sẽ chọn API style nào cho từng boundary và vì sao?

<details>
<summary>Answers</summary>

1. REST hỏi resource nào, gRPC hỏi service method nào, GraphQL hỏi client cần data shape nào.
2. Vì action `createOrder` được encode trong URL; REST thường để URL biểu diễn resource và HTTP method biểu diễn operation.
3. Client có thể retry và charge nhiều lần; cùng `Idempotency-Key` giúp server nhận ra cùng logical operation và không thực hiện charge lần nữa.
4. Vì lời gọi vẫn đi qua network và có latency, timeout, network failure hoặc remote service unavailable.
5. Schema định nghĩa client có thể query gì; Resolver định nghĩa dữ liệu cho field được lấy bằng cách nào.
6. Một query lấy N parent records rồi resolver fetch child data riêng cho từng parent có thể tạo 1 + N backend calls.
7. REST cho public CRUD vì interoperability/resource model; gRPC cho internal typed communication vì shared typed contract/codegen; GraphQL cho mobile dashboard vì client-driven data composition.
