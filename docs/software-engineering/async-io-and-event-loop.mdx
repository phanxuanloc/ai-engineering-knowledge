# Async I/O & Event Loop

## TL;DR

<TLDR>
Async I/O hiệu quả khi application dành nhiều thời gian **chờ** network, database, disk hoặc external services. `await` cho task yield control để runtime chạy task khác; nó không tạo thêm CPU cores và không tự làm CPU-heavy computation chạy parallel.
</TLDR>

## Why It Matters

Một backend có thể chỉ dùng 20% CPU nhưng vẫn chậm vì hàng trăm requests đang chờ database, LLM hoặc network. Nếu mỗi pending request giữ một execution resource đắt tiền, throughput và memory footprint có thể bị giới hạn bởi waiting model chứ không phải compute.

Async I/O giải quyết câu hỏi: **khi task chưa có gì để chạy vì đang chờ external I/O, execution resource có thể làm việc khác không?** Nó không giải quyết câu hỏi “làm sao có thêm CPU”.

## Mental Model

<Principle label="Mental rule">
I/O-bound tối ưu thời gian chờ; CPU-bound tối ưu compute. Async phù hợp khi bottleneck nằm ở waiting, không phải vì từ khóa `async` tự làm code nhanh hơn.
</Principle>

## Core Concepts

### I/O-bound vs CPU-bound

**I/O-bound** workload dành phần lớn wall-clock time chờ resource bên ngoài: network, database, disk, LLM API, vector database. **CPU-bound** workload dành phần lớn thời gian thực sự tính toán: compression, parsing lớn, image transform, local model inference hoặc heavy preprocessing.

Hai workload cần strategy khác nhau vì bottleneck khác nhau.

### Blocking execution

Trong blocking model, worker/thread có thể bị giữ cho tới khi operation hoàn thành. Mô hình này đơn giản và hoàn toàn hợp lệ ở concurrency thấp, nhưng hàng nghìn long-lived waits có thể làm thread count, stack memory và scheduling overhead tăng mạnh.

### `await` là yield point, không phải magic parallelism

Với proper async I/O, `await` nghĩa là task chưa thể tiếp tục và có thể yield control. Runtime tiến các ready tasks khác rồi resume task khi result ready.

Nếu function được đánh dấu `async` nhưng bên trong lại chạy blocking API hoặc heavy CPU loop, execution resource vẫn bị block.

### Event loop chạy ready work

Event loop điều phối ready tasks và I/O completion events. Một execution thread có thể coordinate rất nhiều pending I/O tasks vì phần lớn tasks không cần CPU cùng lúc.

Ngược lại, heavy CPU computation chạy trực tiếp trên event-loop thread có thể làm mọi connection khác “đứng hình” dù I/O của chúng đã ready.

### Thread pool là bridge cho blocking APIs

Blocking libraries đôi khi không thể đổi ngay. Bounded thread pool cho phép offload blocking work khỏi event-loop thread. Nhưng pool vẫn là capacity boundary: workers hết thì tasks mới phải queue.

### Dependency graph quyết định cái gì được concurrent

Concurrency chỉ overlap work có thể tiến độc lập. Nếu `fetchPermissions(user.id)` cần output từ `fetchUser()`, hai calls không thể fan-out đúng cách. Với AI Agent, tool calls chỉ nên chạy concurrent khi dependency graph cho phép.

### Bounded concurrency bảo vệ downstream

Async giúp tạo rất nhiều pending tasks rất dễ. Nhưng `1000 agent tasks × 3 calls` có thể tạo hàng nghìn simultaneous requests tới LLM, GitHub hoặc Vector DB. Concurrency limit, connection-pool limit, rate limit, timeout và backpressure vẫn cần thiết.

## Example

### Starting Point

Coding Agent cần gọi ba external systems:

```text
GitHub API    ~1.0s
Vector DB     ~0.5s
LLM API       ~4.0s
```

Nếu gọi tuần tự, latency xấp xỉ `5.5s`.

### Requirement Changes

Agent phải phục vụ nhiều sessions đồng thời và latency mục tiêu dưới 5 giây.

### Naive Solution

Tăng số threads và vẫn gọi tuần tự. Cách này có thể chạy được ở load thấp nhưng mỗi waiting operation giữ worker lâu hơn cần thiết.

### Root Cause

Ba calls là I/O-bound và độc lập. Bottleneck không phải thiếu CPU mà là **application đang serialize thời gian chờ**.

### Better Design

Fan-out các independent calls bằng bounded async concurrency:

```ts
const [repo, context, model] = await Promise.all([
  github.fetchRepo(),
  vectorDb.search(query),
  llm.generate(prompt),
]);
```

Trong production, thêm semaphore/rate-limit nếu downstream không chịu được fan-out vô hạn.

### Why It Works

External systems không chạy nhanh hơn. Application chỉ overlap các waiting intervals nên end-to-end latency tiến gần longest branch, khoảng `4s + overhead`, thay vì tổng từng branch.

Nếu còn CPU-heavy preprocessing, phần đó nên offload sang bounded workers/processes phù hợp compute capacity chứ không chạy vô hạn trên event loop.

## When to Use

- Nhiều concurrent HTTP/DB/LLM/vector-store calls và CPU không phải bottleneck.
- Agent fan-out nhiều independent tool/API requests.
- Server cần giữ nhiều network connections mà không muốn một OS thread cho mỗi pending operation.
- Blocking library cần offload vào bounded thread pool.
- Cần kiểm soát concurrency để tránh downstream saturation.

## Common Mistakes

- **`async = parallel`:** async orchestration không tự tạo multi-core parallelism.
- **`async = luôn nhanh hơn`:** CPU-bound work có thể block event loop.
- **Fan-out mọi step:** dependency phải giữ đúng order.
- **Unlimited async tasks:** downstream capacity, memory và connection pools vẫn hữu hạn.
- **Blocking call bên trong async function:** syntax async không biến blocking API thành non-blocking.

## Decision Guide

Chọn concurrency model theo bottleneck:

| Workload | Primary pressure | Starting model |
| --- | --- | --- |
| Ít request, đơn giản | maintainability | blocking có thể đủ |
| Nhiều network/DB/LLM waits | waiting | async I/O + bounded concurrency |
| Blocking SDK trong async app | incompatible API | bounded thread pool |
| Heavy CPU compute | compute | bounded threads/processes/workers |
| Mixed workload | cả waiting + compute | async orchestration + separate CPU pool |

Sau đó đo queue time, event-loop lag, thread-pool saturation, downstream latency và rate-limit errors thay vì dựa vào keyword `async`.

## Practical Takeaway

Hãy hỏi “task đang **chạy** hay đang **chờ**?”. Nếu phần lớn latency là waiting, async giúp tái sử dụng execution capacity. Nếu phần lớn latency là compute, hãy nghĩ tới bounded parallelism và CPU capacity. Đây là hai bài toán khác nhau.

## Self-test

1. `await` giúp event loop tận dụng thời gian chờ như thế nào?
2. Vì sao async không làm CPU-heavy calculation tự chạy parallel?
3. Khi nào thread pool hữu ích trong async service?
4. Vì sao production async thường vẫn cần bounded concurrency?

<details>
<summary>Answers</summary>

1. Task yield khi result chưa ready để runtime chạy ready task khác và resume sau khi I/O hoàn thành.
2. CPU computation vẫn cần compute resource; từ khóa `async` không tạo thêm cores.
3. Khi cần chạy blocking operation mà không muốn block event-loop thread, bằng một số reusable workers có giới hạn.
4. Vì downstream rate limits, connection pools, memory và service capacity đều hữu hạn.

</details>
