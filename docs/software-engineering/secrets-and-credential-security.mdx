# Secrets & Credential Security

## TL;DR

<TLDR>

Secret management không chỉ là “để key ở đâu”. Một credential an toàn cần được nhìn theo lifecycle: **storage → access → delivery → usage → rotation/revocation**. Khi credential đã bị exposed, hãy coi nó là potentially compromised; xóa khỏi source không làm các bản copy đã tồn tại mất hiệu lực.

</TLDR>

Bảo vệ secret rất quan trọng, nhưng thiết kế tốt còn giả định secret **có thể bị đánh cắp** và giới hạn capability + thời gian mà credential đó có giá trị.

## Core Concepts

### Secret và Credential

**Secret** là thông tin phải giữ bí mật như API key, password, private key hoặc signing key. **Credential** là thông tin/cơ chế dùng để authenticate một identity. Nhiều credentials là secrets, nhưng hai khái niệm không hoàn toàn đồng nghĩa.

### Remove Exposure khác Revoke

Nếu password đã nằm trong Git ba tháng, xóa file hoặc rewrite history không thể thu hồi một bản copy attacker đã lấy trước đó. Rotation/revocation xử lý **validity** của credential.

### Secret Manager không thay Least Privilege

20 services cùng dùng một `PRODUCTION_DB_ADMIN_PASSWORD` vẫn có blast radius lớn dù password nằm trong Secret Manager. Tốt hơn là separate identities với permission phù hợp từng workload.

### Prefer Short-lived, Scoped Credentials

CI/CD chỉ cần deploy không nên giữ cloud-admin key sống vô thời hạn. Khi platform hỗ trợ, workload identity + temporary deploy-only credential giảm cả **credential lifetime** và **privilege**.

<Principle label="Design for credential theft">Đừng chỉ hỏi “credential được cất an toàn chưa?”. Hãy hỏi thêm “nếu nó bị đánh cắp, attacker có quyền gì và dùng được trong bao lâu?”.</Principle>

### Secret Lifecycle

Review nơi secret được lưu, ai có quyền đọc, cách runtime nhận secret, khả năng leak qua logs, cơ chế rotation và cách revoke khi incident xảy ra. Environment variable chỉ là một delivery mechanism, không tự động biến secret thành secure.

## Example

Production database password bị commit vào private repository. Response phù hợp là rotate/revoke credential, chuyển secret khỏi source sang secure runtime/secret-management mechanism, xử lý exposure trong Git history và kiểm tra dấu hiệu misuse khi cần. Repo private không phải lý do để tiếp tục tin credential cũ.

## When to Use

- API keys, database passwords, private/signing keys và OAuth client secrets.
- CI/CD hoặc cloud workloads cần machine-to-machine authentication.
- Incident response khi secret xuất hiện trong Git, logs, artifacts hoặc chat.
- Review architecture có shared admin credentials hoặc long-lived static keys.

## Common Mistakes

- **Repo private nên hard-code được:** private repository vẫn có clones, CI, users và backups.
- **Xóa latest commit là đủ:** credential đã copied vẫn còn valid nếu chưa revoke/rotate.
- **Secret Manager giải quyết mọi thứ:** storage tốt không sửa excessive privilege hoặc shared identity.
- **Environment variable = secure:** security phụ thuộc cả lifecycle và access boundary.
- **Một admin key cho nhiều workloads:** compromise một workload có thể mở blast radius của tất cả.

## Self-test

1. Vì sao xóa leaked password khỏi Git chưa đủ?
2. Secret Manager giải quyết vấn đề nào nhưng không giải quyết Least Privilege như thế nào?
3. Vì sao temporary deploy-only credential tốt hơn static cloud-admin key cho CI?
4. Khi credential bị exposed, rotation/revocation và remove exposure khác nhau ở đâu?

<details>
<summary>Answers</summary>

1. Bản copy đã bị lấy vẫn dùng được cho tới khi credential mất hiệu lực.
2. Nó cải thiện storage/access/delivery, nhưng credential vẫn có thể có permission quá rộng hoặc bị dùng chung quá nhiều workloads.
3. Nó giới hạn cả capability lẫn exploitation window nếu credential bị đánh cắp.
4. Rotation/revocation xử lý validity; remove exposure xử lý nơi credential còn bị lộ.

</details>
