# Abstraction & Encapsulation

## TL;DR

<TLDR>

**Abstraction** định nghĩa capability có ý nghĩa với caller — **WHAT** hệ thống cho phép yêu cầu. **Encapsulation** giữ implementation detail — **HOW** capability đó hoạt động — ở sau boundary.

Hai concept thường đi cùng nhau nhưng không đồng nghĩa. Một interface chỉ có giá trị khi nó bảo vệ một complexity hoặc variability có thật; thêm interface cho mọi class không tự làm design tốt hơn.

</TLDR>

## Why It Matters

Abstraction và encapsulation thường được giải thích bằng định nghĩa kiểu “ẩn chi tiết implementation”. Cách giải thích đó đúng nhưng chưa đủ để ra quyết định thiết kế.

Câu hỏi thực tế hơn là:

> **Khi một implementation thay đổi, phần nào của hệ thống buộc phải biết và thay đổi theo?**

Nếu thay Stripe bằng PayPal, đổi SDK version hoặc thay retry strategy mà business logic của checkout cũng phải sửa theo, implementation detail đã lan quá xa.

Abstraction và encapsulation giúp tạo một boundary để application phụ thuộc vào **capability ổn định**, còn provider-specific mechanics được thay đổi độc lập phía sau boundary đó.

## Mental Model

Hãy hình dung một payment boundary như một quầy dịch vụ. Caller chỉ đưa ra yêu cầu ở ngôn ngữ application; phía sau boundary mới xử lý vendor mechanics.

Caller không cần biết Stripe dùng `PaymentIntent`, PayPal dùng order capture hay provider nào thực hiện request. Implementation phía sau boundary chịu trách nhiệm biến yêu cầu application-level thành provider-specific operations.

<Principle label="Boundary test">Nếu caller phải hiểu vendor detail để sử dụng capability, boundary đang leak phần HOW.</Principle>

## Core Concepts

- **Abstraction** mô tả capability và contract mà caller cần, không phải chi tiết provider thực hiện capability đó.
- **Encapsulation** giữ SDK calls, credentials, retry, state và error mapping ở phía implementation boundary.
- **Meaningful boundary** nói bằng application language như `charge()` thay vì vendor language như `PaymentIntent`.
- **Leaky abstraction** xảy ra khi vendor types hoặc vendor semantics vẫn tràn qua contract.
- **Premature abstraction** xảy ra khi thêm indirection trước khi có complexity hoặc variability thực sự cần cô lập.

Điểm quan trọng: abstraction quyết định **caller được nhìn thấy gì**; encapsulation quyết định **detail nào bị giữ lại phía sau boundary**.

## Example

### Bước 1 — Stripe-only: direct dependency chưa chắc là vấn đề

Giả sử hệ thống checkout ban đầu chỉ hỗ trợ Stripe:

```ts
class CheckoutService {
  constructor(private readonly stripe: Stripe) {}

  async checkout(input: CheckoutInput) {
    const intent = await this.stripe.paymentIntents.create({
      amount: input.amount,
      currency: input.currency,
      payment_method: input.paymentMethodId,
      confirm: true,
    });

    return {
      paymentId: intent.id,
      status: intent.status,
    };
  }
}
```

Ở thời điểm này business chỉ có một provider, Stripe logic còn nhỏ và requirement chưa cho thấy một dimension of change rõ ràng. Thiết kế này **không tự động sai**. Chưa có lý do bắt buộc phải thêm interface, adapter hay factory chỉ để “đúng pattern”.

### Bước 2 — Requirement thay đổi

Sau đó business muốn hỗ trợ PayPal. Đồng thời Stripe bắt đầu có retry, idempotency, error mapping và provider-specific state riêng.

Một evolution ngây thơ có thể là:

```ts
class CheckoutService {
  constructor(
    private readonly stripe: Stripe,
    private readonly paypal: PayPalClient,
  ) {}

  async checkout(input: CheckoutInput) {
    if (input.provider === 'stripe') {
      // Stripe PaymentIntent, Stripe errors, Stripe retry rules...
    }

    if (input.provider === 'paypal') {
      // PayPal order creation, capture, PayPal errors...
    }
  }
}
```

Bản thân `if` không phải root cause. Vấn đề là `CheckoutService` bắt đầu sở hữu cả **checkout/business orchestration** lẫn **provider-specific payment mechanics**.

## Root Cause: Responsibility và Dependency Bị Trộn

`CheckoutService` thực sự chỉ cần biết: **“Tôi cần charge khoản tiền này.”** Nó không cần biết Stripe dùng `PaymentIntent`, PayPal dùng order capture, provider nào cần idempotency key, SDK nào trả exception gì hay provider-specific status được map thế nào.

Khi những detail này nằm trong checkout, business orchestration phụ thuộc trực tiếp vào infrastructure mechanics.

## Better Design: Từ Provider Detail Đến Application Capability

Khi variability đã có thật, ta đưa provider mechanics ra sau một capability boundary:

```ts
interface PaymentGateway {
  charge(input: ChargeInput): Promise<ChargeResult>;
}
```

Contract này nói bằng ngôn ngữ của application: **charge**.

Stripe adapter giữ Stripe-specific detail:

```ts
class StripePaymentGateway implements PaymentGateway {
  constructor(private readonly stripe: Stripe) {}

  async charge(input: ChargeInput): Promise<ChargeResult> {
    const intent = await this.stripe.paymentIntents.create({
      amount: input.amount,
      currency: input.currency,
      payment_method: input.paymentMethodId,
      confirm: true,
    });

    return {
      paymentId: intent.id,
      status: mapStripeStatus(intent.status),
    };
  }
}
```

PayPal adapter giữ PayPal-specific detail:

```ts
class PayPalPaymentGateway implements PaymentGateway {
  constructor(private readonly paypal: PayPalClient) {}

  async charge(input: ChargeInput): Promise<ChargeResult> {
    const order = await this.paypal.capture({
      amount: input.amount,
      currency: input.currency,
    });

    return {
      paymentId: order.id,
      status: mapPayPalStatus(order.status),
    };
  }
}
```

`CheckoutService` quay lại tập trung vào checkout:

```ts
class CheckoutService {
  constructor(private readonly gateway: PaymentGateway) {}

  checkout(input: ChargeInput) {
    return this.gateway.charge(input);
  }
}
```

## Why It Works

Thiết kế mới không tốt hơn chỉ vì có interface. Giá trị nằm ở **change impact**.

<Principle label="Design outcome">Business orchestration phụ thuộc vào payment capability; provider mechanics phụ thuộc vào vendor SDK. Blast radius của provider change được thu hẹp.</Principle>

## Abstraction Không Đồng Nghĩa Với Interface

Interface là một công cụ để biểu diễn abstraction, nhưng abstraction không bắt đầu từ syntax `interface`.

Nếu hệ thống chỉ có SendGrid và chưa có meaningful variability, một concrete class vẫn có thể encapsulate tốt:

```ts
class EmailSender {
  constructor(private readonly sendGrid: SendGridClient) {}

  async send(message: EmailMessage) {
    // Hide SendGrid payload shape, credentials and error mapping here.
  }
}
```

Caller chỉ biết `emailSender.send(message)`. Nó không cần biết SendGrid payload shape, credentials hay error mapping. Implementation detail vẫn được encapsulate dù chưa có interface.

Chỉ tạo interface khi nó bảo vệ một boundary có ý nghĩa, chẳng hạn có nhiều implementation thật, implementation có complexity đáng cô lập, test cần fake capability này, hoặc vendor detail có khả năng thay đổi độc lập với business policy.

## Leaky Abstraction

Một abstraction bị leak khi contract vẫn bắt caller hiểu implementation detail.

```ts
interface PaymentGateway {
  charge(request: Stripe.PaymentIntentCreateParams): Promise<Stripe.PaymentIntent>;
}
```

Tên là `PaymentGateway`, nhưng input/output vẫn là Stripe types. Nếu chuyển sang PayPal, caller vẫn bị kéo theo Stripe semantics.

Một contract tốt hơn dùng application-level types:

```ts
interface ChargeInput {
  amount: number;
  currency: string;
  paymentMethodId: string;
}

interface ChargeResult {
  paymentId: string;
  status: 'succeeded' | 'pending' | 'failed';
}
```

Abstraction tốt không chỉ đổi tên class. Nó **dịch dependency về ngôn ngữ của application**.

## Premature Abstraction

Không phải mọi direct dependency đều cần “fix”. Nếu system chỉ có một implementation nhỏ, requirement ổn định và vendor detail không lan ra ngoài một module nhỏ, thêm interface + factory + resolver có thể chỉ tạo thêm indirection.

## When to Use

Cân nhắc tạo abstraction/encapsulation boundary khi:

- vendor detail xuất hiện ở nhiều business modules;
- thêm implementation mới buộc sửa core orchestration;
- caller phải map vendor errors hoặc dùng vendor request/response types;
- business tests phải dựng cả infrastructure client;
- implementation có complexity riêng cần thay đổi hoặc test độc lập;
- một dependency thay đổi thường xuyên hơn business policy sử dụng nó.

Giữ direct concrete dependency khi implementation còn nhỏ, ổn định và không tạo change blast radius đáng kể. Điểm quyết định không phải “có bao nhiêu class”, mà là **có một dimension of change đáng cô lập hay chưa**.

## Một Ví Dụ Khác: File Storage

Application thường muốn nói:

```ts
interface FileStorage {
  upload(file: Upload): Promise<StoredFile>;
  getDownloadUrl(fileId: string): Promise<string>;
}
```

Nó không muốn biết bucket naming, AWS credentials, S3 object keys hay signed URL implementation. `S3FileStorage` encapsulate các detail đó. Nếu chuyển sang provider khác, application vẫn có thể giữ cùng capability contract.

Abstraction không phải đặc điểm riêng của payment. Nó là cách quản lý dependency và change boundary có thể áp dụng ở storage, messaging, email, authentication, external APIs và nhiều infrastructure integrations khác.

## Common Mistakes

- **Tạo interface cho mọi class:** syntax không tự tạo meaningful abstraction.
- **Đồng nhất abstraction với encapsulation:** abstraction mô tả WHAT; encapsulation giữ HOW phía sau boundary.
- **Premature abstraction:** tạo hierarchy/factory khi chưa có pressure thật.
- **Leaky abstraction:** contract vẫn expose vendor types hoặc vendor exceptions.
- **Abstraction quá generic:** `execute()` hoặc `process()` che semantic thật và làm caller khó hiểu capability.
- **Giấu quá nhiều business logic vào adapter:** provider adapter nên che provider mechanics, không nuốt luôn business policy của checkout.
- **Đánh giá design chỉ bằng số lượng `if`:** một `if` có thể hoàn toàn hợp lý; hãy nhìn responsibility và change impact phía sau nó.

## Decision Guide

Khi review một boundary, hỏi:

1. Caller thực sự cần capability gì?
2. Detail nào là implementation-specific và nên ở phía sau boundary?
3. Change nào hiện đang lan qua quá nhiều modules?
4. Có meaningful variability hoặc complexity thật chưa?
5. Contract đang nói bằng ngôn ngữ application hay vendor?
6. Nếu implementation đổi, phần business nào thực sự cần biết?

Nếu câu trả lời cho câu 6 là **“gần như không phần nào”**, đó thường là dấu hiệu một abstraction + encapsulation boundary có giá trị.

## Practical Takeaway

Khi gặp một dependency, đừng bắt đầu bằng câu hỏi **“Có nên tạo interface không?”**. Hãy bắt đầu bằng:

> **Caller thực sự cần biết điều gì, detail nào đang thay đổi độc lập, và change đó nên dừng ở boundary nào?**

Khi hệ thống còn ổn định và đơn giản, direct dependency có thể đủ. Khi meaningful change pressure xuất hiện, tách application capability, encapsulate implementation detail và thu hẹp blast radius.

Đó mới là mục tiêu của abstraction và encapsulation trong production code: **kiểm soát knowledge và change**, không phải tăng số lượng layer.
