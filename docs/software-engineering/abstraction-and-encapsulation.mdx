# Abstraction & Encapsulation

## TL;DR

<TLDR>

**Abstraction** định nghĩa capability có ý nghĩa với caller — **WHAT** hệ thống cho phép yêu cầu. **Encapsulation** giữ implementation detail — **HOW** capability đó hoạt động — ở sau boundary. Hai concept thường đi cùng nhau nhưng không đồng nghĩa, và việc tạo interface chỉ có giá trị khi nó bảo vệ một complexity hoặc variability có thật.

</TLDR>

## Khi direct dependency bắt đầu trở thành vấn đề

Giả sử hệ thống checkout ban đầu chỉ hỗ trợ Stripe. Một implementation trực tiếp như sau hoàn toàn có thể hợp lý:

```ts
class CheckoutService {
  constructor(private readonly stripe: Stripe) {}

  async checkout(input: CheckoutInput) {
    const intent = await this.stripe.paymentIntents.create({
      amount: input.amount,
      currency: input.currency,
      payment_method: input.paymentMethodId,
      confirm: true,
    });

    return {
      paymentId: intent.id,
      status: intent.status,
    };
  }
}
```

Ở thời điểm này, business chỉ có một provider và Stripe logic còn nhỏ. Chưa có lý do bắt buộc phải tạo interface, adapter hay factory.

Pressure xuất hiện khi requirement thay đổi. Business muốn hỗ trợ thêm PayPal, Stripe có retry/idempotency/error mapping riêng, và checkout bắt đầu phải hiểu chi tiết của từng SDK.

Một evolution ngây thơ thường trông như sau:

```ts
class CheckoutService {
  constructor(
    private readonly stripe: Stripe,
    private readonly paypal: PayPalClient,
  ) {}

  async checkout(input: CheckoutInput) {
    if (input.provider === 'stripe') {
      // Stripe PaymentIntent, Stripe errors, Stripe retry rules...
    }

    if (input.provider === 'paypal') {
      // PayPal order creation, capture, PayPal errors...
    }
  }
}
```

Vấn đề không nằm ở `if` tự thân. Vấn đề là **CheckoutService đang sở hữu hai loại knowledge không cùng responsibility**:

- checkout/business orchestration;
- provider-specific payment mechanics.

Khi thêm provider thứ ba, đổi Stripe API version, hoặc thay cách map provider errors, core checkout tiếp tục phải sửa.

Một payment use case cần nói bằng ngôn ngữ của application: **charge một khoản tiền**. Nó không cần nói bằng ngôn ngữ của Stripe như `PaymentIntent`, hay PayPal như `Order Capture`.

## Từ provider detail đến application capability

Khi variability đã có thật, có thể đưa provider mechanics ra sau một capability boundary:

```ts
interface PaymentGateway {
  charge(input: ChargeInput): Promise<ChargeResult>;
}
```

Stripe adapter giữ Stripe-specific detail:

```ts
class StripePaymentGateway implements PaymentGateway {
  constructor(private readonly stripe: Stripe) {}

  async charge(input: ChargeInput): Promise<ChargeResult> {
    const intent = await this.stripe.paymentIntents.create({
      amount: input.amount,
      currency: input.currency,
      payment_method: input.paymentMethodId,
      confirm: true,
    });

    return {
      paymentId: intent.id,
      status: mapStripeStatus(intent.status),
    };
  }
}
```

PayPal adapter giữ PayPal-specific detail:

```ts
class PayPalPaymentGateway implements PaymentGateway {
  constructor(private readonly paypal: PayPalClient) {}

  async charge(input: ChargeInput): Promise<ChargeResult> {
    const order = await this.paypal.capture({
      amount: input.amount,
      currency: input.currency,
    });

    return {
      paymentId: order.id,
      status: mapPayPalStatus(order.status),
    };
  }
}
```

`CheckoutService` quay lại tập trung vào checkout:

```ts
class CheckoutService {
  constructor(private readonly gateway: PaymentGateway) {}

  checkout(input: ChargeInput) {
    return this.gateway.charge(input);
  }
}
```

Dependency đã đổi từ:

```text
CheckoutService
  ├─ Stripe SDK
  └─ PayPal SDK
```

thành:

```text
CheckoutService
      ↓
PaymentGateway
  ├─ StripePaymentGateway → Stripe SDK
  └─ PayPalPaymentGateway → PayPal SDK
```

Đây là điểm abstraction và encapsulation gặp nhau:

- `PaymentGateway.charge()` là abstraction: capability ổn định mà checkout cần.
- `StripePaymentGateway` và `PayPalPaymentGateway` encapsulate HOW của từng provider.

## Vì sao design này giảm change impact

Nếu Stripe đổi cách tạo payment, phần thay đổi chủ yếu nằm trong `StripePaymentGateway`.

Nếu thêm PayPal, checkout không cần hiểu PayPal SDK.

Nếu provider trả error model khác nhau, adapter map chúng về error model mà application hiểu.

Điểm quan trọng không phải là code "đẹp hơn". Điểm quan trọng là **blast radius của provider change được thu hẹp**.

Business orchestration phụ thuộc vào payment capability; infrastructure implementation phụ thuộc vào vendor SDK.

## Abstraction không đồng nghĩa với interface

Interface là một công cụ để biểu diễn abstraction, nhưng không phải abstraction nào cũng cần interface.

Nếu hệ thống chỉ có SendGrid và chưa có meaningful variability, một concrete class vẫn có thể encapsulate tốt:

```ts
class EmailSender {
  constructor(private readonly sendGrid: SendGridClient) {}

  async send(message: EmailMessage) {
    // Hide SendGrid payload shape, credentials and error mapping here.
  }
}
```

Caller chỉ biết `EmailSender.send()`. SendGrid detail vẫn được giấu.

Chỉ tạo interface khi nó bảo vệ một boundary có ý nghĩa, ví dụ:

- có nhiều implementation thật;
- implementation có complexity đáng cô lập;
- test cần fake capability này;
- vendor detail có khả năng thay đổi độc lập với business policy.

## Leaky abstraction

Một abstraction bị leak khi contract vẫn bắt caller hiểu implementation detail.

Ví dụ:

```ts
interface PaymentGateway {
  charge(request: Stripe.PaymentIntentCreateParams): Promise<Stripe.PaymentIntent>;
}
```

Tên là `PaymentGateway`, nhưng contract vẫn phụ thuộc trực tiếp vào Stripe types. Nếu chuyển sang PayPal, toàn bộ caller vẫn bị kéo theo.

Một contract tốt hơn dùng application-level types:

```ts
interface ChargeInput {
  amount: number;
  currency: string;
  paymentMethodId: string;
}

interface ChargeResult {
  paymentId: string;
  status: 'succeeded' | 'pending' | 'failed';
}
```

Abstraction tốt không chỉ đổi tên class. Nó **dịch dependency về ngôn ngữ của application**.

## Khi nào abstraction là premature

Không phải mọi direct dependency đều cần "fix".

Nếu system chỉ có một implementation nhỏ, requirement ổn định và vendor detail không lan ra ngoài một module nhỏ, thêm interface + factory + resolver có thể chỉ tạo thêm indirection.

Một heuristic hữu ích:

<Principle label="Timing">Đừng abstract vì "sau này có thể cần". Abstract khi bạn đã thấy một dimension of change cần được cô lập.</Principle>

Các signal thường đáng chú ý:

- cùng một provider detail xuất hiện ở nhiều business modules;
- thêm implementation mới buộc sửa core orchestration;
- caller phải map vendor errors hoặc vendor request types;
- test business logic bắt buộc dựng cả infrastructure client;
- thay implementation làm change blast radius lớn hơn responsibility thực sự.

## Một ví dụ khác: File Storage

Application thường muốn nói:

```ts
interface FileStorage {
  upload(file: Upload): Promise<StoredFile>;
  getDownloadUrl(fileId: string): Promise<string>;
}
```

Nó không muốn biết bucket naming, AWS credentials, S3 object keys hay signed URL implementation.

`S3FileStorage` encapsulate các detail đó. Nếu chuyển provider, application vẫn có thể giữ cùng capability contract.

Pattern reasoning vẫn giống payment:

```text
Business Need
    ↓
Application Capability
    ↓
Implementation Boundary
    ↓
Vendor Detail
```

## Common Mistakes

- **Tạo interface cho mọi class:** syntax không tự tạo meaningful abstraction.
- **Đồng nhất abstraction với encapsulation:** một cái định nghĩa WHAT, cái kia che HOW.
- **Premature abstraction:** tạo hierarchy/factory khi chưa có pressure thật.
- **Leaky abstraction:** contract vẫn expose vendor types hoặc vendor exceptions.
- **Abstraction quá generic:** `execute()` hoặc `process()` che semantic thật và làm caller khó hiểu capability.
- **Giấu quá nhiều business logic vào adapter:** provider adapter nên che provider mechanics, không nuốt luôn business policy của checkout.

## Decision Guide

Khi review một boundary, hỏi:

1. Caller thực sự cần capability gì?
2. Detail nào là implementation-specific và nên ở phía sau boundary?
3. Change nào hiện đang lan qua quá nhiều modules?
4. Có meaningful variability/complexity thật chưa?
5. Contract đang nói bằng ngôn ngữ application hay vendor?
6. Nếu implementation đổi, phần business nào thực sự cần biết?

Nếu câu trả lời cho câu 6 là "gần như không phần nào", đó thường là dấu hiệu một abstraction + encapsulation boundary có giá trị.
