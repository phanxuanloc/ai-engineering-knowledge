# Abstraction & Encapsulation

## TL;DR

<TLDR>

**Abstraction** định nghĩa capability có ý nghĩa với caller — **WHAT** hệ thống cho phép yêu cầu. **Encapsulation** giữ implementation detail — **HOW** capability đó hoạt động — ở sau boundary.

Bài này tập trung vào **thiết kế knowledge boundary**: caller nên biết gì, contract nên nói bằng ngôn ngữ nào, và detail nào phải dừng phía sau boundary. Nếu muốn chẩn đoán vì sao change đang lan quá rộng trước khi thiết kế boundary, xem [Coupling & Cohesion](./coupling-and-cohesion.mdx).

</TLDR>

## Why It Matters

Abstraction và encapsulation thường được giải thích bằng định nghĩa kiểu “ẩn chi tiết implementation”. Cách giải thích đó đúng nhưng chưa đủ để ra quyết định thiết kế.

Câu hỏi trung tâm của bài này là:

> **Caller thực sự cần biết WHAT nào, và HOW nào phải được giữ phía sau boundary?**

Nếu checkout phải hiểu Stripe `PaymentIntent`, PayPal order capture, vendor error code hoặc retry semantics chỉ để yêu cầu “charge khoản tiền này”, implementation knowledge đã leak qua boundary.

Abstraction và encapsulation giúp application phụ thuộc vào **capability có ý nghĩa với domain/use case**, còn provider-specific mechanics được giữ độc lập phía sau boundary đó.

## Mental Model

Hãy hình dung một payment boundary như một quầy dịch vụ. Caller chỉ đưa ra yêu cầu ở ngôn ngữ application; phía sau boundary mới xử lý vendor mechanics.

Caller không cần biết Stripe dùng `PaymentIntent`, PayPal dùng order capture hay provider nào thực hiện request. Implementation phía sau boundary chịu trách nhiệm biến yêu cầu application-level thành provider-specific operations.

<Principle label="Boundary test">Nếu caller phải hiểu vendor detail để sử dụng capability, boundary đang leak phần HOW.</Principle>

## Core Concepts

### Abstraction: expose capability có ý nghĩa

Abstraction mô tả điều caller cần hệ thống làm. Một abstraction tốt thường nói bằng **application language**:

```ts
paymentGateway.charge(input)
```

thay vì bắt caller nói bằng vendor language:

```ts
stripe.paymentIntents.create(params)
```

Abstraction vì thế không chỉ là “ẩn code”. Nó định nghĩa **knowledge contract** giữa caller và implementation.

### Encapsulation: giữ mechanics phía sau boundary

Encapsulation giữ những detail không nên trở thành knowledge của caller, ví dụ:

- SDK calls và payload shape;
- credentials và client configuration;
- provider-specific retry/idempotency mechanics;
- vendor errors và status mapping;
- implementation state hoặc caching detail.

Abstraction quyết định **caller được nhìn thấy gì**; encapsulation quyết định **detail nào bị giữ lại phía sau boundary**.

### Meaningful boundary: nói bằng application language

Một boundary có ý nghĩa khi contract phản ánh capability thật mà application cần. `charge()`, `send()`, `store()` hoặc `publish()` có thể meaningful nếu đó đúng là language của use case.

Ngược lại, đổi tên wrapper thành generic nhưng vẫn expose vendor types không tạo ra knowledge boundary thực sự.

### Leakage và timing

Hai failure mode quan trọng:

- **Leaky abstraction:** contract generic về tên nhưng caller vẫn phải biết HOW của implementation.
- **Premature abstraction:** thêm indirection khi chưa có complexity hoặc variability đủ để boundary mang lại giá trị.

## Example

Bài [Coupling & Cohesion](./coupling-and-cohesion.mdx) đã dùng cùng checkout scenario để chẩn đoán change propagation. Ở đây chỉ lấy đủ context cần thiết và tập trung vào **boundary design**.

### Starting Point — caller đang nói bằng Stripe language

Giả sử checkout gọi Stripe trực tiếp:

```ts
class CheckoutService {
  constructor(private readonly stripe: Stripe) {}

  async checkout(input: CheckoutInput) {
    const intent = await this.stripe.paymentIntents.create({
      amount: input.amount,
      currency: input.currency,
      payment_method: input.paymentMethodId,
      confirm: true,
    });

    return {
      paymentId: intent.id,
      status: intent.status,
    };
  }
}
```

Khi integration nhỏ và ổn định, đây chưa chắc là design sai. Nhưng khi PayPal xuất hiện, hoặc Stripe mechanics bắt đầu có retry/idempotency/error mapping riêng, câu hỏi quan trọng không phải “có bao nhiêu `if`”, mà là:

> **Checkout có thực sự cần biết những provider concepts này không?**

### Root Cause — knowledge boundary bị đặt sai

`CheckoutService` thực sự chỉ cần biết: **“Tôi cần charge khoản tiền này và nhận kết quả application hiểu được.”**

Nó không cần biết Stripe dùng `PaymentIntent`, PayPal dùng order capture, SDK nào trả exception gì hay provider-specific status được map thế nào. Những detail đó là HOW của integration.

### Better Design — define application capability

Boundary bắt đầu từ capability mà caller cần:

```ts
interface ChargeInput {
  amount: number;
  currency: string;
  paymentMethodId: string;
}

interface ChargeResult {
  paymentId: string;
  status: 'succeeded' | 'pending' | 'failed';
}

interface PaymentGateway {
  charge(input: ChargeInput): Promise<ChargeResult>;
}
```

`CheckoutService` chỉ phụ thuộc vào application capability:

```ts
class CheckoutService {
  constructor(private readonly gateway: PaymentGateway) {}

  checkout(input: ChargeInput) {
    return this.gateway.charge(input);
  }
}
```

Provider adapter giữ HOW:

```ts
class StripePaymentGateway implements PaymentGateway {
  constructor(private readonly stripe: Stripe) {}

  async charge(input: ChargeInput): Promise<ChargeResult> {
    const intent = await this.stripe.paymentIntents.create({
      amount: input.amount,
      currency: input.currency,
      payment_method: input.paymentMethodId,
      confirm: true,
    });

    return {
      paymentId: intent.id,
      status: mapStripeStatus(intent.status),
    };
  }
}
```

### Why It Works — caller knowledge được thu hẹp

Thiết kế mới không tốt hơn chỉ vì có interface. Giá trị nằm ở **knowledge ownership**:

- checkout biết `charge(input) → result`;
- adapter biết vendor API, errors, retry và mapping;
- vendor-specific change không bắt caller học thêm vendor semantics nếu application contract không đổi.

Đây là điểm abstraction và encapsulation gặp nhau:

- `PaymentGateway.charge()` là **abstraction** — WHAT caller được phép yêu cầu;
- provider adapter **encapsulate** HOW capability đó được thực hiện.

<Principle label="Design outcome">Boundary tốt giảm lượng implementation knowledge mà caller phải mang theo. Change impact nhỏ hơn là hệ quả của knowledge ownership đúng.</Principle>

## Abstraction Không Đồng Nghĩa Với Interface

Interface là một công cụ để biểu diễn abstraction, nhưng abstraction không bắt đầu từ syntax `interface`.

Nếu hệ thống chỉ có SendGrid và chưa có meaningful variability, một concrete class vẫn có thể encapsulate tốt:

```ts
class EmailSender {
  constructor(private readonly sendGrid: SendGridClient) {}

  async send(message: EmailMessage) {
    // Hide SendGrid payload shape, credentials and error mapping here.
  }
}
```

Caller chỉ biết `emailSender.send(message)`. Nó không cần biết SendGrid payload shape, credentials hay error mapping. Implementation detail vẫn được encapsulate dù chưa có interface.

Chỉ tạo interface khi nó bảo vệ một boundary có ý nghĩa, chẳng hạn có nhiều implementation thật, implementation có complexity đáng cô lập, test cần fake capability này, hoặc vendor detail có khả năng thay đổi độc lập với business policy.

## Leaky Abstraction

Một abstraction bị leak khi contract vẫn bắt caller hiểu implementation detail.

```ts
interface PaymentGateway {
  charge(
    request: Stripe.PaymentIntentCreateParams,
  ): Promise<Stripe.PaymentIntent>;
}
```

Tên là `PaymentGateway`, nhưng input/output vẫn là Stripe types. Nếu chuyển sang PayPal, caller vẫn bị kéo theo Stripe semantics.

Một contract tốt hơn dùng application-level types như `ChargeInput` và `ChargeResult`. Abstraction tốt không chỉ đổi tên class; nó **dịch dependency về ngôn ngữ của application**.

Một boundary cũng có thể leak qua semantics dù type nhìn generic. Ví dụ `status: string` nhưng caller phải biết các giá trị `requires_action`, `requires_capture` của Stripe thì HOW vẫn chưa thực sự được giữ phía sau boundary.

## Premature Abstraction

Không phải mọi direct dependency đều cần “fix”. Nếu system chỉ có một implementation nhỏ, requirement ổn định và vendor detail không lan ra ngoài một module nhỏ, thêm interface + factory + resolver có thể chỉ tạo thêm indirection.

<Principle label="Timing">Đừng abstract vì “sau này có thể cần”. Abstract khi bạn đã thấy một dimension of change hoặc implementation knowledge cần được cô lập.</Principle>

## When to Use

Cân nhắc tạo abstraction/encapsulation boundary khi:

- vendor detail xuất hiện ở nhiều business modules;
- caller phải dùng vendor request/response types hoặc hiểu vendor status/error semantics;
- thêm implementation mới buộc sửa core orchestration;
- business tests phải dựng cả infrastructure client chỉ để exercise business behavior;
- implementation có complexity riêng cần thay đổi hoặc test độc lập;
- một dependency thay đổi thường xuyên hơn business policy sử dụng nó.

Giữ direct concrete dependency khi implementation còn nhỏ, ổn định và không tạo knowledge leakage hoặc change blast radius đáng kể. Điểm quyết định không phải “có bao nhiêu class”, mà là **boundary có đang bảo vệ complexity/variability thực hay không**.

## Common Mistakes

- **Tạo interface cho mọi class:** syntax không tự tạo meaningful abstraction.
- **Đồng nhất abstraction với encapsulation:** abstraction mô tả WHAT; encapsulation giữ HOW phía sau boundary.
- **Premature abstraction:** tạo hierarchy/factory khi chưa có pressure thật.
- **Leaky abstraction:** contract vẫn expose vendor types, vendor exceptions hoặc vendor semantics.
- **Abstraction quá generic:** `execute()` hoặc `process()` che semantic thật và làm caller khó hiểu capability.
- **Giấu business policy vào adapter:** provider adapter nên che provider mechanics, không nuốt luôn checkout policy.
- **Đánh giá design chỉ bằng số lượng `if`:** một `if` có thể hoàn toàn hợp lý; hãy nhìn knowledge ownership phía sau nó.

## Decision Guide

Khi review một boundary, hỏi:

1. Caller thực sự cần capability gì?
2. Contract có nói bằng **application language** không?
3. Detail nào là implementation-specific và nên ở phía sau boundary?
4. Caller còn phải hiểu vendor type, error, status hoặc lifecycle nào không?
5. Có meaningful variability hoặc complexity thật để justify indirection chưa?
6. Nếu implementation đổi mà business requirement không đổi, caller có phải học hoặc sửa theo không?

Nếu câu trả lời cho câu 6 là **“có”**, hãy kiểm tra xem HOW có đang leak qua boundary. Nếu câu trả lời luôn là “không” nhưng abstraction lại tạo nhiều layer khó theo dõi, có thể boundary đang premature hoặc quá generic.

## Practical Takeaway

Khi gặp một dependency, đừng bắt đầu bằng câu hỏi **“Có nên tạo interface không?”**. Hãy bắt đầu bằng:

> **Caller cần biết WHAT nào, HOW nào đang leak, và boundary nào có thể giữ implementation knowledge đúng chỗ?**

Khi hệ thống còn ổn định và đơn giản, direct dependency có thể đủ. Khi meaningful change pressure hoặc knowledge leakage xuất hiện, tách application capability và encapsulate implementation detail.

Mục tiêu của abstraction và encapsulation trong production code là **kiểm soát knowledge**, từ đó giảm change impact — không phải tăng số lượng layer.

4. Một concrete `EmailSender` có thể encapsulate tốt dù chưa có interface không? Vì sao?
