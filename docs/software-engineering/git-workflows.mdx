# Git Workflows

## TL;DR

<TLDR>
Git workflow không chỉ là cách đặt tên branch. Điểm quan trọng là nơi code được tích hợp, branch sống bao lâu, release được hình thành thế nào, history được giữ hay rewrite ra sao, và CI/CD bảo vệ trạng thái cuối cùng như thế nào. Git Flow thiên về release lifecycle; GitHub Flow thiên về Pull Request; GitLab Flow thêm upstream/environment hoặc stable release lines; Trunk-Based Development nhấn mạnh integration liên tục vào trunk.
</TLDR>

## Mental Model

<Principle label="Decision rule">{'Chọn workflow từ release constraint khó thay đổi nhất: cần release train và stabilization, cần nhiều stable version, hay có thể deploy liên tục từ một trunk luôn xanh.'}</Principle>

:::tip[Shortcut]
Nếu chưa có constraint đặc biệt, bắt đầu bằng **GitHub Flow**. Khi team cần merge nhiều lần mỗi ngày, thu nhỏ change và thêm feature flag để tiến tới **Trunk-Based**. Chỉ thêm Git Flow hoặc stable/environment branches khi release constraint thực sự đòi hỏi.
:::

GitHub Flow và Trunk-Based không loại trừ nhau: GitHub Flow mô tả cơ chế branch + PR, còn Trunk-Based mô tả kỷ luật integration. Một team có thể dùng PR nhưng vẫn merge các change rất nhỏ vào trunk nhiều lần mỗi ngày.

#### Command playbook cho cùng một feature `checkout`

- **GitHub Flow:** `git switch main` → `git pull --ff-only` → `git switch -c feature/checkout` → PR vào `main` → CD deploy commit vừa merge.
- **Trunk-Based:** bắt đầu giống GitHub Flow, nhưng branch chỉ chứa một tiny change và quay về `main` trong vài giờ; deploy liên tục với flag OFF, rồi bật flag để release.
- **Git Flow:** `git switch develop` → `git pull --ff-only` → `git switch -c feature/checkout` → PR vào `develop` → tạo `release/2.1.0` từ `develop` → merge vào `main`, tag/deploy → merge release fixes về `develop`.
- **GitLab Flow:** `git switch main` → tạo `feature/checkout` → MR vào upstream `main` → promote cùng commit `main` → `staging` → `production` → deploy.

## Core Concepts

Workflow định nghĩa **đường đi và quality gates**, còn merge strategy định nghĩa **history trông như thế nào sau khi đi qua gate**. Đừng chọn `squash`, `rebase` hay merge commit trước khi xác định branch đích và release path.

### Git Flow lifecycle

```text
feature/* : develop -> develop
release/* : develop -> main + develop
hotfix/*  : main    -> main + develop
```

`release/*` dùng để freeze feature và stabilize một release trong khi `develop` tiếp tục cho release sau. `hotfix/*` phải xuất phát từ production state trên `main`, không từ `develop`.

#### Vì sao `release/*` phải quay lại `develop`?

Giả sử lúc cắt release, cả hai branch cùng chứa commit `A`:

```text
release/2.1.0: A -- X       X = fix do QA phát hiện
develop:       A -- B       B = code cho version 2.2
```

Merge `release/2.1.0` vào `main` chỉ đưa `A + X` tới production. Nó không tự làm commit `X` xuất hiện trong `develop`, vì `develop` đã đi tiếp theo nhánh `A + B`. Do đó cần merge `release/2.1.0` vào `develop`; kết quả là dòng phát triển kế tiếp chứa cả `B` và `X`.

```text
main:          A -- X             deploy v2.1.0
develop:       A -- B -- M        M kết hợp B + X
                         /
                        B   X
```

:::info[Điểm cần nhớ]
Merge-back bảo toàn **release fixes**, không phải deploy ngược từ production. Nếu release branch không có commit mới sau khi tách, merge-back gần như không mang thêm thay đổi. Nếu team không muốn merge cả branch, có thể cherry-pick từng fix, nhưng phải theo dõi để không bỏ sót.
:::

### Merge strategy and history shape

- **Squash merge:** nhiều commit tạm của một PR trở thành một commit logic sạch.
- **Rebase + merge:** giữ các commit có ý nghĩa nhưng làm history tuyến tính.
- **Merge commit:** giữ topology của branch và merge event.
- **Fast-forward:** chỉ di chuyển pointer khi history chưa phân nhánh.
- **Cherry-pick:** lấy một commit cụ thể sang branch khác; hữu ích cho backport fix.

### Rewrite vs preserve history

Local/private history chưa public có thể dùng `rebase`, `amend`, `reset` hoặc interactive rebase. Shared history đã public nên ưu tiên `revert`. Sau rebase trên branch cá nhân đã push, ưu tiên `git push --force-with-lease` thay vì `--force`.

Các command đã học theo mental model:

- `git restore` xử lý file/working tree; `git restore --staged` bỏ file khỏi staging nhưng giữ code.
- `git reset --soft` bỏ commit nhưng giữ code staged; `--mixed` giữ code unstaged; `--hard` bỏ cả code.
- `git commit --amend` viết lại commit cuối.
- interactive rebase dùng `pick`, `reword`, `squash`, `fixup`, `drop`; `--autosquash` kết hợp với `fixup!` để dọn branch.
- `git stash` cất tạm working changes; `apply` giữ stash, `pop` lấy ra và bỏ stash khi thành công.
- `git reflog` là safety net local khi reset/rebase/amend nhầm.
- `git fetch` cập nhật remote-tracking refs mà không tự tích hợp; `git pull` fetch rồi merge/rebase theo config.
- `origin/main` là remote-tracking branch local, không phải branch trực tiếp “nằm trên GitHub”.

### Rollback, revert and roll forward

`git revert` sửa source history bằng một commit đảo thay đổi. **Deployment rollback** đưa production về artifact/version trước. Chúng là hai việc khác nhau.

### Tag, SemVer and release traceability

Semantic Versioning:

```text
fix      -> PATCH
feat     -> MINOR
breaking -> MAJOR
```

Pre-release có thể dùng `alpha`, `beta`, `rc`, ví dụ `v5.0.0-rc.1 -> v5.0.0-rc.2 -> v5.0.0`. Git tag là mốc cố định vào một commit; release chính thức thường phù hợp với annotated tag.

## When to Use

Đừng bắt đầu từ câu hỏi “team lớn hay nhỏ”. Hãy bắt đầu từ constraint:

1. **Cần support đồng thời nhiều version đã phát hành?** Chọn GitLab Flow với stable branches và backport fix vào đúng release line.
2. **Cần feature freeze/QA vài ngày hoặc vài tuần trước mỗi release?** Chọn Git Flow; chấp nhận chi phí `develop`, `release/*` và merge-back.
3. **Có thể release từ main, nhưng change vẫn đi qua PR?** Chọn GitHub Flow.
4. **Có thể chia change cực nhỏ, merge nhiều lần mỗi ngày và che incomplete work?** Áp dụng Trunk-Based discipline, có thể vẫn dùng GitHub PR.

Nếu câu trả lời thay đổi theo repository, workflow cũng có thể khác: mobile client có thể dùng Git Flow, trong khi backend deploy độc lập dùng GitHub Flow hoặc Trunk-Based. Không cần ép toàn công ty vào một branch model.

## Common Mistakes

- Nghĩ branch name quyết định workflow; thực tế integration point và branch lifetime quan trọng hơn.
- Giữ feature branch nhiều tuần trong một team muốn Trunk-Based Development.
- Rebase hoặc force-push shared `main` thay vì dùng `revert`.
- Dùng `git reset --hard` như undo mặc định khi chỉ cần `restore` hoặc `reset --mixed/soft`.
- Test một tổ hợp trên shared testing branch nhưng release một tổ hợp khác mà không có final validation.
- Merge hotfix của Git Flow chỉ vào `main` mà quên đưa fix trở lại `develop`.
- Dùng `release/*` cho mọi deploy dù sản phẩm deploy liên tục và không maintain release line riêng.
- Chỉ dùng mutable Docker tag như `latest` mà không trace được release -> tag -> commit -> immutable artifact.

## Self-test

1. `feature/*`, `release/*`, `hotfix/*` trong Git Flow được tạo từ đâu và merge về đâu?
2. GitHub Flow khác Trunk-Based Development ở điểm bản chất nào?
3. Khi nào nên chọn squash, rebase + merge, merge commit hoặc cherry-pick?
4. Vì sao PR CI pass chưa chắc đủ khi nhiều PR merge gần nhau?
5. `git restore`, `reset`, `revert` khác nhau theo mental model nào?
6. Khi production lỗi, rollback deployment và Git revert khác nhau thế nào? Khi nào roll forward hợp lý hơn?
7. Vì sao `testing = main + feature1 + feature2 + feature3` nhưng production chỉ release `feature1 + feature3` có thể nguy hiểm?
8. Release traceability tốt cần nối được những mốc nào?

<details>
<summary>Answers</summary>

1. Feature: `develop -> develop`; release: `develop -> main + develop`; hotfix: `main -> main + develop`.
2. GitHub Flow chủ yếu mô tả branch/PR workflow; Trunk-Based nhấn mạnh integration rất thường xuyên, branch cực ngắn và thay đổi nhỏ, thường kết hợp feature flags.
3. Squash khi PR là một logical change; rebase + merge khi muốn giữ các commit tốt và history linear; merge commit khi topology branch có giá trị; cherry-pick khi chỉ cần mang một commit cụ thể sang branch khác.
4. Vì các PR có thể pass riêng nhưng tổ hợp cuối trên main lại xung đột logic; merge queue/main CI kiểm tra trạng thái tích hợp mới nhất.
5. `restore` chủ yếu xử lý file/working tree; `reset` di chuyển HEAD/index và phù hợp local unpublished history; `revert` tạo commit mới đảo commit cũ, phù hợp shared history.
6. Deployment rollback đổi artifact đang chạy; Git revert sửa source history. Roll forward hợp lý khi rollback rủi ro hoặc chậm nhưng fix mới nhỏ, rõ và nhanh hơn.
7. Vì trạng thái được QA test khác trạng thái thực sự release; dependency hoặc interaction với feature 2 có thể làm production khác kết quả QA.
8. Ít nhất cần trace được release version -> Git tag -> commit SHA -> immutable artifact/image digest -> production runtime.
