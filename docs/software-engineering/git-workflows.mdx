# Git Workflows

## TL;DR

<TLDR>
Git workflow không phải convention đặt tên branch. Nó là cách team kiểm soát branch lifetime, integration point, release formation và quality gates. GitHub Flow phù hợp khi một `main` luôn deployable; Trunk-Based Development đẩy integration nhanh hơn bằng change cực nhỏ; Git Flow phù hợp release train cần stabilization; GitLab Flow hữu ích khi có downstream environments hoặc nhiều stable release lines.
</TLDR>

## Why It Matters

Một workflow không phù hợp tạo ra chi phí rất thật: branch diverge lâu, merge conflict lớn, QA test sai snapshot, hotfix bị mất khỏi dòng phát triển kế tiếp, hoặc release trở thành một chuỗi merge khó biết code nào thực sự ra production.

Ngược lại, một workflow tốt giúp team trả lời nhanh ba câu:

1. **Change bắt đầu từ đâu?**
2. **Change được tích hợp vào đâu?**
3. **Trạng thái nào thực sự được release?**

Nếu ba câu này không rõ, branch naming dù đẹp đến đâu cũng không cứu được workflow.

## Mental Model

<Principle label="Decision rule">{'Chọn workflow từ release constraint khó thay đổi nhất: cần stabilization trước release, cần nhiều stable version, hay có thể tích hợp và deploy liên tục từ một trunk luôn xanh.'}</Principle>

Hãy nhìn Git workflow qua bốn trục thay vì nhớ tên pattern:

- **Integration point** — `main`, `develop` hay một upstream branch nào là nơi code gặp nhau?
- **Branch lifetime** — branch sống vài giờ, vài ngày hay cả release cycle?
- **Release boundary** — deploy trực tiếp từ integrated branch hay cần release/stable branch?
- **Promotion model** — code đi thẳng tới production hay đi qua downstream environment/release lines?

GitHub Flow và Trunk-Based thường có integration point gần production hơn. Git Flow cố tình thêm release lifecycle. GitLab Flow giữ `main` như upstream nhưng có thể thêm downstream branches để phản ánh environment hoặc stable version.

## Core Concepts

### GitHub Flow — short-lived branch, PR, merge to main

GitHub Flow có model đơn giản:

```text
main → feature/* → Pull Request → main → deploy
```

`main` phải luôn ở trạng thái có thể deploy. Feature branch tồn tại đủ lâu để phát triển, review và CI, nhưng không trở thành release line riêng.

Phù hợp với backend/web service deploy thường xuyên. Nếu team chưa có constraint release đặc biệt, đây thường là baseline dễ vận hành nhất.

### Trunk-Based Development — integration frequency là kỷ luật chính

Trunk-Based không chỉ có nghĩa “dùng `main`”. Điểm cốt lõi là **change rất nhỏ, branch rất ngắn và integration rất thường xuyên**.

Feature lớn được chia thành nhiều lát cắt backward-compatible. Incomplete work có thể được merge dưới feature flag thay vì nằm nhiều tuần trên feature branch.

Một team có thể dùng Pull Request như GitHub Flow nhưng vẫn thực hành Trunk-Based nếu PR nhỏ và quay về trunk trong vài giờ. Vì vậy, hai khái niệm này có thể chồng lên nhau.

### Git Flow — release lifecycle tách khỏi development lifecycle

Git Flow thường có hai long-lived branches:

```text
main     — production history
develop  — integration cho release kế tiếp
```

Và ba branch role chính:

```text
feature/* : develop → develop
release/* : develop → main + develop
hotfix/*  : main → main + develop
```

`release/*` cho phép freeze scope và stabilize trong khi `develop` tiếp tục nhận code cho version sau. `hotfix/*` bắt đầu từ `main` vì production bug phải được sửa dựa trên production state hiện tại.

Chi phí đổi lại là merge-back discipline và nhiều branch state hơn để quản lý.

### GitLab Flow — upstream trước, downstream theo release constraint

GitLab Flow thường giữ `main` làm upstream integration branch, sau đó thêm downstream branch khi thật sự cần:

```text
feature/* → main → staging → production
```

hoặc stable version lines:

```text
main → stable/2.x
     → stable/1.x
```

Điểm quan trọng là thay đổi đi **từ upstream xuống downstream**. Environment branch không nên trở thành nơi phát triển ngược rồi merge lên upstream, vì khi đó source of truth bị phân mảnh.

### Workflow khác merge strategy

Workflow trả lời **change đi qua branch nào**. Merge strategy trả lời **history trông như thế nào sau integration**.

Bạn có thể dùng GitHub Flow với squash merge, rebase merge hoặc merge commit. Đừng chọn `squash` hay `rebase` trước khi xác định integration path và release model.

## Example

Giả sử team có hai sản phẩm:

- backend service deploy nhiều lần mỗi ngày;
- mobile app release hai tuần một lần, cần QA stabilization 2–3 ngày trước khi store submission.

### Starting Point

Ban đầu cả hai repo cùng dùng `feature/* → main` vì đơn giản.

### Requirement Changes

Backend vẫn ổn: PR nhỏ, CI nhanh, deploy liên tục.

Mobile bắt đầu gặp vấn đề: khi QA đang test version 5.2, `main` vẫn nhận feature cho 5.3. Team cần một nơi freeze scope của 5.2 mà không chặn development của 5.3.

### Naive Solution

Một lựa chọn thường thấy là tạo shared `testing` branch và merge ngẫu nhiên các feature vào đó. Nhưng branch này dễ trở thành “giỏ feature”: QA test một tổ hợp, trong khi production lại release subset khác.

### Better Design

- Backend giữ GitHub Flow và dần áp dụng Trunk-Based discipline: branch nhỏ, integration nhanh, feature flag cho incomplete capability.
- Mobile dùng Git Flow: feature vào `develop`; đến release cut thì tạo `release/5.2`; QA fix đi vào release branch; khi pass thì merge vào `main`, tag release và merge-back fix vào `develop`.

### Why It Works

Backend không gánh branch ceremony không cần thiết. Mobile lại có đúng một stabilization boundary mà release constraint yêu cầu. Workflow được chọn theo **release physics** của từng repository, không theo quy mô công ty hay sở thích cá nhân.

## Common Mistakes

- Nghĩ branch name quyết định workflow; thực tế integration point và branch lifetime quan trọng hơn.
- Gọi workflow là Trunk-Based nhưng feature branch vẫn sống hàng tuần.
- Dùng Git Flow cho service deploy liên tục chỉ vì “enterprise team nên có `develop`”.
- Merge production hotfix của Git Flow vào `main` nhưng quên đưa fix về `develop`.
- Dùng environment branch như nơi phát triển độc lập rồi merge ngược lên `main`, phá upstream/downstream model.
- Tạo shared testing branch chứa nhiều feature nhưng release một subset khác mà không test final candidate.
- Đồng nhất deploy với release; feature flag có thể cho phép deploy code trước khi mở capability cho user.

## Decision Guide

Trước khi chọn workflow, hỏi theo thứ tự:

1. **Có thể deploy từ `main` không?** Nếu có, GitHub Flow là baseline tốt.
2. **Change có thể chia nhỏ và merge trong vài giờ không?** Nếu có, thêm Trunk-Based discipline.
3. **Có cần freeze scope để stabilize trước release không?** Nếu có, Git Flow đáng cân nhắc.
4. **Có nhiều stable version phải support đồng thời không?** Nếu có, GitLab Flow với stable branches có thể phù hợp hơn.
5. **Branch này tồn tại vì constraint thật hay vì convention cũ?** Nếu không có release/integration reason rõ ràng, hãy nghi ngờ branch đó.

Không cần một workflow cho toàn công ty. Mỗi repository có thể có release constraint khác nhau.

## Practical Takeaway

Đừng bắt đầu bằng “Git Flow hay GitHub Flow cái nào tốt hơn?”. Hãy bắt đầu bằng **integration frequency + release boundary + branch lifetime**.

Một workflow tốt làm đường đi của change ngắn và rõ nhất có thể nhưng vẫn giữ đúng control mà release model yêu cầu. Mỗi long-lived branch nên tồn tại vì một responsibility cụ thể; nếu không giải thích được responsibility đó, branch có thể chỉ đang tạo thêm state để đồng bộ.

## Self-test

1. GitHub Flow khác Trunk-Based Development ở điểm bản chất nào?
2. Vì sao Git Flow cần merge `release/*` và `hotfix/*` trở lại `develop`?
3. Khi nào GitLab Flow phù hợp hơn GitHub Flow?
4. Một team gọi mình là Trunk-Based nhưng branch sống 10 ngày. Vấn đề nằm ở đâu?

<details>
<summary>Answers</summary>

1. GitHub Flow chủ yếu mô tả branch + PR integration path; Trunk-Based nhấn mạnh integration cực thường xuyên, branch cực ngắn và change rất nhỏ, thường kết hợp feature flags.
2. Để release fix và production hotfix không biến mất khỏi dòng phát triển của release kế tiếp.
3. Khi cần downstream environment branches hoặc nhiều stable release lines trong khi vẫn giữ `main` làm upstream.
4. Team đang thiếu kỷ luật integration cốt lõi của Trunk-Based; việc branch tên gì không thay đổi điều đó.

</details>
