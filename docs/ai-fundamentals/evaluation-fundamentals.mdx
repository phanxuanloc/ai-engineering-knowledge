# Evaluation Fundamentals

## TL;DR

<TLDR>
Evaluation đo một AI system **thực hiện task tốt đến đâu**, không chỉ kiểm tra execution có hoàn tất hay không. Bắt đầu từ task và success criteria, rồi mới thiết kế dataset, evaluators, metrics, slices và production decision.
</TLDR>

<Principle label="Mental rule">
`Execution success != Task success`. Coding Agent tạo được patch chưa có nghĩa patch sửa đúng bug, không gây regression, an toàn và đủ tốt để release.
</Principle>

## Core Concepts

### Task success có nhiều quality dimensions

Một output tốt có thể cần **correctness, relevance, completeness, safety, regression risk, performance, latency** hoặc **cost**. Không đo mọi thứ chỉ vì có thể đo; chọn dimensions có ý nghĩa với task và release decision.

### Test Case mô tả điều kiện thành công

Với open-ended AI system, test case không nhất thiết có một exact answer. Mental model hữu ích là **Situation/Input → Success Criteria → Evaluators → Result**. Một Coding Agent có thể tạo nhiều implementation khác nhau nhưng vẫn đúng nếu chúng thỏa behavior, tests, constraints và không phá public contract.

### Evaluator khác Metric

**Evaluator** là mechanism phán xét output. **Metric** là measurement tóm tắt kết quả evaluation. Ví dụ: test runner là evaluator; test pass rate là metric.

### Overall score không đủ

Aggregate score trả lời gần đúng “toàn hệ thống đang làm tốt đến đâu?”. Slice metric trả lời “system đang thất bại ở đâu?”. Production decision cần cả hai.

## Example

Một Coding Agent hoàn thành 100% tool calls nhưng patch chỉ pass 70% regression tests. Execution thành công, nhưng task success chưa đạt.

Một evaluation tốt sẽ bắt đầu bằng các câu hỏi: patch có sửa đúng bug không, existing behavior có bị regression không, security constraints có pass không, cost và latency có nằm trong production budget không? Sau đó mới chọn evaluator và metric phù hợp.

## When to Use

- Khi bắt đầu thiết kế eval cho prompt, model, agent hoặc RAG system.
- Khi team đang tranh luận “score nào nên đo?” nhưng chưa định nghĩa success criteria.
- Khi cần một map để đọc các bài Evaluation sâu hơn.

## Common Mistakes

- **Chọn metric trước success criteria:** dễ tối ưu con số không đại diện user outcome.
- **Đồng nhất execution với success:** workflow chạy xong chưa chứng minh task đã được giải quyết.
- **Chỉ nhìn overall score:** critical failures có thể bị che bởi common easy cases.
- **Đo quá nhiều dimensions:** tăng cost và noise mà không giúp decision.

## Self-test

1. Vì sao execution success không đồng nghĩa task success?
2. Vì sao success criteria phải xuất hiện trước metric?
3. Evaluator và Metric khác nhau thế nào?
4. Vì sao overall score cao vẫn có thể chưa đủ để release?

<details>
<summary>Answers</summary>

1. Workflow hoàn tất chỉ chứng minh execution; task success còn phụ thuộc correctness, regression, safety và các constraints thực tế.
2. Vì metric chỉ có ý nghĩa khi nó đo một success criterion đã được xác định.
3. Evaluator phán xét output; metric tóm tắt kết quả evaluation.
4. Aggregate có thể che failure trong critical slices hoặc candidate có thể vi phạm hard production constraints.

</details>
