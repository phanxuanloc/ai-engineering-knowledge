# Practical Context Manager

## TL;DR

<TLDR>

`Context Manager` là lớp application/agent quyết định **model cần biết gì cho current decision**, chọn context nào đáng giữ, phân bổ token budget, compress khi cần, preserve working state và evict evidence đã obsolete. Nó không phải `Context Window`: Context Window chỉ là capacity tối đa của một model invocation.

Trong ví dụ xuyên suốt `Fix login 401`, agent không cần nhét toàn bộ repository, logs và history vào một lần gọi model. Nó cần giữ đúng task state, đưa đúng evidence vào đúng decision, rồi thay context khi task tiến triển.

</TLDR>

<Remember title="Budget is a ceiling, not a target">
  Context budget là giới hạn tối đa có thể dùng, không phải quota phải lấp đầy. Context ngắn nhưng sufficient tốt hơn context đầy window nhưng nhiều noise.
</Remember>

## Mental Model

Hãy coi Context Manager như người chuẩn bị bàn làm việc cho **một quyết định cụ thể**. Context Window là kích thước mặt bàn; Context Manager quyết định tài liệu nào cần đặt lên bàn ngay bây giờ, tài liệu nào ghim cố định, tài liệu nào chỉ lấy khi cần và tài liệu nào có thể cất đi.

Với `Fix login 401`, current decision thay đổi theo thời gian:

1. Ban đầu: **401 xảy ra ở đâu?** → cần route, auth middleware, recent error và request path.
2. Sau khi tìm thấy JWT validation: **token bị reject vì sao?** → cần JWT config, decode result, expiry/issuer/audience evidence.
3. Sau khi sửa code: **fix đã đúng chưa?** → cần diff, focused tests và fresh runtime result; old search output có thể không còn cần thiết.

Một thông tin có thể hữu ích cho toàn task nhưng không cần xuất hiện **đồng thời** trong mọi invocation.

<ImportantDistinction title="Context Manager ≠ Context Window">
  Context Window là capacity model có thể xử lý trong một invocation. Context Manager là logic bên ngoài model quyết định information nào xứng đáng chiếm capacity đó cho current decision.
</ImportantDistinction>

## Core Concepts

### Context Items: đơn vị để quản lý context

Context Manager nên làm việc với các `Context Item` thay vì một khối prompt không có cấu trúc. Một item có thể là user request, repository rule, source file fragment, test result, log excerpt, tool output hoặc working-state record.

Metadata/signals hữu ích tùy item gồm:

- `source`: item đến từ user, repository, file, test, log hay tool nào.
- `type`: instruction, constraint, code, evidence, working-state, tool-result...
- `relevance`: mức liên quan tới current decision.
- `priority`: mức nên được giữ khi phải cạnh tranh capacity.
- `freshness`: item có còn phản ánh current state không.
- `tokenCost`: chi phí context ước tính.
- `confidence`: mức tin cậy của interpretation hoặc extracted finding khi phù hợp.

Với `Fix login 401`, `AuthFilter.ts` có thể relevance cao, một log 401 mới có freshness cao, project rule `do not bypass authentication` có priority rất cao, còn một test output từ trước khi sửa code có thể nhanh chóng trở thành stale.

### Retrieval score tạo candidates; selection mới quyết định context

Retrieval trả về **candidate items**. Retrieval score chỉ là một signal cho biết item có vẻ liên quan với query; nó không tự trả lời item có nên vào model context cho current decision hay không.

Selection nên kết hợp nhiều tín hiệu: relevance, current-decision usefulness, priority, freshness, confidence/source quality khi cần, redundancy và token cost.

Ví dụ search `401 jwt` có thể xếp `README authentication setup` cao vì lexical match. Nhưng khi agent đã biết failure xảy ra trong runtime validation, một fresh stack trace và `JwtVerifier.ts` có thể hữu ích hơn cho decision hiện tại dù retrieval score thấp hơn.

<ImportantDistinction title="Retrieve creates options; Select spends capacity">
  Retrieval mở rộng tập candidates. Selection quyết định candidate nào thực sự đáng chiếm Context Window cho bước tiếp theo.
</ImportantDistinction>

Trong `Fix login 401`, user goal và repository auth rules thường là pinned. `JwtVerifier.ts` và latest failing test là working context khi đang chẩn đoán JWT. Full search listing hoặc old logs trở thành evictable sau khi nguyên nhân đã được thu hẹp.

### Practical context budgeting

Budgeting trả lời: **với capacity có hạn, nên dành bao nhiêu chỗ cho information nào để quyết định tiếp theo đủ reliable?**

Budget không phải mục tiêu sử dụng. Nếu pinned context + 3 relevant items chỉ cần 6K token trong một window lớn hơn nhiều, Context Manager không nên thêm 20K token “cho đủ”. Capacity còn trống là bình thường.

Một policy đơn giản có thể:

1. Reserve pinned context trước.
2. Ưu tiên decision-critical evidence.
3. Loại duplicate/stale/low-value items.
4. Compress item lớn chỉ khi vẫn giữ được facts cần thiết.
5. Dừng thêm context khi current decision đã sufficient, dù budget chưa đầy.

### Useful does not mean simultaneous

Task lớn nên được giải qua nhiều model invocation. Mỗi invocation chỉ cần context đủ cho **next decision**, còn important state được preserve giữa các vòng.

`Fix login 401` có thể tách thành:

- Invocation A: locate authentication failure path.
- Invocation B: inspect JWT validation và form hypothesis.
- Invocation C: choose minimal fix dựa trên verified evidence.
- Invocation D: inspect diff + test result và decide whether the fix is complete.

Source files hữu ích ở A không nhất thiết phải tiếp tục tồn tại ở D. Cái cần preserve là findings/decisions đã được xác minh và state cần để tiếp tục task.

<KeyInsight title="Useful does not mean simultaneous">
  Information hữu ích cho toàn bộ task không đồng nghĩa phải giữ trong cùng một Context Window. Preserve state, refresh evidence và assemble lại context theo từng decision.
</KeyInsight>

### Working State: bộ nhớ tác nghiệp giữa các invocation

`Working State` nên là structured state nhỏ, dễ inspect và cập nhật. Với coding agent, nó có thể giữ:

- `goal`: sửa login 401 mà không bypass authentication.
- `constraints`: giữ public API, tuân project rules, chỉ sửa scope cần thiết.
- `findings`: 401 phát sinh sau JWT verification; request tới đúng route.
- `decisions`: tập trung inspect issuer validation thay vì session storage.
- `changesMade`: cập nhật issuer normalization trong `JwtVerifier.ts`.
- `unresolvedQuestions`: production issuer format có giống test fixture không?
- `nextActions`: chạy focused auth tests và replay failing request.

Working State không thay thế raw evidence. Nó giúp carry forward state quan trọng mà không phải giữ toàn bộ history/tool output.

### Raw evidence phải tách khỏi model interpretation

Context Manager cần phân biệt:

- **Raw evidence / facts:** test output, exact log line, source code, config value, HTTP response.
- **Interpretation:** hypothesis, summary, inferred cause hoặc compressed finding do model tạo ra.

Ví dụ raw evidence nói `expected issuer=https://api.example.com` và token chứa `iss=https://api.example.com/`. Model có thể interpret rằng trailing slash gây 401. Interpretation này hữu ích để quyết định inspect code, nhưng chưa phải truth cho tới khi code/test xác minh.

<ImportantDistinction title="Evidence ≠ Interpretation">
  Compression hoặc Working State không được biến một assumption thành fact. Giữ provenance/label đủ rõ để biết đâu là observed evidence và đâu là model interpretation.
</ImportantDistinction>

### Eviction policy

Eviction không có nghĩa quên task. Nó có nghĩa giải phóng context không còn hữu ích trong khi preserve state quan trọng.

Sau khi fix được verify, Context Manager có thể evict:

- long initial search output;
- duplicate 401 logs;
- old test failures từ trước code change;
- source fragments không còn liên quan tới final verification.

Nhưng nên preserve task goal, constraints, verified root cause, decision, changes made và final verification state cho tới khi task hoàn tất.

### Complete lifecycle

Lifecycle thực dụng cho mỗi decision là:

`Current Decision → Retrieve → Context Items → Score/Priority → Select → Budget → Compress → Assemble → LLM → Reason/Act → Update Working State → Evict obsolete context → next decision`

Áp vào `Fix login 401`:

1. **Current Decision:** xác định 401 phát sinh ở route, middleware hay token validation.
2. **Retrieve:** search auth path, đọc error mới, inspect relevant files.
3. **Context Items:** biến findings, code, logs và rules thành items có metadata.
4. **Score/Priority:** đánh giá relevance, freshness, priority, token cost và các signal cần thiết.
5. **Select:** chọn evidence hữu ích nhất cho decision hiện tại.
6. **Budget:** bảo đảm selected set nằm dưới ceiling; không cố lấp đầy.
7. **Compress:** rút gọn long logs/history khi có thể mà vẫn giữ decision-critical evidence.
8. **Assemble:** đặt pinned context, raw evidence, interpretation và working state vào role rõ ràng.
9. **LLM → Reason/Act:** model quyết định inspect/chạy tool/sửa code.
10. **Update Working State:** ghi findings, decisions, changes, unresolved questions và next action.
11. **Evict obsolete context:** bỏ evidence/tool output đã superseded hoặc không còn hữu ích.
12. **Next decision:** build một context mới cho bước kế tiếp thay vì kéo nguyên toàn bộ context cũ.

## Example

Một Context Manager v0 chưa cần ranking model phức tạp. Pseudocode đủ để thể hiện ownership:

```ts
type ContextItem = {
  id: string;
  source: string;
  type: 'instruction' | 'constraint' | 'code' | 'evidence' | 'working-state';
  content: string;
  relevance: number;
  priority: number;
  freshness: number;
  tokenCost: number;
  pinned?: boolean;
};

function buildContext(items: ContextItem[], budget: number) {
  const pinned = items.filter((item) => item.pinned);
  const candidates = items
    .filter((item) => !item.pinned)
    .sort((a, b) =>
      (b.relevance + b.priority + b.freshness) -
      (a.relevance + a.priority + a.freshness),
    );

  const selected = [...pinned];
  let used = pinned.reduce((sum, item) => sum + item.tokenCost, 0);

  for (const item of candidates) {
    if (used + item.tokenCost > budget) continue;
    selected.push(item);
    used += item.tokenCost;
  }

  return selected;
}
```

Đây chỉ là v0 để test lifecycle. Production policy cần xử lý redundancy, trust/provenance, confidence calibration, per-type budget, compression và richer selection. Điểm quan trọng là **retrieval result không tự động trở thành model context**.

Với `Fix login 401`, controlled experiment tiếp theo sẽ chạy cùng một task theo hai mode:

- **Raw-context baseline:** đưa broad retrieved context/tool history vào model với ít management.
- **Managed-context:** Context Items + pinned state + explicit selection/budget + Working State + eviction.

Giữ model/task/tools tương đương và so sánh token usage, irrelevant context, số vòng/tool call, evidence quality và khả năng tìm/verify root cause.

## When to Use

- Coding agent làm task nhiều bước, nhiều tool call hoặc nhiều source file.
- Context có thể vượt practical budget dù Context Window còn lớn.
- Agent cần preserve important state qua nhiều invocation mà không kéo toàn history.
- Cần trace vì sao một evidence được giữ, bị loại, compress hoặc evict.
- Cần phân biệt observed facts với model-generated interpretation trong autonomous workflow.

## Common Mistakes

- **Biến Context Window thành target utilization:** cố lấp đầy capacity thay vì dừng khi context đã sufficient.
- **Dùng retrieval score như selection rule duy nhất:** candidate rank cao không đảm bảo usefulness cho current decision.
- **Pin quá nhiều:** mọi thứ mandatory sẽ khiến Context Manager mất khả năng quản lý budget.
- **Không refresh freshness:** old tool result được giữ sau khi code/state đã thay đổi.
- **Giữ toàn bộ history vì “có thể hữu ích”:** useful không có nghĩa simultaneous.
- **Evict cả state quan trọng:** bỏ root cause/decision/constraint cùng với obsolete evidence khiến agent phải khám phá lại.
- **Promote summary thành fact:** một compressed hypothesis mất provenance rồi được dùng như ground truth ở vòng sau.
- **Đo Context Manager chỉ bằng token reduction:** ít token hơn nhưng thiếu evidence hoặc nhiều vòng hơn không phải improvement.

## My Understanding

Context Manager là responsibility của application/agent layer: nó quyết định model cần information nào cho current decision, không phải chỉ nối tất cả retrieved content thành prompt. Context Window là capacity; Context Manager là policy sử dụng capacity đó.

Practical unit nên là Context Item có metadata đủ để selection không phụ thuộc một retrieval score duy nhất. Pinned context giữ goal/critical constraints; working context thay đổi theo decision; evictable context được release khi superseded. Budget là ceiling, không phải quota phải fill.

Với task lớn như `Fix login 401`, agent có thể tiến qua nhiều invocation và chỉ preserve Working State quan trọng gồm goal, constraints, findings, decisions, changes made, unresolved questions và next actions. Raw evidence cần tách khỏi interpretation để hypothesis sau compression không bị biến thành truth.

Checkpoint này mới chốt mental model và design của Practical Context Manager. Chưa có implementation/experiment để chứng minh policy thực sự cải thiện context quality.
