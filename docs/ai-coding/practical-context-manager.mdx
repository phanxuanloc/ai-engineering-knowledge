# Practical Context Manager

## TL;DR

<TLDR>

`Context Manager` là lớp application/agent quyết định **model cần biết gì cho current decision**. Nó chọn context, phân bổ token budget, preserve working state và evict evidence đã obsolete. Nó không phải `Context Window`: Context Window chỉ là capacity tối đa của một model invocation.

Trong ví dụ xuyên suốt `Fix login 401`, agent không cần nhét toàn bộ repository, logs và history vào một lần gọi model. Nó cần giữ đúng task state, đưa đúng evidence vào đúng decision, rồi thay context khi task tiến triển.

</TLDR>

<Remember title="Budget is a ceiling, not a target">
  Context budget là giới hạn tối đa có thể dùng, không phải quota phải lấp đầy. Context ngắn nhưng sufficient tốt hơn context đầy window nhưng nhiều noise.
</Remember>

## Mental Model

Hãy coi Context Manager như người chuẩn bị bàn làm việc cho **một quyết định cụ thể**. Context Window là kích thước mặt bàn; Context Manager quyết định tài liệu nào cần đặt lên bàn ngay bây giờ, tài liệu nào ghim cố định, tài liệu nào chỉ lấy khi cần và tài liệu nào có thể cất đi.

Với `Fix login 401`, current decision thay đổi theo thời gian:

1. Ban đầu: **401 xảy ra ở đâu?** → cần route, auth middleware, recent error và request path.
2. Sau khi tìm thấy JWT validation: **token bị reject vì sao?** → cần JWT config, decode result, expiry/issuer/audience evidence.
3. Sau khi sửa code: **fix đã đúng chưa?** → cần diff, focused tests và fresh runtime result; old search output có thể không còn cần thiết.

Một thông tin có thể hữu ích cho toàn task nhưng không cần xuất hiện **đồng thời** trong mọi invocation.

<ImportantDistinction title="Context Manager ≠ Context Window">
  Context Window là capacity model có thể xử lý trong một invocation. Context Manager là logic bên ngoài model quyết định information nào xứng đáng chiếm capacity đó cho current decision.
</ImportantDistinction>

## Core Concepts

### Context Items: đơn vị để quản lý context

Context Manager nên làm việc với các `Context Item` thay vì một khối prompt không có cấu trúc. Một item có thể là user request, repository rule, source file fragment, test result, log excerpt, tool output hoặc working-state record.

Metadata/signals hữu ích tùy item gồm `source`, `type`, `relevance`, `priority`, `freshness`, `tokenCost` và `confidence` khi phù hợp. Với `Fix login 401`, `AuthService.ts` có thể relevance cao, một log 401 mới có freshness cao, repository auth rule có priority rất cao, còn một design note cũ có thể nhanh chóng trở thành stale.

### Retrieval score tạo candidates; selection mới quyết định context

Retrieval trả về **candidate items**. Retrieval score chỉ là một signal cho biết item có vẻ liên quan với query; nó không tự trả lời item có nên vào model context cho current decision hay không.

Selection nên kết hợp nhiều tín hiệu: relevance, current-decision usefulness, priority, freshness, confidence/source quality khi cần, redundancy và token cost.

<ImportantDistinction title="Retrieve creates options; Select spends capacity">
  Retrieval mở rộng tập candidates. Selection quyết định candidate nào thực sự đáng chiếm Context Window cho bước tiếp theo.
</ImportantDistinction>

### Practical context budgeting

Budgeting trả lời: **với capacity có hạn, nên dành bao nhiêu chỗ cho information nào để quyết định tiếp theo đủ reliable?** Budget không phải mục tiêu sử dụng. Nếu pinned context + vài relevant items đã sufficient, Context Manager nên dừng dù Context Window vẫn còn chỗ.

Một policy v0 có thể:

1. Reserve pinned context trước.
2. Loại stale hoặc clearly irrelevant items.
3. Score các selectable candidates theo nhiều signal.
4. Chọn item tốt nhất khi còn budget.
5. Dừng khi current decision đã sufficient hoặc chạm ceiling.

### Useful does not mean simultaneous

Task lớn nên được giải qua nhiều model invocation. Mỗi invocation chỉ cần context đủ cho **next decision**, còn important state được preserve giữa các vòng.

`Fix login 401` có thể tách thành locate failure path → inspect JWT validation → choose minimal fix → verify diff/tests. Source files hữu ích ở vòng đầu không nhất thiết phải tiếp tục tồn tại ở vòng cuối.

<KeyInsight title="Useful does not mean simultaneous">
  Information hữu ích cho toàn bộ task không đồng nghĩa phải giữ trong cùng một Context Window. Preserve state, refresh evidence và assemble lại context theo từng decision.
</KeyInsight>

### Working State: bộ nhớ tác nghiệp giữa các invocation

`Working State` nên là structured state nhỏ, dễ inspect và cập nhật. Với coding agent, nó có thể giữ `goal`, `constraints`, `findings`, `decisions`, `changesMade`, `unresolvedQuestions` và `nextActions`.

Working State không thay thế raw evidence. Nó giúp carry forward state quan trọng mà không phải giữ toàn bộ history/tool output.

### Raw evidence phải tách khỏi model interpretation

Context Manager cần phân biệt raw evidence/facts với model interpretation. Ví dụ exact test output hoặc code là evidence; hypothesis rằng trailing slash ở issuer gây 401 là interpretation cho tới khi được code/test xác minh.

<ImportantDistinction title="Evidence ≠ Interpretation">
  Compression hoặc Working State không được biến một assumption thành fact. Giữ provenance/label đủ rõ để biết đâu là observed evidence và đâu là model interpretation.
</ImportantDistinction>

### Eviction policy

Eviction không có nghĩa quên task. Nó có nghĩa giải phóng context không còn hữu ích trong khi preserve state quan trọng. Sau khi fix được verify, long initial search output, duplicate logs, old failures và superseded source fragments có thể bị evict; task goal, constraints, verified root cause và final verification state vẫn phải được giữ tới khi task hoàn tất.

### Complete lifecycle

Lifecycle thực dụng cho mỗi decision là:

`Current Decision → Retrieve → Context Items → Score/Priority → Select → Budget → Compress → Assemble → LLM → Reason/Act → Update Working State → Evict obsolete context → next decision`

## Example

Một Context Manager v0 chưa cần ranking model phức tạp. Policy dưới đây đủ để làm rõ ownership: mandatory items luôn được giữ; selectable items bị lọc theo freshness/relevance, được score rồi lấy lần lượt trong token budget.

```ts
function score(item: ContextItem) {
  return item.relevance * 0.5 + item.priority * 0.3 + item.freshness * 0.2;
}

function select(items: ContextItem[], budget: number) {
  const pinned = items.filter((item) => item.kind === 'mandatory');
  const candidates = items
    .filter((item) => item.kind === 'selectable')
    .filter((item) => item.freshness >= 0.25 && item.relevance >= 0.3)
    .sort((a, b) => score(b) - score(a));

  const selected = [...pinned];
  let used = pinned.reduce((sum, item) => sum + item.tokenCost, 0);

  for (const item of candidates) {
    if (used + item.tokenCost > budget) continue;
    selected.push(item);
    used += item.tokenCost;
  }

  return selected;
}
```

Hãy bấm `Play flow` để xem toàn bộ task chạy xuyên suốt, hoặc dùng timeline / `Previous` / `Next` để dừng ở từng checkpoint. Ở mỗi bước, quan sát đồng thời ba vùng: **Context Window now**, **Working State** và **Candidate / dropped context**. Mỗi item mang trạng thái rõ ràng như `Candidate`, `Pinned`, `Selected`, `Preserved`, `Compressed`, `Evicted` hoặc `Rejected`, nên có thể theo dõi chính xác thông tin nào còn ở trong model input và vì sao thông tin khác đã ra ngoài window.

Điểm quan trọng nhất nằm ở bước **Budget pressure**: Context Window tăng tới gần đầy, Context Manager không cố nhét thêm dữ liệu mà phải preserve state quan trọng, compress history/evidence phù hợp và evict item đã obsolete. Sau đó context được re-assemble cho decision tiếp theo với capacity được giải phóng nhưng root cause, constraint và decision quan trọng vẫn còn trong Working State.

Đây vẫn là simulator có scenario cố định, chưa phải Context Manager production. Giá trị của nó là làm trực quan ba ý khó thấy trong v0 cũ: **context thay đổi theo thời gian**, **useful không có nghĩa simultaneous**, và **khi Context Window thiếu chỗ thì manager phải chủ động preserve / compress / evict / rebuild thay vì chỉ báo over-budget**.

## When to Use

- Coding agent làm task nhiều bước, nhiều tool call hoặc nhiều source file.
- Context có thể vượt practical budget dù Context Window còn lớn.
- Agent cần preserve important state qua nhiều invocation mà không kéo toàn history.
- Cần trace vì sao một evidence được giữ, bị loại, compress hoặc evict.
- Cần phân biệt observed facts với model-generated interpretation trong autonomous workflow.

## Common Mistakes

- **Biến Context Window thành target utilization:** cố lấp đầy capacity thay vì dừng khi context đã sufficient.
- **Dùng retrieval score như selection rule duy nhất:** candidate rank cao không đảm bảo usefulness cho current decision.
- **Pin quá nhiều:** mọi thứ mandatory sẽ khiến Context Manager mất khả năng quản lý budget.
- **Không refresh freshness:** old tool result được giữ sau khi code/state đã thay đổi.
- **Giữ toàn bộ history vì “có thể hữu ích”:** useful không có nghĩa simultaneous.
- **Evict cả state quan trọng:** bỏ root cause/decision/constraint cùng với obsolete evidence khiến agent phải khám phá lại.
- **Promote summary thành fact:** một compressed hypothesis mất provenance rồi được dùng như ground truth ở vòng sau.
- **Đo Context Manager chỉ bằng token reduction:** ít token hơn nhưng thiếu evidence hoặc nhiều vòng hơn không phải improvement.

## My Understanding

Context Manager là responsibility của application/agent layer: nó quyết định model cần information nào cho current decision, không phải chỉ nối tất cả retrieved content thành prompt. Context Window là capacity; Context Manager là policy sử dụng capacity đó.

Practical unit là Context Item có metadata đủ để selection không phụ thuộc một retrieval score duy nhất. Pinned context giữ goal/critical constraints; working context thay đổi theo decision; evictable context được release khi superseded. Budget là ceiling, không phải quota phải fill.

Lifecycle simulator làm mental model này dễ quan sát hơn selection demo v0: cùng một task được chia thành nhiều decision, context item thay đổi trạng thái qua từng invocation, Working State carry forward phần cần nhớ, và budget pressure buộc manager phải compress/evict rồi rebuild model input. Điều này chứng minh Context Manager không chỉ là bước ranking trước một LLM call mà là **một vòng đời quản lý context liên tục quanh toàn bộ agent task**. Tuy vậy, simulator vẫn chưa chứng minh managed context tốt hơn raw context trên một coding task thật.
