# Context Engineering Map

Trang này là **entry point + canonical lifecycle** của Context Engineering. Nó không lặp lại toàn bộ chi tiết; mục tiêu là giúp recall mental model trong khoảng 30 giây rồi đi tới đúng deep dive.

## One Mental Model

> **Context Window là cái bàn. Context là những thứ đặt trên bàn. Context Engineering là quyết định đúng thứ cần đặt lên bàn cho current decision.**

Nguyên tắc xuyên suốt: **Relevant context > More context**. Window lớn hơn tăng capacity nhưng không tự làm retrieval, selection, quality, freshness hay trust tốt hơn.

**Feedback loop:** sau `Update State & Refresh`, agent quay lại `Sources / Retrieve` cho **next decision**. Working State giữ goal, constraints và verified findings; stale hoặc duplicate evidence được evict. Loop được giải thích bằng prose để primary lifecycle vẫn dễ đọc.

## Four Layers

### 1. Foundations & Lifecycle

**Question:** model cần information nào và nó đến từ đâu?

- Context ≠ Context Window.
- Prompt chỉ là một phần của context.
- Sources tạo khả năng; Retrieve tạo candidates; Select tiêu context capacity.
- Selection phải dựa trên current decision.
- Useful cho toàn task không có nghĩa simultaneous trong một invocation.
- Working State giữ goal/constraints/verified findings qua các invocation.

→ [Context Engineering: Foundations & Lifecycle](./context-engineering.mdx)

### 2. Context Optimization

**Question:** selected context đã đủ tốt và được đóng gói hiệu quả chưa?

- `Good Context = Relevant + Sufficient + Low Noise + Low Redundancy + Fresh + Correct`.
- Budget là ceiling, không phải quota.
- Compression giữ meaning cần thiết với representation cost thấp hơn.
- Assembly tách authority, task, state và evidence rõ ràng.
- Raw evidence phải phân biệt với model interpretation.

→ [Context Optimization](./context-optimization.mdx)

### 3. Context Operations

**Question:** làm sao biết context lifecycle đang hoạt động đúng và an toàn?

- Trace retrieval/selection/budget/freshness/outcome thay vì chỉ nhìn final answer.
- Metrics phải gắn với stage và task outcome, không tối ưu vanity score.
- Freshness/version giúp phát hiện stale evidence.
- Provenance + trust boundaries ngăn untrusted context trở thành high-authority instruction.
- Observability phải cân bằng privacy và redaction.

→ [Context Operations](./context-operations.mdx)

### 4. Practical Context Manager

**Question:** application/agent layer thực thi các quyết định trên thế nào?

- Context Item + metadata/signals.
- pinned / working / evictable context.
- selection, budget và compact Working State.
- raw evidence vs interpretation.
- eviction và lifecycle qua nhiều model invocation.
- minimal Context Manager v0 + controlled raw-context vs managed-context experiment đã hoàn thành learning evidence.

→ [Practical Context Manager](./practical-context-manager.mdx)

## The Distinctions to Remember

1. **Context ≠ Context Window** — information khác capacity.
2. **Context Manager ≠ Context Window** — application decision logic khác model capacity.
3. **Retrieve ≠ Select** — retrieval tạo options; selection quyết định thứ đáng chiếm capacity.
4. **Select ≠ Budget ≠ Compress** — chọn cái gì; phân bao nhiêu capacity; biểu diễn với ít token hơn.
5. **Evidence ≠ Interpretation** — raw fact khác hypothesis/summary.
6. **Useful ≠ Simultaneous** — useful cho task không đồng nghĩa phải tồn tại cùng lúc.

## Completion Evidence

Context Engineering đã hoàn thành ở mức `understood`: learner đã qua final review/self-test, hoàn thành Practical Context Manager simulator và controlled raw-context vs managed-context experiment. Evidence cho thấy learner có thể giải thích các distinction và decision rule xuyên suốt topic:

- `Context Window` là model capacity; `Context` là information được supply; `Context Manager` là application/agent decision layer quản lý information đó;
- retrieval tạo candidates, còn selection quyết định item nào thực sự vào context bằng nhiều signal thay vì chỉ retrieval score;
- budget là maximum capacity, không phải quota; mục tiêu là minimum sufficient context;
- managed context có thể dùng nhiều cumulative tokens hơn nhưng vẫn tốt hơn cho từng invocation nhờ context decision-specific, ít noise và peak-context pressure thấp hơn;
- task lớn có thể được chia qua nhiều invocation, với goal, constraints, decisions, verified results và remaining work được preserve thay vì carry toàn bộ history.

Mốc này là evidence của understanding, không tự động chứng minh khả năng vận hành một production Context Manager độc lập. Vì vậy progress không được nâng thành `applied` hoặc `mastered`.
